## 1. 目的

本書は、画像アーカイブ管理ビューアのMVPを実装するための開発環境、採用技術、NuGetパッケージ、ソリューション構成、ビルド設定、テスト方針、ログ方針および実装順序を定義する。

本書で次を確定する。

- 開発に使用するIDEと.NETバージョン
- WPFプロジェクトの基本設定
- SQLiteへのアクセス方法
- MVVM、DI、ログ、テストに使用するライブラリ
- ソースコードと実行時データの配置
- 開発用・配布用ビルドの方針
- MVPを段階的に作る実装順序

## 3. 開発環境

### 3.1 必須環境

- Windows 11 x64
- Visual Studio 2026
- .NETデスクトップ開発ワークロード
- .NET 10 SDK
- Git for Windows

Visual Studioでは「WPFアプリケーション」を選び、「WPFアプリケーション (.NET Framework)」は選択しない。

### 3.2 推奨ハードウェア

本アプリ自体は一般的なWindows PCで動作させるが、開発環境では次を推奨する。

- CPU: 4コア以上
- メモリ: 16GB以上
- ストレージ: SSD
- 開発・テスト用空き容量: 20GB以上

ZIP再構築テストでは、元ZIP、一時ZIP、更新前ZIPが一時的に共存するため、実データに近い大容量テストを行う場合は追加の空き容量を確保する。

### 3.3 .NET 10の採用理由

- LTSであり、MVP開発開始時点で長期サポート対象
- WPFの現行.NET実装を利用できる
- C#、非同期処理、DI、ログ、テスト環境を統一できる
- `long` / `Int64`による64bit Unix timeを標準的に扱える

### 3.4 SDKバージョン固定

開発者、CI、将来のビルドでSDK差異を減らすため、ソリューションルートに `global.json` を置く。

初期作成時にインストール済みの.NET 10 SDKを確認し、そのSDK機能バンドを固定する。

例:

```json
{
  "sdk": {
    "version": "10.0.1xx",
    "rollForward": "latestPatch"
  }
}
```

実際の完全なバージョン番号はプロジェクト作成時に `dotnet --list-sdks` で確認して記載する。

Phase 0では `10.0.403` を固定した。

### 3.5 テストランナー設定

.NET 10 SDKでは、xUnit v3（Microsoft.Testing.Platform）のテストをVSTest経由で実行できない。`dotnet test` を使うため、`global.json` にテストランナーを明示する。

```json
{
  "sdk": {
    "version": "10.0.403",
    "rollForward": "latestPatch"
  },
  "test": {
    "runner": "Microsoft.Testing.Platform"
  }
}
```

この設定がない場合、`dotnet test` は「Testing with VSTest target is no longer supported」というエラーで失敗する。

テスト実行コマンド（ソリューション指定には `--solution` が必要）:

```bash
dotnet test --solution K35Viewer.slnx -c Release
```

### 4.1 プロジェクトを増やさない理由

MVP段階ではApplication、Domain、Infrastructureをフォルダと名前空間で分離し、別プロジェクトにはしない。

次の条件が発生した場合に分割を再検討する。

- Infrastructureへの参照をコンパイル時に強制的に制限したい
- 複数アプリからDomain / Applicationを共有する
- テストビルド時間または依存関係が管理しにくくなる
- 動画や追加アーカイブ形式等で実装規模が大きくなる

## 5. WPFプロジェクト設定

`K35Viewer.App.csproj` の基本方針は次のとおり。

```xml
<Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup>
    <OutputType>WinExe</OutputType>
    <TargetFramework>net10.0-windows</TargetFramework>
    <UseWPF>true</UseWPF>
    <Nullable>enable</Nullable>
    <ImplicitUsings>enable</ImplicitUsings>
    <LangVersion>latest</LangVersion>
    <PlatformTarget>x64</PlatformTarget>
    <InvariantGlobalization>false</InvariantGlobalization>
    <RootNamespace>K35Viewer</RootNamespace>
    <AssemblyName>K35Viewer</AssemblyName>
  </PropertyGroup>
  <ItemGroup>
    <Using Include="System.IO" />
  </ItemGroup>
</Project>
```

WPF SDKの暗黙usingには `System.IO` が含まれないため、`<Using Include="System.IO" />` を明示する。

### 5.1 x64固定

MVPはx64を対象とする。

理由:

- 10,000件以上のアーカイブと画像サムネイルを扱う
- 32bitプロセスのメモリ制限を避ける
- 2038年問題とは別に、x86特有の制約を増やさない
- Windows 11 x64を主対象とする

ARM64対応はMVP完成後に検討する。

### 5.2 コード品質設定

`Directory.Build.props` で全プロジェクトに共通設定を適用する。

```xml
<Project>
  <PropertyGroup>
    <Nullable>enable</Nullable>
    <ImplicitUsings>enable</ImplicitUsings>
    <TreatWarningsAsErrors>true</TreatWarningsAsErrors>
    <AnalysisLevel>latest-recommended</AnalysisLevel>
    <EnforceCodeStyleInBuild>true</EnforceCodeStyleInBuild>
  </PropertyGroup>
</Project>
```

開発初期に外部パッケージ由来の警告等で阻害される場合は、警告全体を無効にせず個別に扱う。

個別に扱う規則は、リポジトリ直下の `.editorconfig` に理由とともに記載する。

| 規則 | 扱い | 理由 |
|---|---|---|
| CA1822（staticにできるメンバー） | 無効 | DI経由で注入して差し替える前提のサービス・Repositoryは、インスタンス状態を使わないメソッドもインスタンスメソッドのままにするため（内部アーキテクチャ設計書 17章） |
| CA1707（アンダースコア） | テストコードのみ無効 | テストメソッド名を `対象_期待動作` の形式で書くため（`tests/.editorconfig`） |

ログの引数でメソッド呼び出しを行うとCA1873が発生するため、ログ出力は `[LoggerMessage]` を使い、引数には変数をそのまま渡す。

### 5.3 外観（テーマ）

画面の見た目は、WPF の Fluent テーマ（Windows 11 の見た目）の暗い配色に固定する（画面一覧 12.1）。

```xml
<!-- App.xaml -->
<Application x:Class="K35Viewer.App" ... ThemeMode="Dark">
    <Application.Resources>
        <ResourceDictionary>
            <ResourceDictionary.MergedDictionaries>
                <ResourceDictionary Source="Themes/AppColors.xaml" />
            </ResourceDictionary.MergedDictionaries>
        </ResourceDictionary>
    </Application.Resources>
</Application>
```

- `ThemeMode` は .NET 10 では試験的なAPIで、使うと警告 WPF0001 が出る。警告はエラー扱い（5.2）のため、App とテストの両方のプロジェクトで、この警告だけを `<NoWarn>$(NoWarn);WPF0001</NoWarn>` で抑える（テストは画面のXAMLを読み込むため）
- 画面の文字・面・枠の色は、Fluent テーマの色（`TextFillColorPrimaryBrush` など）を `DynamicResource` で参照する。色の値をXAMLに直接書かない
- テーマによらず同じ意味を持つアプリ独自の色だけを `Themes/AppColors.xaml` に置く（名前は `K35.` で始める）

| 名前 | 用途 |
|---|---|
| `K35.SelectionFillBrush` | 選択した項目の背景（アクセント色を薄く重ねる） |
| `K35.DangerFillBrush` | 「削除予定」のラベル（白い文字を載せる） |
| `K35.OverlayBrush` | 画面全体を覆う表示（更新中）、画像の上に重ねる表示の背景 |

- ビューアの画像の背景は、テーマによらず暗いままにする（`ViewerView.xaml`）
- 将来、ライト / Windowsの設定に合わせる、を選べるようにするときは、`ThemeMode` を `Light` / `System` に変えるだけで、画面が追従することを前提とする（上の規則は、そのため）
- 標準の部品のスタイルを一部だけ変えるときは、テーマのスタイルを引き継ぐ。`TreeViewItem` はXAMLの `BasedOn="{StaticResource {x:Type TreeViewItem}}"` で引き継げる。`ListViewItem` は、同じ書き方ではテストでの読み込み時に見つからず失敗するため、表示時にコードで、一覧に適用されているスタイル（なければ `TryFindResource(typeof(ListViewItem))`）を元に作る（`LibraryView.ApplyCompactRows`）
- 自動テスト（`ThemeTests`）で、XAMLが参照する色がすべてテーマの中にあること、暗い配色で背景が暗く文字が明るいことを確かめる

## 6. NuGetパッケージ方針

### 6.1 採用パッケージ

| パッケージ | 用途 | 採用理由 |
|---|---|---|
| `CommunityToolkit.Mvvm` | ObservableObject、RelayCommand、AsyncRelayCommand | WPFで使用可能な軽量MVVM Toolkit |
| `Microsoft.Data.Sqlite` | SQLite接続 | 軽量ADO.NETプロバイダー、SQLを直接制御可能 |
| `Microsoft.Extensions.Hosting` | DI、構成、アプリ寿命 | WPF起動・終了とサービス生成を統合 |
| `Microsoft.Extensions.Options.ConfigurationExtensions` | Options設定 | 将来の設定画面と構成ファイルに備える |
| `Serilog.Extensions.Logging` | Microsoft Loggingとの統合 | `ILogger<T>`を維持したままファイル出力 |
| `Serilog.Sinks.File` | ローカルログファイル | 日次・サイズ単位のローリングログ |
| `SharpCompress` | RAR / 7z の読み取り | 純粋な .NET（ネイティブのDLLが要らない）、MIT。RAR 4 / 5 と 7z を読める。ZIP には使わない（ZIP の読み書きは System.IO.Compression のまま） |
| `xunit.v3` | テストフレームワーク（xUnit v3） | Unit Testと結合テスト |
| `xunit.runner.visualstudio` | Visual Studio Test Explorer | IDEからテスト実行 |
| `Microsoft.NET.Test.Sdk` | テスト基盤 | `dotnet test`とTest Explorer |
| `coverlet.collector` | カバレッジ収集 | 任意の品質確認用途 |

### 6.2 採用しないもの

#### Entity Framework Core

MVPでは採用しない。

理由:

- テーブル数とクエリが限定されている
- SQL、インデックス、トランザクション境界を明示的に管理したい
- スキャン時の一括処理と差分更新を直接制御したい

#### Dapper

MVPでは採用しない。

`Microsoft.Data.Sqlite` のコマンドとリーダーで規模的に対応可能と判断する。SQLマッピングが冗長になった場合に再評価する。

#### ほかのアーカイブのライブラリ
RAR / 7z の読み取りには、SharpCompress だけを使う（v0.2.0 の後）。次は採用しない。

- 7-Zip の `7z.dll`（SevenZipSharp など）: 読める形式は最も広いが、ネイティブのDLLを同梱し、ライセンス（LGPL と unRAR の制限）に従って配る必要がある
- Susie プラグイン、統合アーカイバのDLL（caldix で入れる UNLHA32.DLL など）: 多くが32bitで、64bitのアプリから直接読み込めない。利用者がDLLを別に入れる必要もある
- ZIP も SharpCompress に載せ替えること: 作り直し（書き込み）の処理を変えると、壊す危険があるため

ほかの形式（TAR / CBT など）は、GitHub の Issue #21 で検討する。
#### 画像処理ライブラリ

MVPではImageSharp等を導入せず、WPFの `BitmapDecoder`、`BitmapImage`、`TransformedBitmap` 等でJPEG / PNG / GIF / WebPの表示とサムネイル生成を行う。

EXIF回転、色管理、巨大画像のメモリ消費等で不足が判明した場合のみ追加ライブラリを評価する。

GIF / WebP の対応（GitHub の Issue #2）でも、追加のライブラリは入れなかった。検討した候補と、入れなかった理由:

| 候補 | 理由 |
|---|---|
| SixLabors.ImageSharp | WebP / GIF は読めるが、AVIF / HEIC は読めない。全体を読んでから縮小するため、WIC の「縮小しながら読む」より重い。ライセンス（Six Labors Split License）の条件の確認も要る |
| Magick.NET | 形式は多いが、ネイティブの部品が約67MBあり、配布物が大きくなる。信頼できないファイルを読むライブラリで、過去にセキュリティの問題があったため、出どころの分からないアーカイブを開くこのアプリでは、慎重に考える |

WIC は、GIF を標準で読み、WebP / HEIC / AVIF は、Windows の Store の拡張機能があれば読める。開発機では、WebP と HEIF の拡張機能が入っていて、AVIF は入っていなかった。AVIF / HEIC / JPEG XL は、手元のファイルで必要になったときに、改めて選ぶ。

## 7. MVVM方針

### 7.1 CommunityToolkit.Mvvmの使用範囲

- `ObservableObject`
- `[ObservableProperty]`
- `[RelayCommand]`
- `[NotifyCanExecuteChangedFor]`
- `AsyncRelayCommand`

### 7.2 ViewModelの責務

ViewModelは次に限定する。

- 表示状態
- 選択状態
- コマンド
- 入力検証
- Application Serviceの呼び出し
- `OperationResult` のUI反映

ZIP、SQLite、ファイル、ごみ箱を直接操作しない。

### 7.3 UIスレッド

- ObservableCollectionの更新はUIスレッドで行う
- ZIP解析、スキャン、DBアクセス、サムネイル生成はUIスレッドで実行しない
- バックグラウンド結果をまとめてUIへ反映し、項目ごとの過剰なDispatcher呼び出しを避ける

## 8. DI・アプリケーション起動

`Microsoft.Extensions.Hosting` を使用し、WPFの起動・終了とホストの寿命を統合する。

概念例:

```csharp
public partial class App : Application
{
    private readonly IHost _host;

    public App()
    {
        var builder = Host.CreateApplicationBuilder();
        ConfigureServices(builder.Services);
        _host = builder.Build();
    }

    protected override async void OnStartup(StartupEventArgs e)
    {
        await _host.StartAsync();
        _host.Services.GetRequiredService<MainWindow>().Show();
        base.OnStartup(e);
    }

    protected override async void OnExit(ExitEventArgs e)
    {
        await _host.StopAsync();
        _host.Dispose();
        base.OnExit(e);
    }
}
```

### 8.1 サービス寿命

| 種別 | 寿命案 |
|---|---|
| MainWindow / MainViewModel | Singleton |
| LibraryViewModel | Singleton |
| ViewerViewModel | Singleton |
| ViewerSession | Singleton。ただしアーカイブ離脱時に内容を破棄 |

## 9. SQLite開発方針

### 9.1 接続ライブラリ

`Microsoft.Data.Sqlite` を使用し、SQLはRepository内に集約する。

### 9.2 SQLルール

## 13. ZIP処理方針

### 13.1 読み取り

`System.IO.Compression.ZipArchive` のReadモードを使用する。

### 13.2 再構築

ZIP内エントリの削除は元ZIPを直接更新せず、削除対象以外を新しい一時ZIPへコピーする。

### 13.3 圧縮レベル

MVPでは再構築時に `CompressionLevel.Optimal` を基本とし、**元のZIPでほとんど圧縮されていないエントリ（圧縮後が元の95%以上）は、圧縮し直さずにそのまま保存する**（Phase 8で確定）。

JPEG / PNG は圧縮済みで、さらに圧縮しても容量が減らないため、時間をかけて再圧縮しない。測定結果（開発機、150頁・10頁削除）:

| 方式 | 圧縮が効く合成画像（元 24.7MB） | 圧縮済み相当の乱数データ（元 44.0MB） |
|---|---|---|
| `NoCompression` | 作成 約0.4秒 / **48.5MB（約2倍に肥大）** | 作成 約0.1秒 / 41.0MB |
| `Fastest` | 作成 約1.0秒 / 30.0MB（肥大） | 作成 約0.9秒 / **43.3MB（元より約6%肥大）** |
| `Optimal` | 作成 約1.7秒 / 23.1MB | 作成 約1.7秒 / 41.0MB（約15倍遅い） |
| **既定（Optimal＋未圧縮はそのまま保存）** | 作成 約1.9秒 / 23.1MB | 作成 **約0.12秒** / 41.0MB |

- `Fastest` は、圧縮の効かないデータでも元より大きくなるため採用しない。`NoCompression` は圧縮の効くデータで肥大するため、常用しない
- 既定の方式は、圧縮の効くデータでは `Optimal` と同じ容量で、圧縮済みの画像では元と同じ容量を最短の時間で作れる。元より容量が増えるとしても、ほとんど圧縮されていないエントリに限られ、最大でも5%（圧縮後が元の95%以上のものを、圧縮せずに保存するため）
- 検証（開き直して全エントリを展開し、サイズとCRC32を元と突き合わせる）は、44MBで約0.3〜0.5秒

### 13.4 メタデータ

可能な範囲で次を維持する。

- エントリ名
- ディレクトリ構造
- エントリ更新日時
- 削除対象外の非画像エントリ

ZIPコメント、外部属性、特殊な追加フィールド等の完全維持はMVPでは保証しない。実データによるスパイクテストを行う。

Phase 8の実装で、次を維持することを確認した（自動テスト）: エントリ名（日本語を含むUTF-8の名前）、エントリの順序、フォルダのエントリ、画像以外のエントリ、更新日時（ZIPの2秒単位の精度）、外部属性、エントリのコメント。**維持しないもの**: ZIP全体のコメント、特殊な追加フィールド。

**エントリ名の文字コード**: UTF-8のフラグがなく、Shift_JIS（CP932）で保存された古いZIPは、.NETの既定ではエントリ名を正しく読めない（U+FFFD に化ける）。Phase 10 で、UTF-8 として不正な名前を Shift_JIS として読むようにした（内部アーキテクチャ設計書 31.3）。閲覧・解析・再構築のいずれでも正しい名前になり、再構築後は UTF-8 の名前で保存する。UTF-8 でも Shift_JIS でも読めない名前のアーカイブは、名前を壊さないよう更新を中止する（元のアーカイブは変更しない）。

## 14. Windows連携

### 14.1 ごみ箱

RecycleBinServiceを境界として実装する。

Phase 8の実装で確定した方式: `SHFileOperation` に `FOF_ALLOWUNDO | FOF_NOCONFIRMATION | FOF_NOERRORUI | FOF_SILENT` を指定して移動する。**この関数は、ネットワーク上のファイルやごみ箱が無効なドライブでは、確認なしで完全削除してしまう**ため、呼び出す前に次を確認し、1つでも該当すれば呼び出さない（`RECYCLE_BIN_UNAVAILABLE`）。

- UNCパス、ネットワークドライブ、リムーバブルドライブ（固定ドライブ以外）
- ドライブのごみ箱の設定（レジストリ `HKCU\Software\Microsoft\Windows\CurrentVersion\Explorer\BitBucket\Volume\{GUID}`）で、`NukeOnDelete` が有効、またはファイルが `MaxCapacity`（MB）を超える（設定がなければ既定のごみ箱を使う）
- 移動後もファイルが元の場所に残っていれば、失敗として扱う

確認した内容（開発機のローカルドライブ、明示的な統合テスト）: ローカルのファイルをごみ箱へ移動できること、ビューアと同じ共有モード（読み取り・書き込み・削除を許可）で開いたままのファイルも移動できること、ごみ箱に実際に入ること（完全削除ではないこと）。ネットワークドライブでの実際の挙動は、NASを使えないため確認していない（利用不可として更新を中止する）。

初期スパイクでは次を確認する。

- ローカルファイルをごみ箱へ送れること
- 大容量ZIPで処理結果を取得できること
- UNCパスやネットワークドライブでの挙動
- ユーザーキャンセルと失敗を判別できること

ごみ箱利用不能時に完全削除へ自動切替しない。アーカイブ削除ではユーザー承認時のみ完全削除する。

### 14.2 エクスプローラーで表示

`explorer.exe /select,"対象ファイル"` 相当の処理をFileSystemServiceへ集約する。

パス文字列を安全に引用し、存在確認後に起動する。

### 15.3 テストコードの規約

- テストメソッド名は `対象_期待動作` の形式とし、日本語を使用できる。
- `Directory.Build.props` で警告をエラー扱いにしているため、アンダースコアを禁止するCA1707は `tests/.editorconfig` でテストコードに限り無効にする。
- テストプロジェクトでは `Xunit` と `System.IO` を暗黙usingに追加する。
- `InternalsVisibleTo` により、テストからAppプロジェクトのinternal型を参照できる。
- ウィンドウを表示するテスト（一覧の仮想化、キー操作、全画面の確認等）は、専用のSTAスレッドで実行する。キー入力やホイール操作は、ウィンドウにイベントを発行して再現する。画面の更新や非同期処理の完了は、UIのメッセージを処理しながら待つ（共通処理は `WpfTestHelper`）。
- プロセスのメモリ使用量を測るテストは、他のテストと並列に動かさない（xUnitのコレクションで並列実行を無効にする）。WPFの画像のピクセルデータはマネージドヒープの外にあるため、`GC.GetTotalMemory` ではなくプロセスのプライベートバイトで測る。
- バックグラウンド処理（スキャン、サムネイル生成、画像の読み込み）を行うテストは、一時フォルダを削除する前に、処理が終わっていることを確認する。処理の途中で削除すると、後始末が失敗して不安定になる。
- 性能を測るテストの時間は、テストの並列実行で大きく揺れる。時間そのものは出力に記録し、判定は件数や生成された要素数などで行う。時間の上限は、桁違いの遅さだけを検知する緩い値にする。
- xUnit v3のアナライザー(xUnit1051)により、`CancellationToken` を受け取る非同期呼び出しには `TestContext.Current.CancellationToken` を渡す。警告はエラー扱いのため、渡さないとビルドが失敗する。
- 画面のXAMLを読み込むテストは、互いに並列に動かさない（`[Collection(WpfViewsGroup.Name)]` を付ける）。別々のSTAスレッドで同時にXAMLを読み込むと、WPFの内部（`System.IO.Packaging.PackagePart`）で競合し、まれに失敗するため。

正式配布時にMSIXまたはインストーラーを検討する。

### 17.4 リリース

配布物は、GitHub のリリースに ZIP（`K35Viewer-v〈バージョン〉-win-x64.zip`。17.2 のフォルダをまとめたもの）と、そのハッシュ（SHA-256）を書いたファイル（`K35Viewer-v〈バージョン〉-win-x64.zip.sha256`。「〈ハッシュ〉  〈ファイル名〉」の1行）として添付する。ハッシュは、アプリの更新（設定画面の「更新する」）が、ダウンロードした配布物を確かめるために使う。名前は、アプリ（`GitHubReleaseClient`）とそろえる。

- バージョンは `K35Viewer.App.csproj` の `Version` に書き、タグ（`v0.1.0` など）と合わせる。実行ファイルのプロパティには、バージョンとコミット（`0.1.0+〈コミットのID〉`）が入る
- 1.0 より前の版は、試用版（Pre-release）とする
- リリースノートは、版ごとの紹介（`.github/release-notes/〈タグ〉.md`。例: `v0.2.0.md`。あれば）、定型の部分（`.github/release-notes.md`。ダウンロード、アンインストール、Code signing policy、プライバシー）、GitHub が自動で作る変更点、の順に並べる。版ごとの紹介は、タグを打つ前に書いて、コミットしておく。ワークフローが、タグと同じ名前のファイルを探して、先頭に付ける
- 実行ファイルには署名をしていない。初回の起動時に Windows の警告（SmartScreen）が出ることがあるため、リリースノートに対処（「詳細情報」→「実行」）を書く。署名は、広く配るときに検討する（オープンソース向けの無料の署名サービス等。GitHub Actions でビルドすることが条件になるものが多い）

手順:

1. `K35Viewer.App.csproj` の `Version` を上げてコミットし、push する
2. 注釈付きのタグを付けて push する（`git tag -a v0.2.0 -m "35Viewer v0.2.0"`、`git push origin v0.2.0`）
3. GitHub Actions（18章の Release）が、テスト・配布物の作成を行い、ZIP を添付したリリースを**下書き**で作る。タグと `Version` が違えば失敗する
4. GitHub の画面で、リリースノートを確かめて公開する

v0.1.0 は、GitHub Actions を作る前に、手元で作って添付した。

## 18. CI方針

GitHub Actions を使う（`.github/workflows/`）。Windows固有のWPFビルドと、ウィンドウを表示するテストがあるため、Windows のランナー（`windows-latest`）を使う。

| ワークフロー | 動くとき | 行うこと |
|---|---|---|
| CI（`ci.yml`） | main への push、プルリクエスト、手動 | restore → build（Release）→ test（Release）。テスト結果（TRX）を成果物（Artifacts）に置く（失敗したときも） |
| Release（`release.yml`） | タグ（`v*`）の push | バージョンの確認 → `scripts\publish.ps1`（テスト → 発行）→ ZIP → ハッシュ（SHA-256）のファイル → ZIP とハッシュを添付したリリースの下書きを作る（17.4） |
| Release（手動で実行） | 手動 | 上と同じく ZIP まで作り、成果物に置く。リリースは作らない（確認用） |

- SDK は `global.json` に合わせて入れる（`actions/setup-dotnet` の `global-json-file`）
- 使う action（`actions/checkout`、`actions/setup-dotnet`、`actions/upload-artifact`）は、コミットのIDで固定する（タグが差し替えられても、知らない内容が動かないようにするため）
- 権限は最小にする（CI は読み取りだけ。Release は、リリースを作るため `contents: write`）
- 実際のごみ箱を使う統合テストは、環境変数を指定しないため、CI では実行しない
- カバレッジは、まだ出していない（今のテストの実行方式（Microsoft.Testing.Platform）では、`coverlet.collector` が使えないため。出すなら、`Microsoft.Testing.Extensions.CodeCoverage` を追加する）
- **ランナーの画面は、開発機より小さい**（大きさは確かめていないが、幅1280のウィンドウが縮められたことから、1280より狭い）。ウィンドウは画面より大きくできないため、ウィンドウに大きさを指定するテストは、ウィンドウが縮められて、手元と違う結果になる。画面の大きさに関わるテストは、ウィンドウではなく画面（View）に大きさを指定し、その大きさで確かめていることも確認する（`LibraryViewLayoutTests`）。最初の CI で、この理由で1件が失敗した

### Phase 8 ZIP再構築

- 一時ZIP作成

**完了条件:** 複数削除を1回の再構築で反映し、失敗時は元ZIPを保持する。

**実装範囲の補足:**

- 変更確認ダイアログ（DLG-01）で「更新する」を選ぶと、削除予約した画像を除いたZIPを作り、元のZIPをごみ箱へ移して置き換える（UC-11）。手順: 更新できるかの確認（外部変更、ごみ箱を使えるか、空き容量）→ 同じフォルダに一時ZIP（`〜.k35tmp`）を作成 → 開き直して全エントリを検証（サイズとCRC32）→ **安全境界** → 元のZIPをごみ箱へ移動 → 一時ZIPを元の名前へ変更 → DB更新と操作履歴（1トランザクション）→ ライブラリ画面の更新とサムネイルの再生成
- **安全境界**: 一時ZIPの作成と検証まではキャンセルでき、失敗・キャンセルでは一時ZIPを削除して、元のZIPと削除予約を保持する。元のZIPのごみ箱への移動を始めたあとは、キャンセルせずに最後まで完了する。一時ZIPを元の名前にする処理は、他のプログラムが一時的に掴んでいる場合に備えて、待ちながら（0.2秒・0.8秒・2秒後に）最大3回やり直す
- **外部変更の確認**: ビューアでアーカイブを開く直前のファイルのサイズと更新日時を覚えておき、更新の直前と、安全境界の直前に、変わっていないことを確認する。変わっていれば更新を中止する（外部で書き換えられた内容を、古い内容で上書きしない）。ウィンドウが前面に戻ったときにも確認し、変わっていれば閲覧内容が古い可能性を通知する
- 同じアーカイブへの更新は同時に行わない。更新中は画面の操作を受け付けず、ウィンドウを閉じても更新が終わるまで閉じない
- 圧縮方式は13.3、ごみ箱は14.1。ネットワーク上のファイルは、ごみ箱へ退避できないため更新できない（要件定義 11章）
- 自動テスト: `ArchiveWriter`（エントリの保持、削除対象なし、上書きしない、キャンセル、検証、CRC32）、`ArchiveService`（成功、外部変更、ごみ箱の利用不可・失敗、書き込み・検証の失敗、想定外の例外、安全境界の前後のキャンセル、置き換えの失敗、再試行、排他）、画面の流れ（更新して戻る、失敗して留まりやり直す、利用不可、キャンセル、ウィンドウを閉じる）。自動テストは、ごみ箱の代わりに偽の実装を使い、実際のごみ箱を操作しない。実際のごみ箱への移動は、環境変数 `K35_RUN_RECYCLEBIN_TESTS=1` を指定したときだけ行う統合テスト
- **未対応・課題**: CP932のエントリ名のアーカイブ（13.4）、更新中に異常終了した場合に残る一時ファイル（`〜.k35tmp`）の起動時の後始末（Phase 10）、更新の進行状況の割合表示（現在は処理の段階のみ）、ネットワークドライブでの実機確認
- 画面の見た目の確認（更新中の表示、ダイアログの配置）は、全フェーズの完了後に行う
