## 1. 目的

本書は、画像アーカイブ管理ビューアのMVPを実装するための内部アーキテクチャを定義する。

主な目的は次のとおり。

- UIとファイル操作を分離する
- ZIP更新、SQLite、サムネイル生成等の責務を明確にする
- 長時間処理をバックグラウンドで安全に実行する
- ファイル操作成功後にのみDBを更新する
- 将来の追加形式対応や画面追加を妨げない構造とする
- MVPで必要以上の抽象化を行わない

## 2. 前提技術

- 言語: C#
- ランタイム: .NET 10
- UI: WPF
- DB: SQLite
- アーカイブ: ZIP / CBZ
- 画像: JPEG / PNG / GIF / WebP（GIF / WebP は、40章）
- ZIP基本操作: `System.IO.Compression`
- 非同期処理: `async` / `await` とキャンセルトークンを基本とする

## 3. 全体構成

MVPでは、論理的に次の4層へ分離する。

```text
Presentation
  Library / Viewer / Dialog / Toast
          |
          v
Application
  Use Case / Service / Session
          |
          v
Domain
  Archive / Folder / OperationResult 等
          |
          v
Infrastructure
  SQLite / ZIP / FileSystem / RecycleBin / ThumbnailCache
```

依存方向は原則として上から下とする。

UIからSQLiteやZIPを直接操作しない。

## 4. Presentation層

### 4.1 役割

- ライブラリ画面の表示とユーザー操作受付
- ビューアの1枚表示・一覧表示
- 確認ダイアログ
- トースト通知
- ViewModelと画面状態の管理

### 4.2 View

MVPでは主に次を持つ。

- `MainWindow`
- `LibraryView`
- `ViewerView`
- `ArchiveChangeConfirmDialog`
- `ArchiveDeleteConfirmDialog`
- `ToastHost`

ライブラリとビューアは別ウィンドウではなく、`MainWindow` 内で切り替える。

### 4.3 ViewModel

#### MainViewModel

- 現在表示する画面の切替
- 全体的なナビゲーション
- 長時間処理状態の連携

#### LibraryViewModel

- フォルダツリー
- アーカイブ一覧
- 検索条件
- ソート条件
- 表示モード
- フォルダ追加
- 再スキャン
- アーカイブの移動、名前変更、削除

#### ViewerViewModel

- 現在のArchive ID
- 現在画像
- 画像一覧
- 現在位置
- 1枚表示 / 一覧表示切替
- 選択状態
- 削除予約
- 拡大・縮小等の表示状態

### 4.4 UIルール

- ViewModelから直接 `File.*`、`Directory.*`、SQLite等を呼ばない。
- ユーザー操作はApplication層のサービスへ依頼する。
- ViewModelは処理結果 `OperationResult` を受け取り、画面状態へ反映する。
- トースト表示は共通の通知サービス経由とする。

## 5. Application層

画面から呼ばれるユースケースを実装する。

### 5.1 LibraryService

ライブラリに関する操作の窓口。

主な責務:

- 登録フォルダ追加
- フォルダツリー取得
- アーカイブ一覧検索
- 検索・ソート条件に応じた一覧取得
- アーカイブを開くための情報取得

想定インターフェース例:

```csharp
Task AddFolderAsync(string path, CancellationToken ct);
Task<IReadOnlyList<FolderNode>> GetFolderTreeAsync(CancellationToken ct);
Task<PagedResult<ArchiveSummary>> QueryArchivesAsync(
    ArchiveQuery query,
    CancellationToken ct);
```

### 5.2 ScanService

フォルダスキャンと差分更新を担当する。

主な責務:

- 初回スキャン
- 手動再スキャン
- 起動時更新チェック
- 登録フォルダ、サブフォルダ、ZIP / CBZの列挙
- Path、Size、LastWriteTimeを用いた差分判定
- 新規・変更・不在項目の反映
- `scan_runs` の開始・終了記録
- 差分があるアーカイブの解析要求

スキャン中でもライブラリの読み取り操作を可能とする。

### 5.3 ArchiveService

アーカイブ自体のファイル管理を担当する。

主な責務:

- 名前変更
- 移動
- 削除
- ZIP再構築
- 元ファイルの再確認
- ファイル操作成功後のDB更新
- 操作履歴作成

ZIP内部の具体的な読み書きはInfrastructure層へ委譲する。

### 5.4 ViewerService

アーカイブ内部の閲覧に必要な処理を担当する。

主な責務:

- ZIP内画像エントリ一覧取得
- 自然順ソート
- 画像（JPEG / PNG / GIF / WebP）の読み込み
- 最終閲覧位置の取得・保存
- 前後画像取得

### 5.5 ViewerSession

現在開いているアーカイブの未確定状態をメモリ上で保持する。

主な状態:

```text
ArchiveId
Entries
CurrentEntry
CurrentIndex
SelectedEntries
PendingDeleteEntries
ViewMode
```

`PendingDeleteEntries` はDBへ保存しない。

アーカイブ離脱時にのみ確定または破棄する。

### 5.6 ThumbnailService

サムネイル生成・取得を担当する。

主な責務:

- ライブラリ用表紙サムネイル取得
- キャッシュ有効性確認
- サムネイル生成
- `STALE` サムネイル再生成
- キャッシュファイル消失時の再生成

一覧スクロールをブロックしないよう、生成はバックグラウンドで実行する。

### 5.7 HistoryService

操作結果を `operation_history` へ記録する。

MVPでは履歴閲覧画面を持たないが、履歴記録は実装する。

開始通知は履歴へ保存せず、確定した最終結果のみ保存する。

### 5.8 NotificationService

アプリ内トースト通知の共通窓口。

```csharp
ShowInfo(message);
ShowSuccess(message);
ShowWarning(message);
ShowError(message);
```

スキャンやZIP更新など時間を要する処理は、開始時と完了時に通知する。

## 6. Domain層

純粋なデータ構造とルールを保持する。

### 6.1 主なモデル

#### LibraryFolder

- Id
- Path
- IsEnabled
- AvailabilityStatus

#### Folder

- Id
- LibraryFolderId
- ParentFolderId
- Name
- FullPath
- RelativePath
- Depth

#### Archive

- Id
- FolderId
- FileName
- Extension
- FileSize
- LastWriteTime
- ImageCount
- LastViewEntry
- LastViewIndex
- AnalysisStatus
- AvailabilityStatus

アーカイブの実パスは `Folder.FullPath + Archive.FileName` から生成する。

#### ArchiveEntry

ZIP内の1エントリを表す。

- Name
- FullName
- Size
- CompressedSize
- LastWriteTime
- IsSupportedImage

#### OperationResult

ファイル操作の結果を共通表現する。

```text
OperationType
Status
ArchiveId
Message
AffectedCount
OldPath
NewPath
ErrorCode
ExecutedAt
```

同じ結果をトースト表示と操作履歴記録に利用する。

`OperationResult` はユーザー向けの確定結果を表し、トースト通知と `operation_history` の共通データとして使用する。例外、スタックトレース、一時ファイルパス、内部処理段階等の開発・障害調査情報は `OperationResult` へ詰め込まず、アプリケーションログへ記録する。

### 6.2 時刻

Unix timeを使用する場合は64bit整数とし、C#では `long` (`Int64`) を使用する。

`int` (`Int32`) へ変換しない。

## 7. Infrastructure層

## 7.1 SQLiteRepository

SQLiteへの永続化を担当する。

Repositoryはテーブル単位に過剰分割せず、MVPでは用途別に次を基本とする。

- `LibraryRepository`
- `ArchiveRepository`
- `HistoryRepository`
- `ScanRepository`
- `ThumbnailRepository`

DB接続設定:

```text
foreign_keys = ON
journal_mode = WAL
synchronous = NORMAL
busy_timeout = 5000
```

書き込み処理はアプリ内で1本の書き込みキューへ集約する。

### 7.2 ArchiveReader

ZIP / CBZの読み取りを担当する。

MVPでは `System.IO.Compression.ZipArchive` を利用する。

主な機能:

- エントリ列挙
- 画像の拡張子の判定（JPEG / PNG / GIF / WebP）
- エントリStream取得
- アーカイブ検証

### 7.3 ArchiveWriter

ZIP再構築を担当する。

主な責務:

1. 一時ZIP作成
2. 削除対象以外のエントリをコピー
3. 一時ZIPを閉じる
4. 再オープンして読み取り確認
5. 成否をApplication層へ返す

元ZIPの退避・置換判断は `ArchiveService` が統括する。

### 7.4 FileSystemService

Windowsファイルシステム操作を集約する。

主な機能:

- ファイル・フォルダ存在確認
- ディレクトリ列挙
- ファイル情報取得
- 名前変更
- 移動
- エクスプローラーで対象表示
- 一時ファイル名生成

ViewModelやRepositoryから直接ファイル操作しない。

### 7.5 RecycleBinService

Windowsのごみ箱への移動を担当する。

用途:

- アーカイブ削除
- ZIP再構築時の更新前ZIP退避

ごみ箱を利用できない保存先の場合は `RECYCLE_BIN_UNAVAILABLE` を返し、自動的な完全削除へは切り替えない。

- アーカイブ削除：UIが確認ダイアログを表示し、ユーザーが承認した場合のみ、`ArchiveService` が完全削除を明示的に要求する。
- ZIP再構築：更新を中止し、元ZIPと削除予約を保持する。

### 7.6 ThumbnailCacheStore

サムネイルファイルの保存・取得・削除を担当する。

DBの `thumbnail_cache` はメタデータを保持し、画像実体はキャッシュディレクトリへ保存する。

## 8. 依存関係

代表的な処理の依存関係は次のとおり。

```text
LibraryViewModel
    -> LibraryService
        -> LibraryRepository
        -> ScanService

ViewerViewModel
    -> ViewerService
        -> ArchiveReader
        -> ArchiveRepository

ViewerViewModel
    -> ArchiveService
        -> ArchiveWriter
        -> FileSystemService
        -> RecycleBinService
        -> ArchiveRepository
        -> HistoryService
        -> NotificationService
```

`ArchiveWriter` からSQLiteを操作しない。

`ArchiveRepository` からファイルを操作しない。

## 9. ZIP閲覧フロー

```text
ユーザーがアーカイブを開く
        |
        v
LibraryViewModel
        |
        v
ViewerService
        |
        +--> ArchiveRepository からArchive取得
        |
        +--> Folder情報から実パス生成
        |
        +--> ArchiveReaderで画像一覧取得
        |
        v
ViewerSession生成
        |
        v
ViewerViewModelへ表示
```

画像データは全件を同時展開せず、現在画像と前後の必要数のみ読み込む。

## 10. 削除予約フロー

```text
Delete
  |
  v
ViewerViewModel
  |
  v
ViewerSession.PendingDeleteEntriesへ追加
  |
  +--> 画面から通常画像として除外
  |
  +--> 削除予定件数を更新
```

この時点ではZIP、SQLite、操作履歴を変更しない。

一覧表示で複数選択された場合も同じ `PendingDeleteEntries` を利用する。

## 11. アーカイブ更新フロー

アーカイブ離脱時に削除予約が存在し、「更新する」が選択された場合の処理。

```text
ViewerViewModel
    |
    v
ArchiveService
    |
    +--> 更新開始トースト
    |
    +--> 元ファイルの存在・Size・LastWriteTime確認
    |
    +--> ArchiveWriterで一時ZIP作成
    |
    +--> 一時ZIP検証
    |
    +--> RecycleBinServiceで元ZIP退避
    |
    +--> FileSystemServiceで一時ZIPを正規名へ変更
    |
    +--> DB書き込みトランザクション
    |      + archives更新
    |      + thumbnail_cacheをSTALE化
    |      + operation_history追加
    |
    +--> 完了トースト
    |
    +--> ThumbnailServiceへ再生成要求
    v
離脱を継続
```

### 11.1 失敗時

- 元ZIPをごみ箱へ移す前の失敗では元ZIPを保持する。
- 一時ZIPは可能なら削除する。
- 元ZIP退避後の失敗は復旧に必要なパスをエラー結果へ含める。
- DB更新前に実ファイル操作が失敗した場合、DBは更新しない。
- DB更新のみ失敗した場合、次回スキャンにより実ファイルから再同期可能とする。

## 12. スキャンフロー

```text
起動 / フォルダ追加 / 再スキャン
        |
        v
ScanService
        |
        +--> 開始トースト
        +--> scan_runs作成
        +--> FileSystemServiceで再帰列挙
        +--> LibraryRepositoryと差分比較
        +--> 新規Archive登録
        +--> 変更Archive解析
        +--> 不在判定
        +--> Folderツリー更新
        +--> scan_runs完了
        +--> operation_history記録
        +--> 完了トースト
```

起動時チェックはライブラリ画面表示後に開始し、通常の閲覧・検索をブロックしない。

## 13. 並行処理

MVPでは複雑な並列実行を避け、次のルールとする。

### 13.1 DB

- 読み取りは必要に応じて並行可能
- 書き込みは単一キューへ直列化

### 13.2 同一アーカイブ

同じArchive IDに対する破壊的操作は同時実行しない。

例:

- 再構築中の名前変更は禁止
- 移動中の削除は禁止
- 更新中の再更新は禁止

### 13.3 スキャンとの競合

MVPでは高度なロック、世代管理、競合解決機構は実装しない。

スキャン結果をSQLiteへ反映する直前に、対象ファイルの存在、Size、LastWriteTimeを再取得する。スキャン開始時または解析時に取得した値と異なる場合、そのファイルのスキャン結果は破棄し、次回の起動時更新チェックまたは再スキャンの対象とする。

アプリ内のファイル操作が成功した場合は、その操作結果によるDB更新を優先する。スキャン側は確認済みの古い情報で上書きしない。

## 14. キャンセル方針

### キャンセル可能

- フォルダスキャン
- 起動時差分チェック
- サムネイル生成待ち

### ZIP更新のキャンセル境界

次の処理まではキャンセル可能とする。

- 一時ZIP生成
- 一時ZIPの検証

元ZIPをごみ箱へ退避する処理を開始した時点を安全境界とし、それ以降はキャンセル不可とする。

安全境界を越えた後は、新ZIPへの置換、DB更新、履歴記録まで処理を最後まで完了させる。これにより、元ZIPのみがごみ箱にあり、一時ZIPだけが残る中途半端な状態を避ける。

## 15. エラー処理

Application層のサービスは、ユーザー操作で想定される失敗を例外のままUIへ投げず、原則 `OperationResult` 等へ変換する。

例:

- `FILE_NOT_FOUND`
- `ACCESS_DENIED`
- `DISK_FULL`
- `ARCHIVE_BROKEN`
- `ARCHIVE_CHANGED_EXTERNALLY`
- `RECYCLE_BIN_UNAVAILABLE`
- `TARGET_ALREADY_EXISTS`
- `DATABASE_ERROR`

予期しない例外は共通例外ハンドラで捕捉し、ログへ記録する。

## 16. ログ

操作履歴と開発・障害調査ログは分離する。

### 操作履歴

ユーザーが後日確認する対象。

- ZIP更新
- 名前変更
- 移動
- 削除
- スキャン最終結果

SQLiteの `operation_history` へ保存する。

### アプリケーションログ

障害調査用。

- 例外
- スタックトレース
- SQLiteエラー
- ZIP処理エラー
- スキャン詳細

アプリケーションログの記録はMVPから実装し、ローカルログファイルへ保存する。ログ閲覧画面はMVP対象外とし、将来仕様とする。

最低限、日時、ログレベル、処理名、Archive ID、対象パス、エラーコード、例外メッセージ、スタックトレースを記録できる構造とする。保存形式、保存期間、最大ファイルサイズおよびローテーション方式は実装設計で確定する。

## 17. DIと生成管理

各Service、Repository、Infrastructure依存はコンストラクタ注入を基本とする。

例:

```csharp
ArchiveService(
    IArchiveWriter archiveWriter,
    IFileSystemService fileSystem,
    IRecycleBinService recycleBin,
    IArchiveRepository archiveRepository,
    IHistoryService historyService)
```

ただしMVPではインターフェースを無制限に作らず、次の条件に該当する境界を優先して抽象化する。

- OSや外部資源に依存する
- 単体テストで置き換えたい
- 将来実装を差し替える可能性が高い

例:

- FileSystem
- RecycleBin
- ZIP Reader / Writer
- SQLite Repository
- Notification

## 18. ソリューション構成案

MVPではプロジェクトを細分化しすぎず、まず2プロジェクト構成を推奨する。

```text
K35Viewer.sln

K35Viewer.App
  Views/
  ViewModels/
  Services/
  Domain/
  Infrastructure/

K35Viewer.Tests
  Services/
  Infrastructure/
```

規模が大きくなった時点で、必要に応じてCore / Infrastructure等へ分割する。

フォルダ分離だけでも層の依存関係は維持する。

## 19. MVPのテスト重点箇所

特に次を自動テストまたは結合テスト対象とする。

1. ZIP内画像の自然順ソート
2. 画像エントリ抽出（JPEG / PNG / GIF / WebP）
3. 削除予約状態の追加・解除
4. 複数削除を1回のZIP再構築で反映
5. 再構築失敗時に元ZIPが残ること
6. 外部変更されたZIPを上書きしないこと
7. 名前変更後もArchive IDが維持されること
8. フォルダ移動後も配下Archiveのパスを正しく組み立てられること
9. 起動時差分チェックでNASアクセス不能を削除扱いしないこと
10. SQLiteの64bit時刻が2038年以降でも扱えること

## 20. MVP対象外
- RAR / 7z（v0.2.0 の後に、閲覧だけ対応した。38章）
- AVIF / HEIC / JPEG XL など、ほかの画像形式（WebP / GIF は、のちに対応した。40章）
- PDF
- 動画
- Susie Plug-in
- 操作履歴閲覧画面
- 設定画面
- 更新確定後のアプリ独自Undo
- 高度な重複検出
- ファイル内容による高度な同一性追跡
- 複数端末間のDB共有

## 21. レビュー結果

1. `ViewerService` と `ArchiveService` の責務境界は現案を採用する。
2. `ViewerSession` はViewModel内部ではなくApplication層の状態として保持する。
3. ZIP再構築時の元ZIP退避と新ZIP置換は `ArchiveService` が統括する。
4. DB書き込みは単一キューへ集約し、直列化する。
5. スキャンとアプリ内操作の競合は、MVPではSizeとLastWriteTimeの書き込み直前再確認による簡易対応とする。高度なロックや世代管理は実装しない。
6. サムネイル再生成はZIP更新完了後に非同期実行する。
7. アプリケーションログの記録はMVPから実装する。ログ閲覧画面は将来仕様とする。
8. 2プロジェクト構成で開始し、必要になるまでCore / Infrastructureを別プロジェクト化しない。
9. `OperationResult` はトースト通知と操作履歴の共通データとして使用する。開発・障害調査情報はアプリケーションログへ分離する。
10. ZIP更新は、一時ZIP生成および検証まではキャンセル可能とし、元ZIPのごみ箱退避開始後はキャンセル不可とする。

## 23. Ver.0.2.1で確定した実装方針（Phase 2 フォルダ追加・スキャン）

実装を通じて、次の方針を確定した。上記の各章と異なる場合は、本章を優先する。

### 23.1 DB書き込みキュー

- 書き込みは `DatabaseWriter` を必ず経由し、アプリ内で1つずつ（直列に）実行する。1回の呼び出しが1トランザクションになり、例外時はロールバックする
- 読み取りは `SqliteConnectionFactory` から各自で接続を開いて並行に行う（WALのため書き込みと衝突しない）
- Repositoryの書き込みメソッドは、呼び出し元のトランザクション内で実行する。複数テーブルにまたがる更新（管理フォルダ追加時のフォルダ統合等）を1トランザクションにまとめるため

### 23.2 LibraryServiceとScanServiceの関係

8章の依存関係図では `LibraryService` が `ScanService` を呼ぶ構成だったが、次のとおり変更する。

- `LibraryService.AddFolderAsync` は登録（と親フォルダ追加時の統合）だけを行い、スキャンは実行しない
- 登録に成功（`Added`）した場合、呼び出し側（`LibraryViewModel`）が `ScanService` を起動する。スキャンを待たずにUIを操作できる状態にするため、また登録とスキャンを個別にテストできるようにするため

### 23.3 スキャンの2段階処理

`ScanService` は次の2段階で処理する。詳細な反映規則はDB設計書 11.7を参照。

1. ファイル列挙: `FileSystemService` が書き込みなしで実行する。キャンセル可能
2. 差分反映: 書き込みキュー経由の1トランザクション。`scan_runs` の完了も同じトランザクションで行う

### 23.4 アクセスできない範囲の扱い

13.3の「書き込み直前の簡易再確認」に加え、次を原則とする（テスト重点箇所9の具体化）。

- 読み取れなかったフォルダと、その配下の既存登録は、不在判定の対象外とする
- 登録フォルダ自体にアクセスできない場合は、配下を変更せずスキャンを失敗として終了する
- 再確認（サイズ・更新日時）は、新規・変更として書き込むファイルだけを対象とする（変更のないファイルは再取得しない）

### 23.5 スキャンに含めない処理

スキャンは、ZIPの内容を読む処理（画像枚数、表紙画像の特定、サムネイル生成）を含まない。新規・変更のアーカイブは `analysis_status = PENDING` で登録し、解析とサムネイル生成はPhase 4以降で行う。

### 23.6 通知・履歴

- `NotificationService` はイベントで通知を発行する。バックグラウンドスレッドから呼ばれるため、購読側（トースト表示）でUIスレッドへ切り替える
- スキャンの最終結果は、キャンセル・失敗の場合も `operation_history` へ記録する。このときの書き込みは、呼び出し元のキャンセルトークンに従わない（キャンセル済みでも履歴を残すため）
- 履歴の `operation_type` は、スキャンの種別（`INITIAL` / `MANUAL` / `STARTUP`）に応じて `SCAN_INITIAL` / `SCAN_MANUAL` / `SCAN_STARTUP` とする

## 24. Ver.0.2.2で確定した実装方針（Phase 3 ライブラリ画面）

上記の各章と異なる場合は、本章を優先する。

### 24.1 ScanServiceの全体スキャン

- `ScanAsync(libraryFolderId, scanType)`: 管理フォルダ1件を対象とする（フォルダ追加直後の初回スキャン）
- `ScanAllAsync(scanType)`: 有効なすべての管理フォルダを、1回のスキャンとして実行する（再スキャン・起動時チェック）。対象がなければ何もせず `null` を返し、通知も履歴も出さない
- 全体スキャンでも、開始・完了のトーストと `scan_runs`・`operation_history` は1回分だけ作る。件数は全管理フォルダの合計とする（DB設計書 11.7）
- スキャンは同時に1つだけ実行する。実行中に別のスキャンが要求された場合は、先のスキャンの完了を待ってから開始する（起動時チェック中にフォルダを追加した場合等）

### 24.2 LibraryServiceの検索API

5.1の想定インターフェースに合わせ、次を提供する。

```csharp
Task<PagedResult<ArchiveSummary>> QueryArchivesAsync(ArchiveQuery query, CancellationToken ct);
Task<IReadOnlyList<FolderNode>> GetFolderTreeAsync(CancellationToken ct);
```

- `ArchiveQuery` は、フォルダ（任意）、検索語、並べ替え項目、昇順/降順、Offset / Limit（任意）、新着だけ（`NewOnly`。41章）を持つ。クエリの規則はDB設計書 11.8
- `GetFolderTreeAsync` は、登録フォルダを起点とするツリーを返す。起点はフルパス、配下はフォルダ名を持つ（画面の表示は、起点もフォルダ名だけ。32.1）。同階層は名前順（大文字小文字を区別しない）に並べる。見つからなくなったフォルダは配下ごと含めない。登録フォルダに接続できない場合は起点を残し、接続なしとして示す

### 24.3 ライブラリ画面（LibraryViewModel）

- **一覧**: 現時点では詳細表示（列表示）のみ。サムネイル表示はPhase 4で追加する
- **一覧の取得**: 現時点では取得範囲を指定せず、条件に一致する全件を取得する（1万件でも約70ms以下）。`ListView` の仮想化により、画面に見える行だけが生成される（1万件を渡しても生成される行は約30件）。ページングが必要になった場合は、`ArchiveQuery` の Offset / Limit を使う
- **一覧の差し替え**: 項目ごとの変更通知を避けるため、検索のたびに一覧を丸ごと差し替える。表示用の文字列（サイズ、日時の書式）は、画面に表示される行だけがバインド時に組み立てる
- **検索入力**: 入力後250ミリ秒待ってから取得する（デバウンス）。取得が重なった場合は前の取得をキャンセルし、最後の結果だけを反映する
- **フォルダツリー**: スキャン等でツリーを再構築しても、展開状態と選択中のフォルダを維持する。選択中のフォルダがなくなった場合は「すべて」に戻す。新しく登録されたフォルダは展開して表示する
- **起動時チェック（UC-17）**: ライブラリ画面の表示後に、管理フォルダがあれば `ScanAllAsync(Startup)` をバックグラウンドで開始する。完了を待たずに一覧を表示し、チェック中も閲覧・検索できる。完了後に一覧とツリーを読み込み直す
- **再スキャン（UC-16）**: 管理フォルダがない場合、またはスキャン中は実行できない
- **管理フォルダ追加**: 登録に成功したら、ツリーを更新したうえで、初回スキャンを待たずに開始する

### 24.4 UIのテスト

- ViewModelは、ダイアログ（`IDialogService`）を差し替えて、実DBと一時フォルダで検証する
- 一覧の仮想化は、実際のWPFウィンドウに1万件を渡し、生成された行数を数えて確認する（STAスレッドで実行）
- 実際のフォルダ選択ダイアログと、画面の見た目（配色、余白、操作感）は自動テストの対象外であり、手動で確認する

## 25. Ver.0.2.3で確定した実装方針（Phase 4 サムネイル）

上記の各章と異なる場合は、本章を優先する。

### 25.1 構成

| 部品 | 層 | 責務 |
|---|---|---|
| `IArchiveReader` / `ArchiveReader` | Infrastructure | ZIP / CBZ を開き、対応画像の数と表紙候補を返す（`Analyze`）。1エントリをメモリへ読み込む（`ReadEntry`）。破損・暗号化・存在しない等は、例外ではなく解析結果の状態で返す |
| `ThumbnailGenerator` | Infrastructure | 画像データからサムネイル（JPEG）を作る。WPF標準の画像APIだけを使い、どのスレッドからでも呼べる |
| `ThumbnailCacheStore` | Infrastructure | サムネイル画像ファイルの保存・取得・削除。保存は一時ファイル経由で置き換える |
| `ThumbnailRepository` | Infrastructure | `thumbnail_cache` の永続化 |
| `ThumbnailService` | Application | 解析とサムネイル生成の対象選定・実行・DB反映・キャッシュの修復。完了を `ArchiveProcessed` イベントで通知する |
| `ThumbnailImageLoader` | Infrastructure（画面側） | 一覧に表示する画像の遅延読み込みとメモリ上のLRUキャッシュ |
| `NaturalStringComparer` | Domain | 自然順の文字列比較（ビューアの画像順でも使う） |

`ThumbnailService` は5.6のとおりライブラリ用サムネイルを担当する。解析（画像枚数・表紙の特定）も、ZIPを1回開く処理に含めるため、同じサービスで行う。

### 25.2 ZIPを開く場面

- ZIPを開くのは、`ThumbnailService` による解析・生成と、ビューアでの閲覧だけである
- 一覧の表示・検索・並べ替え・スクロール、およびサムネイル画像の表示は、SQLiteの検索結果（サムネイルのファイルの場所と状態を含む）と、キャッシュのファイルだけで行う
- 生成済みのライブラリでは、起動時の確認でもZIPを開かない（サムネイル画像ファイルの存在を確認するだけ）。これはテストで、ZIPを開いた回数を数えて確認している

### 25.3 バックグラウンド処理

- 生成は同時に2件まで行う（CPUとディスク・NASへの負荷を抑える）。実行中に再度要求された場合は、重複して実行せず、終わったあとにもう一度確認する
- 1件の失敗（例外）で全体を止めない。アーカイブが壊れている等は異常ではなく、`BROKEN` 等の状態として記録して先へ進む
- キャンセルすると処理を中断し、処理済みの結果は残る。再開すると、残りから続ける
- 生成の開始契機は、ライブラリ画面の表示後（前回の未処理分）と、スキャンの完了後（新規・変更分）

### 25.4 画面への反映

- 1件の生成が終わるたびに `ArchiveProcessed`（Archive ID、解析状態、画像枚数、サムネイルの場所と状態）を通知する。画面は、表示中の一覧のうち該当する行だけを更新する。一覧を取得し直さないため、スクロール位置が変わらない
- **一覧の取得中に届いた通知**（Ver.0.2.11）: 一覧の取得（DBの検索）と、差し替えの間に作成が終わると、その通知は古い一覧に当たり、新しい一覧は取得した時点の状態（作成待ち）のまま残る。起動時は、更新チェックのスキャンが終わると一覧を取得し直し、同時にサムネイルの作成も動いているため、起こりうる。そこで、取得中に届いた通知を記録しておき、差し替える一覧にも当ててから差し替える。記録と差し替えは、作成スレッドからの通知と競合しないよう、ロックの中で行う（`LibraryViewModel.RefreshArchivesAsync`）。自動テストでは、取得の直後に作成を最後まで行うことで、確実に再現して確かめる
- 画像のメモリ上の保持枚数には上限を設ける（既定400枚）。1万件分を保持するとメモリを使い切るため。画面から外れた画像は破棄し、戻ってきたらキャッシュのファイルから読み直す。読み込みは新しい要求（画面に出た行）を優先する
- 再生成では同じパスの画像ファイルの中身が変わるため、通知を受けた行は、メモリ上の古い画像を破棄して読み直す
- 画像を読み込めなかったファイルは、再生成の通知があるまで再試行しない

### 25.5 サムネイル表示（一覧の表示方式）

- 画面の表示方式は「詳細」と「サムネイル」を切り替える。表示方式は記憶せず、起動のたびに詳細表示から始まる（設定画面はMVP対象外のため）。一覧の項目の選択や、アーカイブを開く操作はPhase 5以降で追加する
- サムネイル表示は、一覧を1行ぶん（横に並ぶ数枚）ずつにまとめ、その行を仮想化する。WPFの標準パネルには、折り返しながら仮想化するものがないため。1行に並べる枚数は、表示領域の幅から決める
- 詳細表示に戻したときは、行のまとまりを破棄する
- 解析できなかったアーカイブは、画像枚数の欄と、サムネイルの枠に状態を表示する（破損、暗号化（非対応）、画像なし、読み込み失敗、表紙を読めません、作成待ち）。色だけに頼らない

### 25.6 スコープ外とした項目

- 画像のEXIFの回転情報は考慮しない（コミック等の用途では影響が小さいため。必要になった場合に評価する）
- 現在表示している行を先に生成する優先制御は行わない（アーカイブID順に処理する）
- 生成の進捗は、ライブラリ画面の右下に件数で表示する（トーストは出さない）

## 26. Ver.0.2.4で確定した実装方針（Phase 5 ビューア 1枚表示）

上記の各章と異なる場合は、本章を優先する。

### 26.1 構成

| 部品 | 層 | 責務 |
|---|---|---|
| `IArchiveReader.Open` / `IOpenedArchive` | Infrastructure | 閲覧のためにアーカイブを開く。対応画像を自然順に並べ、**開いたまま**エントリを読み出す。画像がない・壊れている・暗号化されている等は、例外ではなく状態で返す |
| `ViewerService` | Application | アーカイブを開く（UC-05）。ファイルの存在確認、開けない場合の通知、前回位置の復元。閲覧位置の記録 |
| `ViewerSession` | Application | 開いているアーカイブの閲覧状態。画像の一覧、現在位置、位置の移動、画像の読み出し。閉じるとファイルを手放す |
| `PageImageLoader` | Application | 頁画像の読み込みと、前後の先読み、範囲外の破棄 |
| `ViewerImageDecoder` | Infrastructure | 画像のデコード（WPF標準API）。巨大な画像はデコード時に縮小 |
| `ViewerViewModel` | Presentation | 1枚表示、拡大率、全画面、キー操作、閲覧位置の保存 |
| `MainViewModel` | Presentation | ライブラリ画面とビューア画面の切り替え |

5.4の `ViewerService` の責務のうち、「画像の読み込み」は `PageImageLoader` と `ViewerImageDecoder` が担う。

### 26.2 アーカイブを開いたままにする

- 連続して頁をめくる間、ZIPを開き直さない。開き直すと、毎回エントリ一覧（セントラルディレクトリ）を読むため、NASでは遅延が頁ごとに加わる
- 開くときは、他のプログラムによる読み取り・書き込み・削除・名前変更を妨げない共有モードにする。閲覧中でも、エクスプローラーでの名前変更や移動ができる（開いているファイルへの読み取りは、移動後も続けられる）
- `ZipArchive` は同じストリームからの同時読み取りで壊れるため、読み取りを直列化する。先読みと現在頁の読み込みが同時に走っても安全
- ビューアを閉じる（`ViewerSession.Dispose`）とファイルを手放す。ZIP再構築（Phase 8）では、閲覧のために開いたままのファイルを、更新の前に閉じない。削除（名前変更）を許可する共有モードで開いているため、ごみ箱への移動もできる（実際のごみ箱で確認済み。29.5）
- 閲覧中にファイルが外部で書き換えられた場合の扱いは、29.4

### 26.3 前後の頁の先読みとメモリ

- 現在の頁の前1枚・後2枚だけを保持する（UC-06: 全画像を同時に展開しない）。それより遠い頁は破棄する。戻ったら読み直す
- 破棄した頁の読み込みが途中であれば中止する。先頭から末尾へ飛ぶ操作で、使わない画像の展開を続けない
- 1枚の画像の読み込みは、展開後128MBまで。デコード後の画素数が3,600万画素を超える画像は、デコード時に縮小する（この場合、ズーム倍率は縮小後の画像に対する倍率になる）
- 壊れた画像は、エラーとして保持する（何度も読み直さない）。画面にはエラーを表示し、前後への移動は続けられる
- 測定（2400×3400のJPEG、300頁、約104MB）: ZIPを開いて画像の一覧を作るのに約15ms、最初の頁の表示約110ms、先読み済みの頁送りは中央値0ms。100頁めくっても、メモリ（プライベートバイト）の増加は約28MBで、積み上がらない

### 26.4 位置の移動

- 端では止まる（最後から次へ進んでも、先頭へは戻らない）
- 操作が連続した場合は、最後に要求した頁だけを画面に反映する。途中の頁の読み込みが遅れて届いても、上書きしない
- 削除予約された画像を移動対象から除く処理は、Phase 7で追加した（28.2）

### 26.5 拡大率

- 拡大率は「画像の1画素を画面の何画素で表示するか」で表す。画面の拡大率（DPI）を考慮し、原寸（100%）は画像の1画素＝画面の1画素になる
- **フィット**: ウィンドウに収まる倍率。ただし縮小のみで、小さい画像は拡大しない（拡大してぼかさないため）
- **原寸**: 100%
- **拡大・縮小**: 10%〜800%の段階式（10, 15, 20, 25, 33, 50, 67, 75, 100, 125, 150, 200, 300, 400, 600, 800）。現在の倍率の次の段階へ移る。フィットから操作した場合は、フィット時の倍率の次の段階になる
- 拡大率の設定（フィット / 原寸 / 倍率）は、頁をめくっても保たれる。頁が変わると、左上から表示する
- 表示領域に収まらないときは、ドラッグまたはスクロールバーで移動する。マウスホイールは頁送りに使う（Ctrlを押しながらで拡大・縮小）

### 26.6 閲覧位置の保存

- 頁の移動から約0.8秒後に保存する。連続して移動している間は、最後の位置だけを保存する
- ビューアを閉じるときは、待たずに保存する。アプリの終了時にビューアを開いたままの場合も、保存する（待ち時間は最大2秒）
- 保存に失敗しても閲覧は続け、ログに記録する
- 復元の規則はDB設計書 6.3

### 26.7 画面の切り替え

- ライブラリ画面とビューア画面は、同じウィンドウ内で表示を切り替える。どちらも作り直さないため、ライブラリへ戻ったときに、スクロール位置・検索条件・選択が残る
- 「開く」操作は、ライブラリのViewModelがイベントで通知し、`MainViewModel` がビューアを開く。開けなかった場合は、理由がトーストで通知され、ライブラリ画面に留まる（UC-05 の異常フロー）
- ビューアの表示中だけ、ウィンドウがキー操作をビューアへ渡す。ライブラリ画面の検索欄などへの入力は妨げない
- 全画面は、ウィンドウの枠をなくして最大化する。解除すると、元の状態（大きさ・位置・枠）に戻る。全画面ではツールバーを隠し、現在位置と拡大率だけを表示する
- アーカイブを「開く」操作は、詳細表示では行のダブルクリックと Enter、サムネイル表示ではカードのダブルクリック
- サムネイル表示のカードの選択とキーボード操作は、Phase 9で対応した（30.4）

- 予約の状態は `ViewerSession` が1か所で持つ。1枚表示と一覧表示は同じ状態を使うため、同期のための処理は不要。DB・ZIP・操作履歴には何も書かない（5.5、10章）

- 確認は、ビューアの表示中に削除予約が1件以上あるときだけ行う。ライブラリへ戻る操作（`CloseRequested`）と、ウィンドウを閉じる操作（`Closing`）の両方で、同じ `ConfirmLeaveViewer` を使う

- 「更新する」は、Phase 7では常に選べなかった。Phase 8で有効にした（29章）。`IDialogService.ConfirmLeaveArchive` の第3引数は、`bool canUpdate` から、更新できない理由（`string?`。更新できるなら null）に変えた
- 確認は、画面の切り替えを始める前（`_isTransitioning` を立てる前）に、同期的に行う。確認ダイアログはモーダルで、その間は他の操作を受け付けない

### 28.5 スコープ外・未対応

- 「更新する」（ZIPの再構築、ごみ箱への退避、外部変更のチェック）はPhase 8で実装した（29章）
- 削除予約した画像を前後の先読みの対象から外す最適化。先読みは位置の前1・後2のままで、予約済みの画像を先読みすることがある（読み込みを無駄にするだけで、動作には影響しない）

### 29.2 更新の手順と安全境界

1. 通知: 「更新を開始しました」。同じアーカイブの更新中なら、始めずに `UPDATE_IN_PROGRESS`（通知しない）
2. **確認**（キャンセル可）: ファイルの存在、開いた時点から外部で変更されていないこと（サイズ・更新日時）、ごみ箱へ退避できること（29.3）、空き容量（ローカルドライブのみ。元のZIPの大きさ＋16MB以上）。満たさなければ、何も作らずに中止する
3. **一時ZIPの作成**（キャンセル可）: 元のZIPと同じフォルダに `〈ファイル名〉.〈GUID〉.k35tmp` を新規作成する（拡張子がzip / cbz ではないため、スキャンの対象にならない。同名があっても上書きしない）。削除対象以外を元の順序でコピーする
4. **検証**（キャンセル可）: 一時ZIPを開き直し、エントリの数・名前・サイズ・CRC32が元と一致し、すべて展開できることを確認する
5. 安全境界の直前に、元のZIPが変更されていないことをもう一度確認する
6. **安全境界**（ここからキャンセルしない）: 元のZIPをごみ箱へ移動する。失敗した場合で、元のZIPが残っていれば、一時ZIPを削除して中止する（元のZIPと削除予約を保持）
7. 一時ZIPを元の名前にする。失敗した場合は、0.2秒・0.8秒・2秒後に最大3回やり直す。それでも失敗した場合は `REPLACE_FAILED`（29.6）
8. DB更新と操作履歴を1トランザクションで行う（DB設計書 11.3）
9. 通知: 「更新しました。N枚の画像を削除しました」

安全境界より前のどの失敗・キャンセルでも、一時ZIPを削除し、元のZIPは変更されず、呼び出し側のセッションの削除予約も保持される（`ApplyDeletionsAsync` はセッションを変更しない）。安全境界を越えたあとは、`CancellationToken` を参照しない。進行状況の報告（`IProgress`）が例外を投げても、更新は止めない（画面側の不具合で、安全境界以降の処理が中断されないようにするため）。

### 29.3 ごみ箱

- ごみ箱へ退避できない保存先では、更新を中止する。完全削除への自動切替はしない（要件定義 11章、7.5）
- `SHFileOperation` は、ネットワーク上のファイルやごみ箱が無効なドライブでは、確認なしで完全削除する。そのため、呼び出す前に29.2の2.で確認する。確認する内容は開発環境設計書 14.1
- ごみ箱への移動は、ビューアが閲覧のために開いたままのファイルに対しても行える（共有モードで開いているため）。ビューアは更新の前にファイルを閉じない

### 29.4 外部変更の検出

- `ViewerService.OpenAsync` が、アーカイブを開く直前のサイズと更新日時を `ViewerSession.OpenedFileState` に記録する
- 検出するのは、変更確認ダイアログを開く前（「更新する」を選べるかの判定）、更新の確認、安全境界の直前、およびウィンドウが前面に戻ったとき（閲覧中の通知。同じセッションにつき1回）
- 変更を検出した場合は、更新しない。閲覧中の画像は、開いたままのZIPから読み出し続けるため、外部で書き換えられると、読み出しが失敗または古い内容になることがある。通知は、その可能性を伝えるもの

### 29.5 更新後の表示

- 更新に成功したら、ビューアの閲覧位置の保存を止めたまま（`SuspendPositionSaving` → `MarkArchiveUpdated`）閉じる。更新で決めた位置を、更新前の位置で上書きしないため。更新を始める時点から止めるので、更新中に遅延保存が動いても上書きしない。失敗・キャンセルでは再開する
- ライブラリ画面は `LibraryViewModel.OnArchiveChangedAsync` で一覧を読み込み直し、サムネイルの作成を始める。解析待ち（`PENDING`）になったアーカイブの解析と、サムネイルの再生成（`STALE`）が行われ、画像枚数と表紙が更新後の内容になる
- スキャンが更新後のファイルを見ても、同じArchive IDのまま、サイズ・更新日時がDBと一致しているため、変更扱いにならない

### 29.6 置き換えの失敗

元のZIPをごみ箱へ移したあとに、一時ZIPを元の名前にできなかった場合。

- 更新前のファイルはごみ箱にあり、更新後のファイルは一時ファイルに残っている。ユーザーへ、その場所を通知する（トースト）
- 操作履歴に `IMAGE_DELETE`（`FAILED`、`error_code = REPLACE_FAILED`）を記録する。`old_path` は元のパス、`new_path` は一時ファイルのパス
- ビューアは閉じる（開いているファイルの内容が、もう現在のファイルではないため）。呼び出し側は、結果の `OriginalPreserved` が false であることでこれを判断する

### 29.7 再構築の詳細

- 圧縮: `Optimal` を基本に、元のZIPでほとんど圧縮されていないエントリ（圧縮後が元の95%以上）はそのまま保存する（開発環境設計書 13.3）
- 維持するもの: エントリ名（UTF-8）、順序、フォルダのエントリ、画像以外のエントリ、更新日時、外部属性、エントリのコメント。維持しないもの: ZIP全体のコメント、特殊な追加フィールド
- エントリ名を正しく読めないアーカイブ（UTF-8 でも Shift_JIS でもない。名前に U+FFFD を含む）は、名前を壊さないよう、更新を中止する（`UNSUPPORTED_ENTRY_NAME`）。Shift_JIS の名前は、Phase 10 で読めるようにした（31.3）
- 削除対象が元のZIPにない（アーカイブが閲覧中の内容と違う）場合は、`ENTRY_NOT_FOUND` で中止する
- エラーコード: `ARCHIVE_CHANGED`、`FILE_NOT_FOUND`、`RECYCLE_BIN_UNAVAILABLE`、`RECYCLE_FAILED`、`DISK_FULL`、`ACCESS_DENIED`、`ARCHIVE_BROKEN`、`IO_ERROR`、`ENTRY_NOT_FOUND`、`UNSUPPORTED_ENTRY_NAME`、`VERIFY_FAILED`、`REPLACE_FAILED`、`UPDATE_IN_PROGRESS`、`NOTHING_TO_DELETE`、`UPDATE_FAILED`（想定外）、`CANCELLED`

### 29.8 スコープ外・未対応

- CP932のエントリ名のアーカイブ（Phase 10 で対応。31.3）
- 更新中に異常終了した場合に残る一時ファイル（`〜.k35tmp`）の後始末（Phase 10 で対応。31.2）
- 進行状況の割合表示（段階の表示のみ）
- ネットワークドライブ・NAS上のアーカイブの更新（ごみ箱へ退避できないため、行わない）

### 30.2 操作の共通規則

- 実ファイルの操作が成功してから、DBの更新と操作履歴の記録を1トランザクションで行う（6.2、DB設計書 11章）
- 結果は `OperationResult` で返し、トーストで通知する。**操作の前の検証で断った場合**（同名がある、使えない名前、移動先が管理フォルダの外など）は、ファイルに何もしていないため、通知だけを行い、履歴には記録しない。**ファイルの操作に失敗した場合**は、通知と履歴（`FAILED`）の両方に反映する（ユースケース定義書 6.2）
- 対象のアーカイブが登録されていない、または不在（`MISSING`）の場合は、何もせず再スキャンを促す
- 操作の実行中は `LibraryViewModel.IsOperating` が true になり、重ねて操作できない。成功した場合は一覧とツリーを読み込み直し、サムネイルの作成を始める（移動先で再解析が必要になった場合のため）
- ビューアの表示中はライブラリ画面を操作できないため、ビューアで開いているアーカイブを名前変更・移動・削除することはない（UC-18 の「ビューアで開いているアーカイブが対象の場合」も、この構造で満たす）

### 30.3 各操作

- **名前変更**: 検証（30.5）→ 同名の確認（大文字小文字だけの変更は除く）→ ファイルの名前変更 → DB更新・履歴。DB更新に失敗した場合は、ファイル名を元に戻す
- **移動**: 移動先の確認（アクセスできる、管理フォルダの中、元と同じフォルダではない、同名のファイルがない）→ 移動 → 移動先のフォルダの登録（未登録なら途中のフォルダも）→ DB更新・履歴。異なるボリューム間はコピー → 大きさの確認 → 元の削除の順で、元を削除できなければ一部成功（`PARTIAL`）とする。移動先を管理フォルダの中に限るのは、外へ移すとライブラリから見えなくなり、Archive IDを維持する意味がなくなるため
- **削除**: 通常はごみ箱へ移動する。ごみ箱を使えない保存先では、画面が元に戻せないことを示して確認し、承認された場合だけ `permanent: true` で完全に削除する（自動の切替はしない）。ファイルを削除できてから、DBの登録とサムネイルの管理行を削除し、サムネイル画像のファイルを削除する
- **エクスプローラーで表示**: ファイルの存在を確認してから起動する。パスは常に引用符で囲む（Windowsのファイル名には引用符を含められない）
- **管理フォルダの解除**: 確認（件数つき）→ 1トランザクションで、サムネイルのパスの取得・登録の削除（CASCADE）・履歴の記録 → サムネイル画像のファイルの削除。スキャン中は実行できない（コマンドを無効にする）

### 30.4 選択とキー操作

- 選択は1件。詳細表示は一覧（`ListView`）の選択と双方向にバインドし、サムネイル表示はカードのクリックで選ぶ
- 一覧を取得し直したときは、選択していたアーカイブが一覧にあれば選択を保つ。操作の後は、操作したアーカイブ、それが一覧にない場合は操作前の次の（なければ前の）項目を選ぶ
- キー操作は `LibraryViewModel.HandleKey` に集約する。Enter・F2・Delete は両方の表示で使える。サムネイル表示では矢印・PageUp/PageDown・Home/End で選択を動かし、その行へスクロールさせる（`ScrollToRowRequested`）。詳細表示の矢印キーは、一覧の標準の動作に任せる
- 右クリックしたアーカイブ・ツリーの項目は、メニューを開く前に選択する。詳細表示の行（`ListViewItem`）とツリーの項目は右クリックを処理済みにするため、処理済みのイベントも受け取るハンドラーで選択する。ツリーは、入れ子の項目でも、右クリックした位置に最も近い項目を選ぶ

### 30.5 ファイル名の検証

- 前後の空白を除く。拡張子が .zip / .cbz でなければ、元の拡張子を付ける（「v1.2」のように「.」を含む名前でも、拡張子として扱わない）
- 断る名前: 空、`Path.GetInvalidFileNameChars()` の文字を含む、末尾が「.」、拡張子を除いた部分が空、予約名（CON、PRN、AUX、NUL、COM1〜9、LPT1〜9。「NUL.zip」も含む）、256文字以上
- 同名の確認は、検証に通った名前で、同じフォルダの既存のファイルと比べる（大文字小文字を区別しない）。名前変更のダイアログは、入力のたびにこの検証を行い、理由を表示する

### 30.6 スキャンとの競合

- スキャンは列挙（DBへ書き込まない）とDBへの反映を分けて行うため、その間にアプリ内で名前変更・移動すると、列挙結果は古い場所を指す。反映の際に、不在にする前に、DBの記録どおりの場所にファイルがあるかを確認し、あれば不在にしない（13.3、DB設計書 11.7）
- 古い場所のファイルは既にないため、新規の登録にもならない（反映の直前の再確認で除かれ、失敗として数える）

### 30.7 スコープ外・未対応

- 複数のアーカイブの同時選択と一括操作
- 操作履歴の画面（SCR-04。MVP対象外）
- ドラッグ＆ドロップでの移動
- 管理フォルダの外への移動
- 名前変更・移動の取り消し（Undo）

## 31. Ver.0.2.9で確定した実装方針（Phase 10 安定化）

上記の各章と異なる場合は、本章を優先する。

### 31.1 想定外の例外

`UnhandledExceptionReporter`（Infrastructure）が、どこでも処理されなかった例外をログへ記録する。起動時に `App` が登録する。

| 発生場所 | 扱い |
|---|---|
| 画面のスレッド（`Dispatcher.UnhandledException`） | Error で記録し、処理済みにしてアプリは続ける。利用者には「予期しないエラーが発生しました。操作は続けられますが、直前の操作が完了していない可能性があります」とログの場所を知らせる。続けて起きた場合、知らせるのは5秒に1回まで |
| 待たれなかったタスク（`TaskScheduler.UnobservedTaskException`） | Error で記録し、観測済みにする（アプリは続ける。利用者には知らせない） |
| それ以外のスレッド（`AppDomain.UnhandledException`） | Critical で記録する。.NETの既定どおり、アプリは終了する |

- 利用者に見せる文には、例外の内容やスタックトレースを含めない（ログだけに残す。15章）
- ログの出力は、1件ごとにファイルへ書き込まれる（Serilog のファイル出力の既定。バッファしない）ため、異常終了の直前の記録も残る

### 31.2 異常終了で残った一時ファイル（ユースケース定義書 6.2）

| 一時ファイル | 片付ける処理 | 規則 |
|---|---|---|
| 管理フォルダの中の `〈元の名前〉.〈GUID〉.k35tmp`（ZIP再構築、ボリュームをまたぐ移動） | スキャン（起動時の更新チェック、再スキャン、初回スキャン） | 同じフォルダに元のファイルがあれば、途中で止まった処理の作りかけなので削除する。元のファイルがなければ、置き換えの途中で止まった更新後のファイルや、移動の途中のファイルの可能性があるため、削除せずに残し、場所を通知する（「内容を確認し、不要なら削除してください」） |
| サムネイルのキャッシュの `〜.tmp` | 起動時の後始末（`StartupMaintenance`） | 削除する |
| アプリの一時フォルダ（`%LOCALAPPDATA%\K35Viewer\temp`）のファイル | 起動時の後始末 | 削除する |

- どれも、最後の書き込みから10分以内のものには触れない（実行中の処理が使っている可能性があるため）。使用中で削除できないものは、次の機会に回す
- 形式が違うファイル（GUIDの部分がない等）は、アプリが作ったものではないため触れない
- 一時ファイルは拡張子が zip / cbz ではないため、アーカイブとして登録されることはない
- 起動時の後始末は、画面の表示を待たせないよう、表示のあとに背景で行う。失敗しても起動は妨げない

### 31.3 Shift_JIS のエントリ名

- ZIPを読み取りで開くときは、必ず `ArchiveReader.OpenRead`（または同じ `ZipEntryNameEncoding` の指定）を使う。解析・閲覧・再構築・検証で開き方が違うと、同じエントリの名前が変わり、閲覧位置の記録や削除対象と一致しなくなるため
- UTF-8 のフラグがあるエントリは、.NETが常に UTF-8 で読む。フラグがないエントリだけ、名前のバイト列を厳密な UTF-8 として読み、不正なら Shift_JIS（CP932）として読む。どちらでも読めなければ、読めない部分を U+FFFD にする
- 再構築で作るZIPは、.NETの既定どおり、ASCII以外の名前を UTF-8 とフラグで保存する。Shift_JIS のアーカイブを更新すると、更新後は UTF-8 の名前のアーカイブになる（名前の文字列は同じ）
- 既知の限界: 半角カナだけからなる短い名前などは、まれに UTF-8 としても正しいバイト列になり、UTF-8 として読まれる（Shift_JIS の正しい名前にならない）。また、この変更の前に Shift_JIS のアーカイブで記録した閲覧位置（U+FFFD を含む名前）は一致しなくなり、次に開いたときは先頭から開く

### 31.4 二重起動の防止

- 起動時に名前つきのミューテックス（`Local\K35Viewer.SingleInstance`。ユーザーのセッションごと）を取得する。取得できなければ、すでに動いている方のウィンドウを（最小化されていれば元に戻して）前面に出し、終了する（終了コード 0）
- 二重に起動すると、同じDBに対してスキャン・サムネイルの作成が同時に動き、ログファイル（排他で開いている）も2つ目からは書けなくなるため

### 31.5 異常系の確認

| 異常 | 動作 | 確認 |
|---|---|---|
| 壊れたZIP | 解析で `BROKEN` とし、一覧に「破損」と表示。開こうとすると理由を通知してライブラリに留まる。再構築は `ARCHIVE_BROKEN` で中止 | 自動テスト（Phase 4・5・8） |
| 管理フォルダに接続できない（NAS切断） | 配下を不在にせず、管理フォルダを `UNAVAILABLE`（ツリーに「接続なし」）にする。接続が戻ると元どおり | 自動テスト（フォルダを見えなくして再現） |
| 閲覧中の切断 | 読めない頁はエラーとして表示し、閲覧は続けられる。接続が戻れば、次の頁は読める | 自動テスト（読み出しで IOException を返すアーカイブで再現） |
| ディスク容量不足 | ZIP再構築は、一時ZIPを作る前に空き容量（元の大きさ＋16MB）を確認して中止する。作成中に不足した場合も、書きかけを削除して元のZIPを保持する | 自動テスト（空き容量の取得と、容量不足の HRESULT を差し替えて再現） |
| 想定外の例外 | 31.1 | 自動テスト（画面のスレッドで例外を起こし、記録・通知・継続を確認） |

- 実際のNASでの切断、実際のディスクの容量不足は、環境がないため確認していない（上記はいずれも再現による確認）

### 31.6 スコープ外・未対応

- サムネイルの保存やDBの書き込みでのディスク容量不足の個別の通知（例外として記録され、該当の処理だけが失敗する）
- 単一ファイル化・トリミング・ReadyToRun・インストーラー（開発環境設計書 17章）

## 32. Ver.0.2.10で確定した実装方針（画面の見た目の確認）

全フェーズの完了後に行った画面の見た目の確認（画面一覧 Ver.0.2.6 の12章ほか）で、次のとおり確定した。上記の各章と異なる場合は、本章を優先する。

### 32.1 フォルダツリーの表示

- `GetFolderTreeAsync` が返す `FolderNode` は変えない（起点はフルパス、配下はフォルダ名）。表示の組み立ては Presentation 層の `FolderTreeItem` で行う
- `FolderTreeItem.Header` は、起点もフォルダ名だけ（`PathNormalizer.GetDisplayName`。フォルダ名がないドライブ直下などは、パス全体）。接続できない起点は「(接続なし)」を付ける
- `FolderTreeItem.FullPath` にフルパスを持ち、ツールチップに表示する。管理対象から外す操作は、これまでどおり管理フォルダのIDで行い、確認のダイアログ（DLG-03）にはフルパスを表示する（同じ名前の管理フォルダがあっても区別できるため）

### 32.2 詳細表示の保存場所

- `ArchiveSummary` に、そのアーカイブの管理フォルダのパス（`LibraryRootPath`。任意）を加えた。一覧の検索で `library_folders` を結合して取得する（列を増やすだけで、検索の条件・並べ替え・インデックスは変えない）
- 表示用の文字列は `ArchiveListItem.LocationText` で組み立てる（管理フォルダの名前＋そこからの相対パス）。相対パスにできない場合（管理フォルダの外。通常は起きない）は、フルパスのまま表示する
- `ArchiveListItem.Location`（フルパス）は変えない。エクスプローラーで表示・移動などの操作と、ツールチップは、これを使う

### 32.3 サムネイルの並べ方

- 25.5の「1行ぶんずつにまとめて仮想化する」構成は変えない。1行の中の並べ方だけを変えた
- 1行は、列の数を `ColumnCount` に固定した横1行のグリッド（`UniformGrid`）に並べる。カードの大きさは固定のまま、余った幅が列の間に均等に配られる。最後の行は、カードの位置を上の行とそろえる（左から詰める）
- 列の数は、一覧の使える幅（一覧の枠・内側の余白・縦スクロールバーの幅を除いた幅）に入るカードの数とする。ビューアの一覧表示（27章）も同じ規則で、使える幅の計算は `LibraryView.UsableWidth` を共用する
- 列の数は、一覧の大きさが変わったときに加えて、**一覧が表示されたとき**と**ViewModelがつながったとき**にも計算し直す。起動直後は、ViewModelがつながる前に一覧の大きさが決まり、その後は表示方式を切り替えても大きさが変わらないため、大きさの変化だけを見ていると、列の数が既定値のまま残る（画面の確認で見つかった不具合）

### 32.4 確認とお知らせのダイアログ

- `WpfDialogService` の確認（削除・完全削除・管理フォルダの解除・統合）と、`App` のお知らせ（想定外の例外の通知、DBの初期化の失敗）は、`MessageBox` をやめ、テーマに合わせた `ConfirmDialog` で表示する。`IDialogService` の形は変えない
- `ConfirmDialog.Ask` は、操作の名前のボタンとキャンセルのボタンを出し、操作のボタンが押されたときだけ true を返す。既定のボタン（Enter）とEscはキャンセル。`ConfirmDialog.Inform` は「OK」だけ
- DBの初期化に失敗したときは、メインウィンドウを作る前にお知らせを出す。お知らせのウィンドウを閉じた時点でアプリが終わらないよう、先に `ShutdownMode` を `OnExplicitShutdown` にしてから表示し、閉じたあとに終了コード 1 で終了する

### 32.5 テスト

- 画面の並べ方は、実際のWPFウィンドウで確かめる（`LibraryViewLayoutTests`）。サムネイル表示は、幅を変えて（1000 / 1280 / 1500）、カードが一覧の中に収まること、カードの間が均等で狭すぎないこと、もう1列入る余りが残っていないことを確かめる。起動直後と同じ順序（ウィンドウの大きさが決まってからViewModelをつなぎ、そのあと表示方式を切り替える）で行う
- 詳細表示は、横スクロールが出ないこと、行の高さ、保存場所の表示を確かめる。確認のダイアログは、既定のボタンとEscがキャンセルであることを確かめる
- XAMLを読み込むテストは、並列に動かさない（開発環境設計書 15.3）

## 33. v0.2.0 Phase 11 で確定した実装方針（設定画面・外観・表示方式の記憶）

### 33.1 構成

| 部品 | 層 | 責務 |
|---|---|---|
| `AppSettings` | Infrastructure（Settings） | 設定の値（外観、2つの確認、ライブラリ・ビューアの表示方式）。不変の record。既定値は、プロパティの初期値 |
| `SettingsStore` | Infrastructure（Settings） | 設定のファイル（`settings.json`）の読み書き。書き込みは一時ファイル（`.tmp`）に書いてから置き換える |
| `SettingsService` | Application | 起動時に読み、変更のたびに保存して `Changed` で知らせる（その場で反映）。画面のスレッドから使う |
| `ThemeManager` | Presentation | 外観を `Application.ThemeMode`（Fluent テーマ）に当てる。開いているすべてのウィンドウが、その場で切り替わる |
| `SettingsViewModel` / `SettingsWindow` | Presentation | 設定画面。開くたびに作る（DI の Transient。`IDialogService.ShowSettings` が `Func<SettingsViewModel>` で作る） |
| `AppInfo` | Infrastructure | アプリの版（`AssemblyInformationalVersion` の「+」より前）と、リポジトリ・ライセンス・リリースのページの URL |

### 33.2 設定のファイル

- JSON。選択肢（外観、表示方式）は名前で保存する（例: `"Theme": "Light"`）。読んで意味がわかり、選択肢の並びを変えても壊れない
- ファイルにない項目は既定値になる（古い版で作ったファイルを読んでも、新しく増えた項目は既定値で動く）
- 読めない場合（JSON として不正、知らない選択肢の名前、`null`）は壊れたとみなし、既定値で起動する。壊れたファイルは `settings.json.broken` として残し（原因を調べられるように）、起動後に「設定のファイルを読めなかったため、初期の設定で起動しました」と通知する
- 保存に失敗しても（書き込めないなど）、変更はアプリの実行中は有効にする。ログに記録し、次の変更でもう一度保存する
- 読み込みに失敗しても、DB（ライブラリの情報）は使えるため、起動は止めない

### 33.3 外観

- 起動時は、画面を表示する前に、設定の外観を当てる（`App.xaml` の `ThemeMode="Dark"` は、設定を読む前の既定）。設定画面で変えると、`SettingsService.Changed` を受けて、その場で当て直す
- 画面の色はテーマの色を参照しているため（開発環境設計書 5.3）、外観を変えても画面の作りは変えない。ビューアのツールバーは、それまで暗い色に固定していたため、テーマの色（`SolidBackgroundFillColorTertiaryBrush`、文字は `TextFillColorPrimaryBrush`）に変えた。画像の領域（1枚表示・一覧表示の背景、カード）は、配色によらず暗いまま
- 独自のスタイルは、テーマのスタイルを引き継ぐ（`BasedOn`）。引き継がないと、古い見た目（白い入力欄など）に戻る（設定画面の、保存場所の欄で起きた）

### 33.4 表示方式の記憶

- ライブラリ: `LibraryViewModel.InitializeAsync` で、記憶した表示方式にする（このときは保存しない）。以降、切り替えるたびに保存する
- ビューア: アーカイブを開いたときに、記憶した表示方式で始める。一覧表示で始める場合は、画像本体を読み込まない（一覧表示の規則どおり。27章）。保存するのは、切り替えの操作（G、ツールバーのボタン）のときだけ。一覧でダブルクリックして1枚表示にするのは「その画像を見る」操作のため、記憶しない
- `SettingsService` は、両方の ViewModel の省略可能な引数（既定は null）にした。null なら記憶しない（それまでのテストは、そのまま動く）

### 33.5 設定画面からの、フォルダ・ページを開く

- `IExplorerLauncher` に、フォルダを開く（`OpenFolder`。なければ作ってから開く）と、Web のページを開く（`OpenWebPage`）を加えた
- ブラウザに渡すのは、アプリが組み立てた `https://github.com/` のページだけにする（ほかの URL は例外。任意の文字列を既定のプログラムで実行させないため）
- 開けなかった場合は、ログに記録して「開けませんでした」と通知する

### 33.6 テスト

- 設定のファイル: ファイルがない、保存と読み込み、項目が足りない、壊れている（3種類）、変更の通知と保存、起動時の壊れたファイル
- 設定画面: 外観の選択と保存（ラジオボタンの、外れたときの false を無視する）、フォルダ・ページを開く、開けなかったときの通知、ブラウザで開ける URL の制限、画面の表示（選んでいる外観が選ばれている、「閉じる」が Esc）
- 表示方式の記憶: ライブラリ・ビューアとも、切り替えて保存し、作り直して（再起動に相当）同じ表示方式で始まることを確かめる
- 外観: XAML が参照する色が、ダークとライトの両方のテーマにあること、ライトでは背景が明るく文字が暗いこと
- 実際の画面: サンプル（開発環境設計書 15.5）を、ダークとライトで撮影して確かめた（撮影の道具は、設定のファイルで外観を指定する）

## 34. v0.2.0 Phase 12 で確定した実装方針（確認のオン/オフ・サムネイルのキャッシュの削除）

要件定義 24.3・24.5、画面一覧 8.3。上記の各章と異なる場合は、本章を優先する。

### 34.1 確認のオン/オフ

- 設定は `AppSettings.ConfirmBeforeLeave`（離れるとき）と `ConfirmBeforeDelete`（削除するとき）。どちらも既定は true。設定画面のチェックボックスから、`SettingsService.Update` で、その場で保存する
- **離れるとき**（`MainViewModel.DecideLeave`）: オフで、削除予約があり、更新できる（`GetUpdateBlockReason` が null）場合は、ダイアログを出さずに `Update` を返す。ビューアを閉じる場合と、アプリを終了する場合の、どちらも同じ経路を通る。更新できない場合（外部変更、ごみ箱を使えない保存先など）は、オフでも DLG-01 を表示する（「更新する」は選べない）
- **失敗した更新を、確認なしで繰り返さない**: アプリの終了では、更新が失敗すると、ウィンドウを閉じる要求が再び `DecideLeave` を呼ぶ。オフのままだと、失敗する更新を確認なしで繰り返してしまう。そのため、更新が失敗・キャンセルされたあとの1回は、オフでも DLG-01 を表示する（`MainViewModel` の `_confirmNextLeave`。更新を終えるたびに、成功なら false、失敗なら true にする。ダイアログを出したら false に戻す）
- **削除するとき**（`LibraryViewModel.DeleteSelectedAsync`）: ごみ箱へ移せる場合だけ、設定がオフなら DLG-02 を省く。ごみ箱を使えない保存先の完全削除の確認は、設定によらず必ず出す（元に戻せないため）
- `SettingsService` は、`MainViewModel` の省略可能な引数（既定は null）にした。null なら、常に確認する（それまでのテストは、そのまま動く）

### 34.2 サムネイルのキャッシュの削除

| 部品 | 層 | 責務 |
|---|---|---|
| `ThumbnailCacheStore.GetTotalBytes` / `Clear` | Infrastructure | キャッシュの大きさを数える。サムネイルのファイルを削除する |
| `ThumbnailRepository.DeleteAllAsync` | Infrastructure | `thumbnail_cache` の記録をすべて削除する |
| `ThumbnailService.GetCacheSizeAsync` / `ClearCacheAsync` | Application | 大きさを返す。記録とファイルを削除する。作成中は実行せず false を返す |
| `IThumbnailCacheMaintenance` | Application | 設定画面から見た、キャッシュの管理の窓口（削除できない理由、大きさ、削除）。状態の変化は `INotifyPropertyChanged` で知らせる |
| `LibraryViewModel` | Presentation | `IThumbnailCacheMaintenance` を実装する。削除したあと、一覧を読み込み直し、作り直しを始める |

- **削除するもの**: キャッシュのフォルダの直下のサブフォルダにある `archive-*` のファイル（サムネイル本体と、書き込み途中の一時ファイル）だけ。同じフォルダにあるほかのファイルには触れない。削除できないファイルがあっても、残りの削除を続ける。空になったサブフォルダは消す
- **順序**: 記録（DB）を先に消し、そのあとにファイルを消す。途中で失敗しても、記録のないファイルが残るだけで、画面には出ない（作り直すときに上書きされる）
- **作り直し**: 記録を消すと、`GetPendingProcessingIdsAsync` の対象（記録のない、解析済みのアーカイブ）になる。削除のあと `LibraryViewModel` が一覧を読み込み直し（作成待ちの表示に戻る）、`StartThumbnailProcessing` で順に作り直す。失敗（FAILED）の記録も消えるため、作り直しの1回で再試行される
- **同時に実行しない**: `ThumbnailService.ClearCacheAsync` は、作成と同じ実行中の印（`_running`）を使う。削除の途中で作成が始まらず、作成中は削除できない。さらに `LibraryViewModel.ClearBlockedReason` が、スキャン中・作成中・他の操作の実行中は理由を返し、削除させない（要件定義 24.5）
- **設定画面**: 開いたとき（`InitializeAsync`）に大きさを調べ、`ClearBlockedReason` の変化を購読する。削除できない間は、ボタンを無効にし、ツールチップで理由を示す（`ShowOnDisabled`）。スキャンや作成が終わったら、ボタンを有効にし、大きさを調べ直す。閉じたとき（`Closed`）に、購読をやめる（ライブラリの ViewModel は、アプリの間ずっと生きているため）
- 確認のダイアログは出さない。削除したあと、「サムネイルのキャッシュを削除しました。サムネイルを順に作り直します」と通知する（画面一覧 8.3）

### 34.3 テスト

- キャッシュの保存場所: 大きさ、削除（サムネイルだけを消し、ほかのファイルとフォルダは残す）、フォルダがない場合
- `ThumbnailService`: 作成 → 削除（記録もファイルも消え、アーカイブの登録は残る）→ 作り直し
- `LibraryViewModel`: 削除すると作成待ちに戻り、作り直されて、READY に戻る
- 設定画面: 大きさの表示、削除と通知、削除できない間の無効とツールチップ、終わったあとの再計算、削除できない状態になっていた場合の警告
- 確認: 設定の保存、削除の確認がオフ（確認なしでごみ箱へ。完全削除は確認する）、離れるときの確認がオフ（確認なしで更新して離れる、削除予約がなければ何もしない、更新できない場合は確認する、更新をキャンセルしたあとは確認する）

## 35. v0.2.0 Phase 13 で確定した実装方針（バックアップと復元）

要件定義 24.5、画面一覧 8.3。上記の各章と異なる場合は、本章を優先する。Phase 13 は、バックアップの作成（35.1〜35.2）と、復元（35.3〜35.4）に分けて実装した。

### 35.1 バックアップの作成

| 部品 | 層 | 責務 |
|---|---|---|
| `BackupService` | Application | バックアップの作成、一覧、古い自動バックアップの整理 |
| `AppPaths.BackupsDirectory` | Infrastructure | 保存先（`<データの保存先>\backups`）。最初のバックアップを作るときに作る |
| `AppSettings.AutoBackupKeepCount` | Infrastructure（Settings） | 自動バックアップを残す数（既定5、範囲1〜20） |

- **ファイルの形**: ZIP 1つ。`K35Viewer-backup-〈yyyyMMdd-HHmmss〉.zip`（手動）、`K35Viewer-auto-〈yyyyMMdd-HHmmss〉.zip`（自動）。同じ秒に続けて作った場合は、`-2`、`-3` と番号を足す（上書きしない）。時刻は、ローカル時刻
- **中身**: `library.db`（DB の整合のとれたコピー）、`settings.json`（あれば）、`manifest.json`（`FormatVersion`、`AppVersion`、`SchemaVersion`、`CreatedAt`、`Kind`）。サムネイルのキャッシュとログは含めない
- **DB の写し方**: SQLite のバックアップ機能（`SqliteConnection.BackupDatabase`）で、別のファイルへ写す。スキャンなどでDBを使っている最中でも、整合のとれたコピーになる（ファイルのコピーでは、WAL の途中を写してしまう）。写したあとは `journal_mode = DELETE` にして、`-wal` / `-shm` のファイルを残さない。写し先の接続は、プールを使わない（閉じたときにファイルを手放し、作業フォルダを消せるようにする）
- **作り方**: 作業フォルダ（`temp\backup-〈GUID〉`）に3つのファイルを置き、ZIP を `.tmp` として作ってから、名前を変える。途中で失敗しても、不完全なバックアップのファイルは残らない。作業フォルダは、成功・失敗に関わらず消す
- **整理**（`PruneAutoBackups`）: 自動バックアップ（名前の `auto`）を、新しいものから残す数だけ残して、ほかを削除する。手動のバックアップは、数に関わらず削除しない。呼び出し側が指定したファイル（復元元）も削除しない。残す数が範囲の外なら、範囲に収める。自動バックアップを作ったあと、設定の数を変えたときに、整理する
- **一覧**（`List`）: 名前が上の形式に合うファイルだけを、新しいものが先で返す。ほかの名前のファイル（利用者が置いたメモなど）は、無視する

### 35.2 設定画面

- 「バックアップ」の行: 最後のバックアップ（日時と、手動 / 自動）、「バックアップを作成」、「フォルダを開く」。作っている間は、作成のボタンを押せない。失敗は、ログに記録して通知する
- 「自動バックアップ」の行: 残す数を、1〜20から選ぶ（`ComboBox`）。選ぶと、その場で保存し、整理する

### 35.3 復元

| 部品 | 層 | 責務 |
|---|---|---|
| `RestoreService` | Application | バックアップの確認（`CheckAsync`）と、復元の準備（`PrepareAsync`） |
| `PendingRestore` | Infrastructure（Backup） | 入れ替えの予定の目印の書き込み（`WriteMarker`）と、起動の最初の入れ替え（`TryApply`） |
| `IBackupDialogs` / `WpfBackupDialogs` | Presentation | バックアップのファイルの選択と、復元の確認 |
| `IAppRestarter` / `WpfAppRestarter` | Presentation | 新しいプロセスを起動して、このアプリを終了する |
| `RestartArguments` | Infrastructure | 再起動の引数（`--wait-for-exit <プロセス番号>`）と、古いプロセスの終了を待つ処理 |

動いているアプリは、DB のファイルを使っているため、その場では入れ替えられない。そこで、**準備**（動いている間）と**入れ替え**（再起動後の、起動の最初）に分ける。

**準備**（`RestoreService.PrepareAsync`。設定画面の「復元…」から）

1. ZIP を確かめる（`CheckAsync`）。ZIP として開けない、`library.db` か `manifest.json` がない、`manifest.json` の `FormatVersion` か `SchemaVersion` が、今のアプリより新しい、のどれかなら、理由を返す（画面には、確認の前に通知する）
2. 利用者に確認する（「〈日時〉の状態に戻しますか？」。既定はキャンセル）
3. `library.db` と `settings.json` だけを、決まった場所（`restore-staging`）へ展開する。ZIP の中の名前で、ほかの場所へ書かれることはない（決まった名前のエントリだけを、決まった場所へ書く）
4. 展開した DB を確かめる（`PRAGMA quick_check`、スキーマの版）。壊れている、読めない、今のアプリより新しい版、ライブラリの情報がない、のどれかなら、`RestoreRejectedException` で断る。この時点まででは、今のデータには何も触れず、自動バックアップも作らない
5. 今のデータを、自動でバックアップする。復元元は、整理の対象から外す（35.1。残す数が1でも消えない）
6. 入れ替えの予定の目印（`restore-pending.json`）を、最後に書く（途中で失敗した場合は、展開したファイルを消す。目印は、まだない）
7. 新しいプロセスを起動し（`--wait-for-exit <このプロセスの番号>`）、このアプリを終了する。起動できなかった場合は、終了せずに、「アプリを終了して、起動し直すと、復元されます」と知らせる（予定は残る）

**入れ替え**（`PendingRestore.TryApply`。`App.OnStartup` で、DB を開く前に実行）

- 新しいプロセスは、単一起動の仕組み（ミューテックス）を取る前に、古いプロセスの終了を待つ（最長30秒。`RestartArguments.WaitForPreviousProcess`）。待たないと、二重の起動として止められる
- 今の `library.db`、`-wal`、`-shm`、`settings.json` を `restore-rollback` へ退避し、展開したファイルを所定の場所へ置く。バックアップに `settings.json` がなければ、設定のファイルはなくなる（初期の設定に戻る）
- **途中で失敗した場合**（ファイルを動かせないなど）は、置いたファイルを消し、退避したファイルを元の場所へ戻す。そのうえで、予定の目印と作業用のフォルダを片付ける。復元はせず、「元のデータで起動しました」と通知する
- 元に戻すことにも失敗した場合は、退避したファイルを消さずに残す。次の起動で、`restore-rollback` が残っていることから、途中で止まったとみなして、退避したファイルを元の場所へ戻す（「前回の復元が途中で止まったため、元のデータに戻しました」）
- **成功した場合**: サムネイルのキャッシュのファイルを消し、復元した DB の `thumbnail_cache` の記録も消す（失敗しても、復元は成功とする。ファイルがなければ、サムネイルの作成が作成待ちに戻して作り直す）。作業用のフォルダと予定の目印を片付ける。画面を出してから、「〈日時〉のバックアップから復元しました。サムネイルを作り直します」と通知する
- 予定の目印が壊れていて読めない場合は、復元せずに片付ける

### 35.4 テスト

- 入れ替え: 復元すると DB と設定が戻る（サムネイルのキャッシュは消え、作業用のファイルは残らない）、復元前の自動バックアップから、さらに戻せる、バックアップに設定がなければ設定のファイルもなくなる、予定がなければ何もしない
- 失敗: 設定のファイルを動かせないとき（途中で失敗）に、DB も設定も元のまま、展開したDBがない、予定の目印が壊れている、前回の入れ替えが途中で止まっている（退避したファイルを元に戻す）
- 準備: ZIP でないファイル、形の違う ZIP、新しい版のバックアップを断る、作ったバックアップを受け入れる、自動バックアップを作って展開して予定を残す（今のデータには触れない）、残す数が1でも復元元は消えない、壊れた DB を断る（何も変更せず、自動バックアップも作らない）、ZIP の中の細工した名前で、ほかの場所へ書かれない
- 設定画面: 選ぶ → 確認 → 準備 → 再起動、ファイルを選ばない・確認でキャンセルしたら何も変えない、復元できないファイルは確認せずに理由を知らせる、再起動できなかったら予定を残して警告する
- 再起動の引数: 読み取り、終わったプロセスは待たない
- 実際の再起動（新しいプロセスの起動、ミューテックス、画面の切り替え）は、自動テストでは確かめていない（手で確かめる）

## 36. v0.2.0 Phase 14 で確定した実装方針（アプリの更新）

要件定義 24.6、画面一覧 8.3。上記の各章と異なる場合は、本章を優先する。

### 36.1 構成

| 部品 | 層 | 責務 |
|---|---|---|
| `GitHubReleaseClient` | Infrastructure（Updates） | GitHub のリリースの一覧の取得（`api.github.com`）と、配布物・ハッシュの URL の取り出し |
| `ReleaseInfo` | Infrastructure（Updates） | リリース1つ（タグ、版、試用版か、ページ、配布物、ハッシュ） |
| `UpdateService` | Application | 確認（`CheckAsync`）、更新の準備と、新しい版の起動（`InstallAsync`） |
| `UpdateApplier` | Infrastructure（Updates） | アプリのフォルダの入れ替え（`Apply`）、結果の書き込みと読み取り、起動の引数 |
| `IUpdateLauncher` / `WpfUpdateLauncher` | Presentation | 新しい版の実行ファイルを起動して、このアプリを終了する |
| `IUpdateDialogs` / `WpfUpdateDialogs` | Presentation | 更新の確認のダイアログ |

### 36.2 確認

- 「更新を確認」を押したときだけ通信する（起動時には通信しない）。`GET https://api.github.com/repos/{owner}/{repo}/releases?per_page=30`。`User-Agent` は `35Viewer/{版}`。送るのは通常の HTTPS の要求だけで、利用者のデータは送らない
- 下書き（draft）は、API が返さない（認証なしのため）うえ、念のため無視する。試用版（prerelease）は対象にする。タグが `v0.2.1`（3つの数字）の形でないリリースは、含めない
- 配布物は `K35Viewer-v{版}-win-x64.zip`、ハッシュは `K35Viewer-v{版}-win-x64.zip.sha256`（`release.yml` が作る。名前は `GitHubReleaseClient.PackageName` / `HashName` に1か所で決めてあり、ワークフローとそろえる）。ダウンロードの URL とリリースのページが、`https://github.com/` でなければ、ないものとして扱う（それ以外の相手へは、通信もブラウザでの表示もしない）
- 一覧の先頭（最新の版）が、今の版より新しければ、新しい版がある。同じか古ければ、最新。30秒で打ち切る。失敗（接続できない、HTTP エラー、レート制限（403/429）、JSON を読めない）は、例外にせず、理由つきの結果で返す

### 36.3 更新の準備と入れ替え

アプリは、動いている間は、自分のフォルダのファイルを入れ替えられない。復元（35章）と同じく、**準備**（動いている間）と**入れ替え**（再起動後）に分け、入れ替えは、ダウンロードした**新しい版の実行ファイル**が行う（別の updater を配布物に足さない）。

**準備**（`UpdateService.InstallAsync`）

1. 配布物とハッシュがなければ、通信せずに断る。アプリのフォルダに書き込めなければ（確認用のファイルを作って消せるか）、通信せずに断る。どちらも「リリースのページから、手で入れ替えてください」と案内する
2. 更新用のフォルダ（`update-staging`）を作り直す
3. ハッシュのファイルをダウンロードし、先頭の16進64文字を SHA-256 として読む（読めなければ断る）。続いて、配布物をダウンロードする（進行を報告し、取り消せる）
4. 配布物の SHA-256 を計算し、ハッシュと比べる。大文字・小文字は区別しない。一致しなければ、「破損または改ざんの可能性があるため、更新を中止しました」と断る
5. `update-staging\app` へ展開する。ZIP が1つのフォルダ（`K35Viewer-win-x64`）に収まっていれば、その1階層を除く。展開先の外へ書かれる名前のエントリが1つでもあれば、何も展開せずに断る。`K35Viewer.exe` がなければ断る
6. 今のデータを自動でバックアップする（35章。新しい版が DB の形を新しくした場合、古い版には戻せないため）
7. `update-staging\app\K35Viewer.exe` を、`--apply-update "<アプリのフォルダ>" --wait-for-exit <このプロセスの番号>` で起動し、このアプリを終了する。起動できなければ断る
8. 途中で失敗・取り消しになった場合は、`update-staging` を消す。アプリのフォルダにも、データ（バックアップを除く）にも、変更を加えない

バックアップ（6）をダウンロードと確認のあとにするのは、ダウンロードに失敗したときに、使わない自動バックアップを増やさず、残す数の枠を、使わせないため（要件定義 24.6 は、バックアップ → ダウンロードの順に書くが、結果は同じで、失敗時の副作用が少ない）。

**入れ替え**（`UpdateApplier.Apply`。`App.OnStartup` が、`--apply-update` を見て、画面を出さずに実行する）

- 起動の最初に、古いプロセスの終了を待つ（復元と同じ。最長30秒）。この起動は、単一起動のミューテックスを取らない
- 展開したフォルダ（今動いている新しい版のフォルダ）の全ファイルについて、アプリのフォルダに同じ名前のファイルがあれば、`update-rollback` へ退避してから、新しいファイルをコピーする。ウイルス対策ソフトなどに一時的に掴まれている場合に備えて、短い間隔で再試行する（5回、200ミリ秒）。アプリのフォルダにあって、新しい版にないファイル（利用者が置いたもの、使われなくなったファイル）は、触れない
- **途中で失敗した場合**: コピーしたファイルを消し、退避したファイルを元の場所へ戻す（新しく増えるはずだったファイルも残さない）。元に戻せなかった場合は、退避したファイルを残し、その旨を結果に書く
- 結果（成功か、メッセージ、版）を `update-result.json` に書き、アプリのフォルダの `K35Viewer.exe` を起動して終了する。成功なら新しい版、失敗なら元の版が起動する
- 起動したアプリが、`update-result.json` を読み（読んだら消す）、画面を出してから通知する。起動のたびに `update-staging` を片付ける（入れ替えのプロセスが終わるまで使用中の場合は、次の起動で片付く）

- **入れ替えの間のウィンドウ**: 起動の最初（古いアプリの終了を待つ前）に、小さな「更新しています」のウィンドウ（`UpdateApplyWindow`）を出す。古いアプリが終わってから、新しい版の画面が出るまで、何も表示されない時間をなくすため。ファイルの入れ替えと、古いアプリの終了待ちは、別のスレッドで行い（ウィンドウを固めない）、結果を書いて、アプリのフォルダの実行ファイルを起動したあと、その画面（メインウィンドウ）が出るまで（最長20秒）、ウィンドウを残してから閉じる。外観は、設定のファイルに合わせる。操作も、閉じることもできない（`Closing` を取り消す。アプリの終了のときは止めない）

入れ替えの処理が、新しい版のコードで動くため、v0.2.0 → v0.3.0 の入れ替えは、v0.3.0 の `UpdateApplier` が行う。v0.2.0 の更新機能が担当するのは、確認、ダウンロード、ハッシュの確認、展開、バックアップ、起動までで、ここは、v0.2.0 のコードが責任を持つ。

### 36.4 設定画面

- 「アプリの更新」: 現在の版、「更新を確認」、「変更点を見る」（新しい版が見つかっているときだけ押せる）、「更新する」（見つかっていて、アプリの中で更新できるときだけ押せる）、「中止」（確認・ダウンロードの間だけ表示）、状況の表示、通信についての注意書き
- 確認と更新は、同時に実行できない。設定画面を閉じるときは、実行中の確認・ダウンロードを取り消す
- ダウンロードの進行は、「ダウンロードしています… 12.3 MB / 80.1 MB」のように表示する
- **更新の間の表示**: 「更新する」の確認のあとから、`IsInstallingUpdate` が true になり、設定画面の上に、画面全体を覆う表示を出す（今していることの説明 `UpdateProgressText`、進みの棒 `UpdateProgressPercent` / `IsUpdateProgressIndeterminate`、「中止」）。下の項目（`DockPanel`）は `IsEnabled` を false にして、マウスでもキーボードでも操作できなくする（`IsSettingsEnabled`）。設定画面を閉じる操作は、`Closing` を取り消して止める（アプリの終了のときは止めない。止めると、新しい版への入れ替えのための終了を妨げるため）
- 進みの棒は、ダウンロードの間（大きさが分かるとき）だけ割合を出し、確認、展開、バックアップ、起動の間は、動き続ける表示にする
- 失敗・中止のときは、`IsInstallingUpdate` を false に戻す。新しい版を起動できたときは、アプリが終わるまで、true のまま残す（消えると、操作できる状態に一瞬戻るため）。「新しい版を起動する」段階（`UpdatePhase.Starting`）に入ったら、中止できない

### 36.5 テスト

- リリースの取得: 下書きを除く、試用版を含む、版の新しい順、配布物の名前の対応、`github.com` 以外の URL を無視する、タグの形（版を読めないタグを除く）
- 確認: 新しい版がある（試用版を含む）、同じ版・古い版・空は最新、失敗（HTTP エラー、レート制限、接続できない、JSON が壊れている）は理由つきで返す
- 準備: 成功（展開、バックアップ、起動の引数、アプリのフォルダに触れない、進行の順序）、ハッシュの不一致（バックアップも起動もせず、ダウンロードしたファイルを残さない）、ハッシュのファイルが読めない、大文字のハッシュ、配布物やハッシュがない・書き込めない（通信しない）、不正な名前の ZIP（何も展開しない）、実行ファイルがない、起動できない、ダウンロードの途中の取り消し

- 設定画面: 確認、最新の表示、確認できなかった表示、アプリの中で更新できない版、更新（確認 → 準備 → 起動）、確認でキャンセル、失敗の表示と通知、ダウンロードの中止
- 更新の間の表示: ViewModel の状態の流れ（準備の間は覆う表示を出して設定を操作できなくし、中止すると戻る。失敗したら消える。起動したあとは残り、もう中止できない）。実際の WPF のウィンドウで、覆う表示が出ること、項目が操作できないこと、閉じられないこと、終わると戻ること。入れ替えの間のウィンドウの表示と、閉じられないこと
- 実際の通信と、新しい版の起動・入れ替え・再起動は、自動テストでは確かめていない（手で確かめる。0.2.0 と 0.2.1 を並べて確かめる）

## 37. ビューアで前後のアーカイブへ移る操作（Issue #13）

画面一覧のビューアのキー割り当て（前後のアーカイブへ移る操作）。上記の各章と異なる場合は、本章を優先する。

### 37.1 構成

| 部品 | 責務 |
|---|---|
| `ViewerViewModel.NavigateArchiveRequested`（`EventHandler<int>`） | ↑ / ↓（一覧表示では Ctrl+↑ / ↓）で発行する。値は向き（+1 が次、-1 が前）。どのアーカイブへ移るかは、ここでは決めない |
| `LibraryViewModel.FindNeighbor` | 今の一覧（`Archives`）の中で、開いているアーカイブの前後を探す。開けないことが分かっているものは飛ばす |
| `ArchiveListItem.IsKnownUnopenable` | 一覧の状態（`BROKEN`、`EMPTY`、`UNSUPPORTED`）から、開けないことが分かっているか |
| `MainViewModel.OnNavigateArchiveRequested` | 確認（DLG-01）、ZIP の更新、今のアーカイブを閉じる、次のアーカイブを開く、の流れ |

### 37.2 前後の決め方

- 基準は、ライブラリの一覧（`LibraryViewModel.Archives`）そのもの。ビューアを開いている間も、ライブラリ画面は作り直されず、一覧が残っているため、選んでいるフォルダ、検索、並べ替えが反映された並びを、そのまま使える。追加の問い合わせ（DB）は要らない
- 「すべて」の一覧は、全フォルダを合わせて並べ替えた1本の並びなので、フォルダをまたいで進む。フォルダを選んでいる一覧は、そのフォルダ（サブフォルダを含む）だけなので、その中で止まる。どちらも、同じ処理（一覧の前後を探すだけ）
- 開いているアーカイブが一覧に見つからない場合（バックグラウンドのスキャンで一覧が組み直されて、消えたなど）は、何もせず、理由を通知する
- 端では、ぐるっと回らない。開けるアーカイブがなければ、通知して、今のアーカイブに留まる

### 37.3 移る流れ（`OnNavigateArchiveRequested`）

1. 画面を切り替え中、更新中、ビューアを表示していないときは、何もしない
2. 移り先を決める（`FindNeighbor`）。見つからなければ、通知して終わる。移り先は、この時点で決め、以降の更新で一覧が並べ替わっても、変えない
3. `DecideLeave`（離れるときの確認 DLG-01。ライブラリへ戻るときと共通）。キャンセルなら、留まる
4. 「更新する」（または、確認の設定がオフ）なら、`UpdateArchiveAsync` で ZIP を更新する。失敗・キャンセルなら、留まる
5. 今のアーカイブを閉じる（閲覧位置の保存を含む）。更新したときは、ライブラリの一覧とサムネイルを更新する
6. ライブラリで、移り先を選ぶ。ライブラリは、ビューアの間、非表示で、プログラムから選んだだけでは、一覧はスクロールしない（スクロールするのは、一覧の中のキー操作のときだけ）。そのため、`LibraryView` が、表示されたとき（`IsVisibleChanged`）に、選ばれているアーカイブまでスクロールする（`ScrollToSelected`。詳細表示は `ListView.ScrollIntoView`、サムネイル表示は、選ばれているアーカイブがある行 `GetSelectedRowIndex` へ）
7. 移り先を開く。開けなかった場合は、ViewerService が理由を通知しているので、ライブラリへ戻る

画面は、ライブラリを経由せず、ビューアのまま、中身だけが入れ替わる。更新中の表示と、キャンセルの扱いは、ライブラリへ戻るときと同じ。

### 37.4 キー

- 1枚表示: ↑ が前、↓ が次。Alt が押されているときは、割り当てない
- 一覧表示: ↑ / ↓ は、画像の選択に使われている（`HandleListKey`）。前後のアーカイブへ移るには、Ctrl を押す
- 前後の画像（← / →）、先頭・末尾（Home / End）とは、重ならない

### 37.5 テスト

- ↓ で次、↑ で前に移る（ライブラリへ戻らない。ライブラリ側の選択も移る）、並べ替え（降順）に従う
- 一覧の先頭・末尾で止まり、理由を通知する
- 開けないことが分かっているアーカイブ（破損）を飛ばす（進むときも、戻るときも）。その先に、開けるものがなければ止まる
- 一覧表示では、↑ / ↓ では移らず、Ctrl+↑ / ↓ で移る
- 削除予約があるとき: キャンセルで留まる（削除予約も残る）、破棄して移る（ZIP は変わらない）、反映して移る（ZIP を更新してから開く。更新前の ZIP は、ごみ箱へ）
- 次のアーカイブを開けなかった場合（ファイルがない）は、通知して、ライブラリへ戻り、開こうとしたものが選ばれる
- ビューアを開いていないときは、何もしない
- ライブラリ画面（WPF）: 非表示の間に、遠くのアーカイブをプログラムから選び、表示したとき、その行が生成されている（スクロールされている）。詳細表示とサムネイル表示の両方
## 38. RAR / 7z の閲覧（Issue #3）
RAR / CBR と 7z / CB7 を、閲覧だけで扱う（要件定義 19.1）。読み取りには SharpCompress（MIT）を使う。ZIP は、今までどおり `System.IO.Compression` で読み書きする（作り直しの処理を変えないため）。
### 38.1 構成
| 部品 | 責務 |
|---|---|
| `ArchiveFormats` | 対応する拡張子（スキャン、名前変更、DBの `extension`）と、形式の判定（`Detect`）。形式は、ファイルの先頭の署名で決め、署名で決まらないとき（読めない、短い、知らない署名）だけ、拡張子で決める |
| `ArchiveImageFilter` | 画像として扱うエントリの判定（JPEG / PNG / GIF / WebP。フォルダ、`__MACOSX/`、`._*` を除く）。ZIP と RAR / 7z で共通 |
| `ArchiveReader` | 入口（`IArchiveReader`）。`Detect` が RAR / 7z なら `SharpCompressArchiveReader` へ渡し、それ以外は今までの ZIP の処理 |
| `SharpCompressArchiveReader` / `OpenedSharpArchive` | RAR / 7z の解析、開く、エントリの読み出し。結果は ZIP と同じ形（`ArchiveAnalysis`、`ArchiveOpenResult`）で返す |
| `IOpenedArchive.CanModify` / `IsSolid` | 作り直せるか（ZIP だけ true）、ソリッド形式か。既定の実装を置かず、実装ごとに明示する（包むクラスが、中身へ渡し忘れても、コンパイルで分かるように） |
| `ViewerSession.CanModify` / `IsSolid` | 開いたアーカイブの上の2つを、ビューアへ見せる |
| `ViewerViewModel.DeleteBlocked` | 削除予約を断ったときに、理由を知らせる。通知は `MainViewModel` が出す |
| `MainViewModel.AnnounceIfSolid` | ソリッド形式を開いたときに、後ろのページが遅いことを知らせる |
### 38.2 形式の判定
- 署名: ZIP は `PK 03 04`（空は `05 06`、分割は `07 08`）、RAR は `Rar! 1A 07 00`（RAR 4 まで）/ `Rar! 1A 07 01 00`（RAR 5）、7z は `37 7A BC AF 27 1C`
- 拡張子ではなく中身で決めるのは、「.cbr」という名前の ZIP や、「.cbz」という名前の RAR が、よくあるため。名前を変えて拡張子が中身と合わなくなっても、開ける
- スキャンの対象は、拡張子で決める（`.zip`、`.cbz`、`.rar`、`.cbr`、`.7z`、`.cb7`）。全部のファイルの先頭を読むと、遅いため
- DB の `archives.extension` は、ファイル名の拡張子を記録する（中身の形式ではない。DB設計書 6.3）
### 38.3 読み取り
- ファイルは、共有を許可して（`FileShare.ReadWrite | Delete`）開き、展開してファイルに書き出さず、メモリ上で読む。読み出しの上限（圧縮爆弾対策）は、宣言されたサイズと、実際に読んだ量の両方で守る（ZIP と同じ）
- エントリの名前は、区切りを `/` にそろえる（閲覧位置の記録との照合に使うため）。並びは ZIP と同じ自然順。同じ名前が重なっていたら、最初のものを使う
- 暗号化（画像のエントリの暗号化、ヘッダーの暗号化）と分割（複数の巻）は、対応していない形式（`UNSUPPORTED`）として、理由を返す。画像がなければ `EMPTY`
- SharpCompress は、壊れたファイルで、専用の例外ではなく、`InvalidOperationException`、範囲外、変換の失敗なども投げる。出どころの分からないファイルを開くため、SharpCompress の呼び出しを囲む場所では、これらも「壊れている」（`BROKEN`）として扱う。ファイルがない、権限がないなどは、ZIP と同じ扱い
- 開いたままのアーカイブ（`OpenedSharpArchive`）の読み出しは、ロックで直列化する（SharpCompress のアーカイブは、複数のスレッドから同時に読めないため）
### 38.4 閲覧だけ
- 削除予約（Delete、右クリックの「削除予約」）は、`ViewerViewModel.ApplyPendingDelete` で、`CanModify` が false なら予約せず、`DeleteBlocked` で理由を知らせる（画面一覧 4.6）。予約の解除は、もともと予約がないため、起こらない
- 念のため、更新（`ArchiveService` の更新できない理由の確認）でも、中身が RAR / 7z なら「ZIP 形式ではないため、更新できません」として断る
- アーカイブ自体の名前変更・移動・削除は、ファイルの操作なので、形式によらず行える
### 38.5 ソリッド形式
ソリッド形式は、1枚だけ取り出すにも、手前を読み進める。測定（28MB・120枚の 7z）では、先頭が約18ms、中ほどが約1.0秒、最後が約2.3〜3.0秒だった（ソリッドでないものは、どのページも4〜17ms）。第1段階では、通常の読み出しのままにし、開くたびに案内（画面一覧 4.7）を出す。ZIP に変換すれば、速くなる（39章）。先読みやキャッシュで速くする工夫は、今後の課題とする。
### 38.6 DB
`archives.extension` のCHECKを広げるため、2番目のマイグレーションで表を作り直す。外部キーを切る手順と、整合の確認は、DB設計書 13章。
### 38.7 テスト
- 形式の判定: 先頭の署名（ZIP、RAR、7z）、名前と中身が違うもの（「.cbr」の ZIP は ZIP として書き込める、「.cbz」の 7z は書き込めない）、ファイルがない・署名が分からないときは拡張子で決める、対応する拡張子と DB に入れる値
- RAR / 7z の読み取り: 解析（画像だけを数える、表紙の候補は自然順）、開いて自然順に読む（ソリッドかどうか、書き込めないこと）、開かずに1枚だけ読む（サムネイル用）、読み出しの上限、閉じたあとは読めない（二重に閉じてもよい）、開いている間も他のプログラムが名前を変えられる、画像なし、暗号化、壊れたもの（アーカイブでない中身、途中で切れた 7z）、ファイルがない、日本語や記号を含む名前の RAR
- 流れ: スキャンで見つけ、解析とサムネイルまで進む、名前変更（拡張子を省くと元の拡張子。DB の拡張子も合う）、ビューアで開ける、削除予約を断って理由を知らせる（ZIP は今までどおり予約できる）、ソリッド形式のときだけ案内が出る、画像の削除を確定する更新を断る
- マイグレーション: 新しい DB で全部の拡張子を登録でき、それ以外は断る、バージョン1の DB を移行しても行と関連する表が変わらない、移行のあとも索引・連番・外部キーが働く、空の DB の移行、整合がとれなければ全体を取り消し、外部キーはオンに戻る、外部キーを切る印の見分け
- 7z のテスト用のファイルは、7-Zip で作った小さなもの（1.3KB以下）を `tests/K35Viewer.Tests/Fixtures/archives/` に置く（ソリッド、非ソリッド、画像なし、データの暗号化、ヘッダーの暗号化）。RAR は、作る道具（WinRAR）が自由に使えないため、テストの中で、無圧縮の RAR 5 を組み立てて使う（`TestRars`）。RAR 5 のフォルダの区切りは `/`
- 実際の RAR（Web で公開されている配布物。非ソリッド、JPEG 12枚）は、手で確かめた（リポジトリには入れない）
## 39. RAR / 7z の ZIP への変換（Issue #20）
RAR / 7z は閲覧だけ（38章）のため、編集したい場合は ZIP に変換する（要件定義 19.1）。
### 39.1 構成
| 部品 | 責務 |
|---|---|
| `IZipConverter` / `ZipConverter` | RAR / 7z の全エントリを、新しい ZIP へ写す（SharpCompress で読み、`ZipArchive` で書く）。変換後に要る容量の見積もり |
| `ArchiveService.PlanZipConversion` | 変換できるか（中身が RAR / 7z か、同じ名前のファイルがないか）と、変換後の名前、元のファイルを残す理由（ごみ箱を使えない） |
| `ArchiveService.ConvertToZipAsync` | 変換の流れ（39.3）。結果を通知し、操作履歴に記録する |
| `ArchiveRepository.UpdateAfterConvertAsync` | DBの反映（DB設計書 11.10） |
| `IDialogService.ConfirmConvertToZip` | 確認（画面一覧 3.5） |
| `LibraryViewModel.ConvertSelectedToZipCommand` | ライブラリの右クリックメニューから。RAR / 7z の名前のときだけ実行できる（`ArchiveListItem.CanConvertToZip`） |
| `ViewerViewModel.RequestConvertToZipCommand` / `ConvertToZipRequested` / `IsReadOnlyArchive` | ビューアのツールバーから。閲覧だけのアーカイブを開いているときだけ、ボタンを出す |
| `MainViewModel.OnConvertToZipRequested` | ビューアからの変換の流れ（39.4） |
### 39.2 写し方
- 全部のエントリ（画像以外のファイル、フォルダ、`__MACOSX` の中も）を、同じ名前で写す。区切りは `/` にそろえ、フォルダは末尾に `/` を付ける。名前は変えないので、閲覧位置の記録と、サムネイルの元の画像の名前が、変換の前後で一致する
- 名前に ASCII 以外の文字があれば、UTF-8 の印を付けて書く（`ZipArchive` の既定）。ZIP の読み取り（38章以前と同じ処理）で、同じ名前として読める
- 圧縮済みの形式（JPEG、PNG、GIF、WebP など）は、そのまま保存する（圧縮し直しても小さくならず、時間だけがかかるため。ZIP の作り直しと同じ考え。29章）。ほかは、最も小さくなる設定で圧縮する
- 日時は、エントリの更新日時を写す。ZIP で表せない日時（1980年より前、2107年より後）は、範囲の端にそろえる
- 読み方: ソリッド形式と 7z は、先頭から順に読む（`ExtractAllEntries`。1件ずつ開くと、そのたびに手前から読み直して遅くなるため）。ソリッドでない RAR は、順に読む方法が使えないため、1件ずつ開く（それぞれ独立に圧縮されていて、速い）
- 暗号化・分割されたものは、全部を写せないため、変換しない。壊れていれば、宣言された大きさと、実際に読めた量が違う場合も含めて、壊れている（`ARCHIVE_BROKEN`）として断る
- 作った ZIP は、ZIP の作り直しと同じ確認（`IArchiveWriter.Verify`。開き直して、全エントリの名前・大きさ・CRC32 が、写したものと一致し、最後まで展開できる）で確かめる
### 39.3 流れ（`ConvertToZipAsync`）
1. 準備: 変換できるか（`PlanZipConversion`）、空き容量（見積もり + 16MB）。同じアーカイブの更新・変換と、同時には行わない
2. 一時ファイル（元のファイルと同じフォルダの `〈元の名前〉.〈GUID〉.k35tmp`。スキャンの対象外で、残ってもスキャンが片付ける）へ写し、確かめる。ここまでは、キャンセルできる。失敗・キャンセルでは、一時ファイルを消し、何も変えない
3. 元のファイルが、その間に変わっていないことを確かめる
4. 一時ファイルを、変換後の名前にする（ここからはキャンセルしない。再試行つき）。失敗したら、一時ファイルを消して終わる（元のファイルは、そのまま）
5. DBを反映する（DB設計書 11.10）。失敗したら、置いた ZIP を消して、元に戻す
6. 元のファイルを、ごみ箱へ移す。ごみ箱を使えない保存先では、移さずに残す。移せなかった場合も残す。どちらも、結果は `Partial` で、警告として通知する

元のファイルを消すのを最後にしているので、どの段階で失敗しても、元のファイルは残る。ZIP の作り直し（11章）とは、置き換えの順序が逆になる（作り直しは、同じ名前に置くため、先に元のファイルを退避する必要がある）。
### 39.4 ビューアからの変換
1. 確認（キャンセルなら、開いたまま何もしない）
2. 画面全体を覆う表示（ZIP の更新と同じ `IsUpdating`。進み具合の説明は、変換用のもの）を出し、アーカイブを閉じる（閲覧位置を保存し、ファイルを離す）
3. `ConvertToZipAsync`（ZIP の作成と確認の間は、表示の「キャンセル」が効く）。成功したら、ライブラリの一覧を読み込み直す
4. 同じアーカイブ（同じID）を開き直す。閲覧位置を引き継いでいるため、同じページから続く。変換できなかった場合も、元のアーカイブを開き直す。開き直せなかった場合は、ライブラリへ戻る
### 39.5 テスト
- 変換の処理: 7z（ソリッド、非ソリッド）の全部のエントリが、同じ名前・内容で写り、確認が通る。RAR の日本語の名前とフォルダが UTF-8 の名前になり、ZIP の読み取りで同じ画像として読める。画像は圧縮し直さない。暗号化（データ、ヘッダー）、途中で切れたものは変換しない。変換先に同じ名前があれば上書きしない。日時と名前の変換
- 流れ: ID・閲覧位置・解析の結果・サムネイルを引き継ぎ（作り直しの対象にならない）、元のファイルはごみ箱へ、履歴が残る、変換した ZIP は画像を削除できる。CBR は CBZ になる。ごみ箱を使えないときは元を残し、次のスキャンで別のアーカイブになる（変換した ZIP は元のID）。ごみ箱へ移せなかったとき。同じ名前の ZIP があるとき、中身がすでに ZIP のときは、何も変えない。変換に失敗、作成の途中でキャンセルしたときは、元のファイルも記録も変わらず、一時ファイルが残らない
- 画面: ライブラリで、ZIP には変換を出さず、確認でキャンセルなら何もしない、変換したあとも同じアーカイブが選ばれている。ビューアで、変換すると同じ位置で開き直し、削除予約できる。確認でキャンセルなら開いたまま
- 実際の RAR（38.7 と同じもの）で、ライブラリとビューアからの変換を、手で確かめた
## 40. GIF / WebP の対応（Issue #2）
画像として扱う形式に、GIF と WebP を加えた（要件定義 19.2）。デコードは、これまでと同じ WPF 標準の画像API（WIC）だけで行い、追加のライブラリは入れない。
### 40.1 変更点
| 部品 | 内容 |
|---|---|
| `ArchiveImageFilter` | 画像として扱う拡張子に、`.gif` と `.webp` を加えた。ZIP（`ArchiveReader`）と RAR / 7z（`SharpCompressArchiveReader`）で共通の判定なので、枚数の数え方、表紙の候補（自然順の先頭3枚）、ビューアに並ぶ画像は、形式によらず同じ流れになる |
| `ThumbnailGenerator` / `ViewerImageDecoder` | 変更なし。どちらも `BitmapDecoder` が形式を見分けるので、GIF / WebP も、JPEG / PNG と同じく「縮小しながら読む」。サムネイルのキャッシュの出力は、これまでどおり JPEG（`thumbnail_cache.format` は出力の形式で、元の画像の形式ではない） |
| `ViewerViewModel.BuildImageErrorText` | 画像を読めなかったときの文言。WebP のときだけ、「この環境では WebP を読めない可能性があります」を添える |
| `ViewerService` | 「画像なし」で開けないときの案内に、対応する形式（JPEG / PNG / GIF / WebP）を出す |
| `0003_requeue_empty_archives.sql` | 「画像なし」を解析待ちに戻す（DB設計書 13.2） |
### 40.2 GIF のアニメーション
`BitmapDecoder.Frames[0]`（最初の1コマ）を使う。サムネイルも、ビューアの表示も、動かさない。アニメーションを動かすかは、将来の課題とする。
### 40.3 読めない環境の扱い
WebP は、Windows の「WebP 画像拡張機能」（Store）がない環境では、WIC が読めない。拡張子で数えるため、枚数には数えるが、画像としては読めない。そのときの扱いは、壊れた画像と同じ経路に乗せる（新しい状態は設けない）。
- サムネイル: 表紙の候補（先頭3枚）を順に試し、すべて読めなければ、サムネイルの状態が `FAILED` になり、枠に「表紙を読めません」と出る（再試行は、アーカイブが変わるまでしない）
- ビューア: `PageImageLoader` が `ImageDecodeException` を受け、その頁の位置に「画像を読み込めません: 〈エントリ名〉」を出す。WebP には、理由を添える。ほかの頁の閲覧は続けられる。一覧表示の小さなサムネイルは、「読み込めません」になる
- 自前のデコーダー（ImageSharp、Magick.NET）は入れない。理由: 縮小しながら読む WIC の速さを保つ、配布物を増やさない、信頼できないファイルを読むライブラリを増やさない。AVIF / HEIC / JPEG XL は、手元のファイルで必要になったときに、改めて選ぶ
### 40.4 テスト
- 判定: `.gif`、`.webp`（大文字、フォルダの中、`\` の区切り）は画像、`.bmp`、`.avif` は画像ではない
- 解析: GIF と WebP だけの ZIP が `Ready` になり、枚数と表紙の候補が自然順で返る。画像でない拡張子（`.bmp`、`.avif`）だけなら `Empty`
- サムネイル: GIF が JPEG のサムネイルになり、アニメーションは最初のコマ（赤）の色になる。WebP は、読める環境ではサムネイルになり、読めない環境では `ThumbnailGenerationException` になる（どちらでも通る。実行する環境に WebP の拡張機能があるかに、結果が左右されないため）
- 移行: DB設計書 13.2 のとおり
- 実際の GIF / WebP の入った ZIP で、ライブラリのサムネイルとビューアの表示を、手で確かめた
## 41. 新着の表示（Issue #16）
スキャンで新しく見つかったアーカイブに、「新着」の印を付ける（要件定義 5.4）。印は DB の `archives.is_new`（DB設計書 6.3、13.3）に持つ。
### 41.1 構成
| 部品 | 責務 |
|---|---|
| `ScanService`（`ApplyAsync` の `markNew`） | 新規に登録するアーカイブに、印を付けるか。管理フォルダの `LastScanAt` が null（はじめてのスキャン）なら付けない。`SuppressNewMarkingOnNextScan` が呼ばれていれば、次の1回のスキャン（全管理フォルダ）で付けない |
| `ArchiveBatch.InsertAsync`（`isNew`） | 新規の行を、`is_new` つきで登録する。更新（`UpdateChangedAsync`、`MarkSeenAsync`）は `is_new` を変えない |
| `App`（起動） | 復元が成功していたら、画面を出す（起動時のスキャンが始まる）前に、`SuppressNewMarkingOnNextScan` を呼ぶ |
| `ViewerService.OpenAsync` → `ClearNewAsync` | アーカイブを開けた時点で、そのアーカイブの印を外す（書き込みの失敗は警告のログだけで、閲覧は続ける） |
| `ArchiveRepository.ClearNewAsync` / `ClearAllNewAsync` | 1件、または選んだフォルダ以下（再帰CTE）・全部の印を外す。1件の方は、印がなければ何も更新しない |
| `LibraryService.MarkAllReadAsync` | 「新着を既読に」の窓口（書き込みキュー経由） |
| `ViewerViewModel.ArchiveOpened` → `MainViewModel` → `LibraryViewModel.MarkRead` | 開いたとき、一覧に出ている行の印だけを外す（一覧は取得し直さない）。ライブラリから開く場合も、ビューアの前後移動、ZIP 変換のあとの開き直しも、同じ経路 |
| `LibraryViewModel.ShowNewOnly` / `MarkAllReadCommand` | 「新着だけ」のチェックで一覧を取得し直す（`ArchiveQuery.NewOnly`）。「新着を既読に」は、選んでいるフォルダ（なければ全部）の印を外して、一覧を取得し直す |
| `ArchiveListItem.IsNew` / `MarkRead` | 一覧の1行の印。外したときに変更を通知する |
### 41.2 判断
- **印を DB の列にした理由**: `created_at` から求める案もあったが、はじめてのスキャン分を除けない（全部が登録日時の新しいものになる）。「すべて既読」も表せない。`last_viewed_at` は、頁を移るたびに更新されるうえ、最初の頁を表示してから少しあとにしか入らないため、外す条件に使いにくい
- **はじめてのスキャンの判定**: スキャンの種別（`ScanType.Initial`）ではなく、管理フォルダの最終スキャン日時（`LastScanAt`）で決める。途中でやめたり失敗したりして、はじめてのスキャンが完了していない間は、次のスキャンも同じ扱いになる。親フォルダを追加して、子の登録を統合する場合も、親の最初のスキャンは付けない
- **復元の直後**: 復元したDBは古い時点のもの。そのあとに増えたファイルが、すべて新着になるのを避ける。復元の予定は DB を開く前に実行され、起動時のスキャンは画面を出したあとに始まるため、画面を出す前に指定する。指定は、次のスキャン1回で使い切る
- **アプリの外での名前変更・移動**: 旧い行が不在（`MISSING`）になり、新しい名前が新規登録されるため、新着に見える。閲覧位置も引き継がれない（要件定義 15章の既存の制限）。今回は直さない
- **日数で外す案**: 入れていない（設定項目が増える。「新着を既読に」で足りる）。必要になったら、`created_at` を基準に足せる
### 41.3 テスト
- はじめてのスキャンでは付かない。そのあとのスキャンと、起動時のスキャン（`ScanType.Startup`）で見つかったものだけ付く。登録済みのアーカイブの変更では付かない
- アプリ内の名前変更では、印が変わらない（新着だったものは新着のまま、そうでないものは付かない）
- 復元の直後のスキャンでは付かず、そのあとのスキャンからは付く。はじめてのスキャンが完了していない管理フォルダは、次のスキャンでも付かない
- 開くと外れる。開けなかったアーカイブは外れない。ほかのアーカイブには影響しない
- 「既読」は、選んだフォルダ以下（サブフォルダを含む）だけ外れ、「すべて」なら全部外れる。外した件数を返す
- 一覧が、印を返し、「新着だけ」で絞り込める。行の `MarkRead` が、変更を通知する（2回目は通知しない）
- マイグレーション 0004: 既存の行が 0、0 と 1 以外は入らない
- 実際のライブラリで、印、絞り込み、既読、開いたときの印の消え方を、手で確かめた

## 42. ショートカット（Issue #23）
スタートメニューとデスクトップに、35Viewer のショートカットを作れるようにする（要件定義 24.8、ユースケース定義書 UC-19、画面一覧 DLG-04・8.3）。
### 42.1 構成
| 部品 | 責務 |
|---|---|
| `ShellLink`（Infrastructure/Shortcuts） | `.lnk` の作成と、リンク先の読み取り。Windows の `IShellLink`（COM）を使う。追加のパッケージはない。日本語・空白を含むパスも扱える |
| `ShortcutLocations` | 置くフォルダ（スタートメニューの「プログラム」、デスクトップ）。`Environment.GetFolderPath` で Windows に尋ねる（OneDrive などでリダイレクトされた場所も求まる）。現在の利用者用の場所だけ（管理者権限は使わない） |
| `IShortcutService` / `ShortcutService` | 作る・作り直す（`CreateAsync`）、削除（`Remove`）、状態（`GetState`: なし / 今の実行ファイルを指す / 違う場所を指す）、作ってよいか（`Availability`） |
| `ShortcutFirstRun` | はじめて起動したときの確認の流れ。聞くのは一度だけ（`AppSettings.ShortcutPromptShown`） |
| `ShortcutMessages` | 結果を、トーストで知らせる（成功と失敗は別の通知） |
| `IShortcutDialogs` / `WpfShortcutDialogs` / `ShortcutPromptDialog` | はじめての確認（DLG-04）と、一時的な場所での確認のダイアログ |
| `SettingsViewModel`（ショートカットの項目） | 設定画面の、状態の表示、作る・作り直す・削除のコマンド。ショートカットの操作の間は、ほかの操作を押せなくする |
### 42.2 判断
- **作ってよいかの判定（`Availability`）**: 実行ファイルの名前が `K35Viewer.exe` でなければ作れない（`dotnet` から動かしている場合などに、別のものを指さないため）。実行ファイルが `%TEMP%` の下にあれば「一時的な場所」（ZIP を Explorer で開いて、そのまま起動した場合は、ここに展開される）。名前が似ているだけの場所は、一時的な場所としない（フォルダの区切りまで含めて比べる）
- **はじめての確認を出す条件**: 聞いていない、かつ、作ってよい、かつ、スタートメニューに今の実行ファイルを指すショートカットがない。一時的な場所や、作れない場所では、聞かず、聞いたことにもしない。答えたら（「今はしない」も）、聞いたことにする
- **出すタイミング**: 起動の最後に、`Dispatcher` の「アイドル」の優先度で出す。画面の表示や、復元・更新の結果のトーストを、遅らせないため。例外は、ここで受けて、ログに残すだけ（確認で、起動を止めない）
- **ファイルの書き込みは、画面のスレッドの外**: `CreateAsync` は、`Task.Run` で動かす（OneDrive 上のデスクトップが、遅いことがあるため）。`IShellLink` は、どのスレッドからでも使える
- **作り直し**: 同じ名前があれば、上書きする（リンク先を、今の実行ファイルにする）。ほかのアプリが作った同じ名前のファイルも、上書きされる（「作り直す」「作る」は、利用者の操作のため）
- **削除は、ショートカットのファイルだけ**: 確認は出さない（いつでも作り直せるため）。アプリ本体、データ、アーカイブには、さわらない
- **タスクバーのピン止めを入れなかった理由**: Windows の API（`TaskbarManager.RequestPinCurrentAppAsync`）は、デスクトップアプリからも使えるが、.NET から呼ぶには、Windows SDK の C# の射影（`Microsoft.Windows.SDK.NET.dll`。ライセンスは Windows SDK のもので、同梱してよいかが、公式の資料ではっきりしない。展開後に約 24 MB、ZIP で約 6 MB 増える）が要る。Windows の版によっては、Microsoft が配るトークンも要る。開発機では「許可されていません」と返り、確かめられなかった。COM を手書きする案は、間違うとアプリが落ちるため、見送った。代わりに、Windows の標準の操作を案内する（Issue #23 のコメント）
### 42.3 テスト
- 実際の `.lnk` を、一時フォルダに作って確かめる（スタートメニュー、デスクトップの実際のフォルダには、触れない）: 作ると、リンク先が実行ファイルになる。日本語・空白を含む場所でも正しい。選んだ場所にだけ作る（作らない場所のフォルダにも、触れない）。リンク先が違うものは「古い」状態になり、作り直すと直る。削除は、ショートカットだけを消し、なければ何もしない。作れない場所があっても、ほかの場所には作り、理由を返す。実行ファイルの名前が違えば作れない。一時的な場所の判定
- はじめての確認: 確認して作り、聞いたことを記録する（保存されている）。「今はしない」でも、二度目は聞かない。すでに聞いていれば聞かない。作れない場所では聞かず、記録もしない。今のショートカットがすでにあれば、聞かずに記録する。古い版の設定のファイル（項目がない）は、聞いていない扱い
- 設定画面: 状態の表示と、ボタンの文字（作る / 作り直す）、作る・削除の動作と通知、失敗の理由の通知、一時的な場所での確認（断ると作らない）、実行ファイルが違う場合は押せない
- 実際のアプリで、はじめての確認、スタートメニューへの作成、タスクバーへの手動のピン留め、設定画面の見た目と動作を、手で確かめた

### 43.3 テスト
- タブは3つ（全般、データ、アプリ）で、この順
- 各項目は、決めたタブにあり、ほかのタブにはない（スクリーンリーダー向けの名前で確かめる）
- 枠は、見出しと同じ名前を持つ
- 更新中の覆い表示（既存のテスト）: 覆う表示が出て、項目を操作できず、閉じられない。項目は「アプリ」のタブを選んでから探す
- 実際のアプリで、3つのタブの見た目と、ダーク・ライトでの読みやすさを、手で確かめた

## 44. アンインストール（Issue #24）
プログラムのフォルダ、データのフォルダ、ショートカットを、アプリの中から削除する（要件定義 24.9、ユースケース定義書 UC-20、画面一覧 DLG-05・8.3）。**アーカイブには、さわらない**ことが、最も大事な条件。
### 44.1 構成
| 部品 | 責務 |
|---|---|
| `UninstallPlanner`（Infrastructure/Uninstall） | 安全の確認。消す場所を調べ、問題があれば、理由（`Blockers`）を返す。プログラムのフォルダの中を、リンクをたどらずに数える。バックアップの保存先の確認（`ValidateBackupFolder`）も持つ |
| `UninstallExecutor` | 消す処理。消す直前に、`UninstallPlanner` で、もう一度、確かめる（問題があれば、何も消さず、中止の結果を返す）。ショートカット → データ → プログラムの順に消す。1つ消せなくても続け、消せなかったものを集める |
| `UninstallHandoff` | 自分自身を消すための引き継ぎ。プログラムの一式を `%TEMP%` の下の `K35Viewer-uninstall-〈GUID〉\app` へ写し、予定（`plan.json`）を書く。起動の引数（`--uninstall 〈予定のファイル〉 --wait-for-exit 〈PID〉`）を作る・読む。控えの後片付け（`cmd`）を頼む |
| `KnownFolders` | Windows の「ダウンロード」フォルダ（`SHGetKnownFolderPath`。移されていても求まる） |
| `IUninstallService` / `UninstallService`（Services） | 確認（`PlanAsync`: 登録された管理フォルダと、今のショートカットを集めて、`UninstallPlanner` に渡す）、始める（`StartAsync`: もう一度確かめる → バックアップを保存 → 控えを起動 → アプリを終了） |
| `IUninstallLauncher` / `WpfUninstallLauncher`（Views） | 控えの用意と起動（画面のスレッドの外）と、アプリの終了（画面のスレッド） |
| `IUninstallDialogs` / `WpfUninstallDialogs` / `UninstallDialog` | 確認のダイアログ（DLG-05） |
| `UninstallWindow` | 控えが出す、消している間と結果のウィンドウ |
| `App.RunUninstallAsync` | 控えとしての起動（`--uninstall`）。単一起動の確認、DB、ログ、ホストの準備は、しない（消すため）。設定のファイルから、外観だけを読む |
| `SettingsViewModel`（アンインストールの項目） | 設定画面の「アンインストール…」の動作、押せない理由（ツールチップ）、案内 |
### 44.2 流れ
1. 設定画面を開いたときに、`PlanAsync` で、実行できるかを調べ、押せるかと、案内を決める
2. 「アンインストール…」を押すと、もう一度、`PlanAsync`。問題があれば、ダイアログを出さずに、理由を通知する
3. 確認のダイアログ（バックアップの保存先、「アンインストール」の入力）に答える
4. `StartAsync`: もう一度、確かめる → （選んだ場合）今のデータのバックアップを作り、保存先へ写して、大きさを確かめる（失敗なら、何も消さずに中止）→ `UninstallHandoff.Prepare`（控えの用意）→ 控えを起動 → アプリを終了
5. 控え（`%TEMP%` の写しの `K35Viewer.exe`）: アプリの終了を待つ（`RestartArguments.WaitForPreviousProcess`）。まだ動いていれば、何も消さずに中止。終わっていれば、`UninstallExecutor` が、消す
6. 結果のウィンドウを出す。閉じられたら、`cmd` に、控えのフォルダを、少し待ってから消すよう頼んで、終了する
### 44.3 判断
- **管理フォルダの保護**: 登録された管理フォルダが、消す場所と同じか、その中にあれば、実行しない。「アーカイブ以外だけ消す」案は、間違ったときの被害が大きいため、採らない。逆に、管理フォルダの中にプログラムのフォルダがあるのは、問題としない（消すのは、プログラムのフォルダだけのため）
- **プログラムのフォルダは、中身ごと消す**ため、追加の確認を重ねる: 35Viewer の本体のファイルがそろっている、アーカイブらしいファイルがない、ファイルが多すぎない（5,000個、2 GB）、大事なフォルダと同じ・含んでいない、ドライブの直下ではない、書き込める。配布物は、約440個、約150 MB で、余裕を持たせている
- **データのフォルダは、既知のものだけ消す**: `AppPaths` が持つ場所（DB と `-wal` `-shm` `-journal`、設定とその `.tmp` `.broken`、サムネイル、ログ、一時、バックアップ、復元と更新の一時）。ほかのものがあれば、フォルダごと残す。管理フォルダがデータのフォルダの中にあれば、実行しない
- **リンクは、たどらない**: ジャンクション、シンボリックリンクは、リンクだけを消し、先には触れない（数える・写す・消すの、どれでも）
- **ショートカット**: `IShortcutService.GetState` が「今のアプリを指している」ものだけ。ファイルの削除だけで、アプリ本体とデータには、さわらない
- **控えを `%TEMP%` に置く理由**: 消す対象（プログラムのフォルダ、データのフォルダ）の外で、書き込める場所のため。控えの場所が、消す場所の中になる場合は、準備しない
- **`cmd` の後片付け**: 控えのフォルダの名前（`K35Viewer-uninstall-` で始まる）と場所（`%TEMP%` の直下）を確かめ、`cmd` で特別な意味を持つ文字（`& ^ % ! | < > "`）を含むときは頼まない（一時フォルダは、Windows が、あとで片付ける）。頼んだ `cmd` は、`ping` で少し待ってから、`rmdir /s /q` する
- **確認のダイアログを 1 つにした**: 「何を消すか」「バックアップ」「確認の入力」を、別々のダイアログに分けると、あとの確認が、前の内容を忘れやすい。1 つにして、押せる条件（保存先に問題がない、「アンインストール」と入力した）を、その場で見せる
- **始められたら、押せないままにする**: アプリが終了するまでの間に、もう一度、始めないため
- **更新との違い**: 更新は、新しい版を、データのフォルダの中（更新用のフォルダ）から動かす。アンインストールは、データのフォルダも消すため、控えは、`%TEMP%` に置く
### 44.4 テスト
- `UninstallPlanner`（実ファイルを、一時フォルダに作る）: 問題がなければ実行できる。実行ファイルの名前、本体のそろい、管理フォルダの位置（プログラム・データの中、外、親）、アーカイブらしいファイル（`backups` の ZIP は対象外）、ファイルが多すぎる、大事なフォルダ、控えの一時フォルダ、バックアップの保存先
- `UninstallExecutor`: 消すものだけを消し、アーカイブと、指定していないショートカットは残る。35Viewer のものではないファイルは残り、フォルダも残る。消す直前の確認で、問題があれば、何も消さず、アーカイブも残る。ジャンクションは、リンクだけが消え、先のファイルは残る。読み取り専用のファイルも消える。使用中で消せないものがあっても、残りは消え、消せなかったものが報告される
- `UninstallHandoff`: 控えは、消す場所の外にあり、プログラムの写しと、読める予定がある。控えの場所が、消す場所の中なら、準備しない。起動の引数の作成と読み取り。壊れた予定は、読めない。後片付けは、決まった名前と場所のフォルダだけ
- `UninstallService`: 確認は、登録された管理フォルダと、今のショートカットだけを使う。バックアップは、保存してから、控えを起動する。選ばなければ、作らない。保存先が消す場所の中、保存できない、始める直前に問題が出た、控えを起動できない、の場合は、控えを起動せず、アプリも終了しない
- 設定画面: 問題がなければ押せる。実行できない理由の表示。スキャン・作成中は押せない。キャンセル、進む、バックアップなし、始められなかった場合の、それぞれの動作。ダイアログの前の確認で、実行できなくなっていた場合
- 実機での通し（自動の確認を、一時フォルダの見本で）: 実際に、控えのプロセスを起動し、プログラム、ショートカット、データ（35Viewer のものではないファイルを除く）が消え、アーカイブが残り、結果を閉じると、終了コード 0 で終わり、控え自身も消えることを、2 回、確かめた
- 動作確認用に、見本の環境を作る `scripts/uninstall-sandbox.ps1` を加えた。本物のアプリとデータには、触れない

## 45. 最近開いたアーカイブと、終了時の状態の復元（Issue #27、#26）
最近開いたアーカイブの一覧（要件定義 5.5、ユースケース定義書 UC-21、画面一覧 3.2）と、終了時の状態の復元（要件定義 24.10、UC-22、画面一覧 8.3・10章）。2つは、「最後に開いたアーカイブ」を扱う点が近いため、まとめて実装した。追加のパッケージはない。
### 45.1 構成（最近開いたアーカイブ）
| 部品 | 責務 |

| `archives.last_opened_at`（DB設計書 6.3、13.4） | 最後に開いた日時 |
| `ViewerService.OpenAsync` → `ClearNewAndMarkOpenedAsync` | 開けた時点で、「新着」の印を外し、開いた日時を記録する（1つの書き込み。失敗しても閲覧は続ける） |
| `ArchiveRepository.MarkOpenedAsync` / `ClearAllOpenedAsync` | 日時の記録と、すべての消去 |
| `ArchiveQuery.RecentOnly` / `ArchiveRepository.QueryAsync` | 開いたことのあるものだけを、新しい順に返す（DB設計書 11.8）。`ArchiveSummary.LastOpenedAt` に日時を入れる |
| `LibraryService.ClearRecentAsync` | 「履歴を消す」の窓口（書き込みキュー経由） |

| 部品 | 責務 |
|---|---|
| `AppSettings`（`MainWindowPlacement`、`LibrarySortKey`、`LibrarySortDescending`、`LibraryShowNewOnly`、`ResumeLastArchive`、`LastOpenArchiveId`） | 設定のファイルの項目（33.2）。古い版のファイルにはないため、既定値（ウィンドウは null、並べ替えはファイル名の昇順、続きから開くはオフ）になる |

| `MainViewModel.SaveExitState` | ウィンドウの位置と、ビューアで開いているアーカイブ（ライブラリ画面なら null）を保存する |
| `MainViewModel.ResumeLastArchiveAsync` | ライブラリの初期化を済ませてから、設定がオンで記録があれば、記録を消してから、一覧からの「開く」と同じ処理で開く |
| `LibraryViewModel.InitializeAsync` | 記憶した並べ替えと「新着だけ」にする。戻している間（`_restoringState`）は、一覧の取得と保存をしない（初期化の読み込みで、1回だけ取得する）。以降、変えるたびに保存する |
| `SettingsViewModel.ResumeLastArchive` | 設定画面の「起動時」の項目 |
### 45.3 判断
- **開いた日時を、パスではなくアーカイブの記録に持つ**: 設定のファイルにパスの一覧を持つ案は、アプリ内で名前を変える・移すと切れる。DB の行なら、同じ Archive ID のまま残る。不在・管理対象外の除外も、一覧のクエリと同じ条件で済む
- **`last_viewed_at` を使わない**: DB設計書 6.3 のとおり（頁を移るたびに変わる、ZIP の作り直しで NULL に戻る、履歴を消すと閲覧位置まで消える）
- **一覧を開くたびに読み直す**: 10 件だけのため、取得は軽い。開いたアーカイブを、一覧の表示に反映し忘れることがない
- **メニューバーは作らない**: 既存の画面にメニューバーがなく、ボタンとポップアップの方が、ほかの操作と並びがそろう（Issue #27 の相談で決めた）
- **続きから開く対象は、ビューアで終了したときだけ**: ライブラリへ戻ってから終了したのは、読み終えた、または閉じた、とみなす。「最後に開いたもの」は、最近開いたアーカイブの一覧から開ける
- **続きから開くのは1回だけ**: 開く前に記録を消す。開けないアーカイブを、起動のたびに開こうとして、通知を繰り返さない
- **ライブラリの初期化のあとに開く**: ビューアを閉じたときに、一覧がすぐ使えるように、また、前後のアーカイブへ移る操作（37章）の並びが決まっているように
- **検索の文字と、選んでいたフォルダは戻さない**: 起動したときに、一覧が絞り込まれたままだと、アーカイブが消えたように見えるため
- **ウィンドウの位置の確かめ方**: モニターごとではなく、仮想スクリーンとの重なりで判断する（WPF の標準の値だけで済む）。モニターの並びが L 字などで、仮想スクリーンの中の空いた所に出る場合は、確かめられない（そのときは、Windows の操作で戻せる）
### 45.4 テスト
- 開くと日時が記録され、開けなかったものは記録されない。一覧は、開いたものだけを新しい順に、指定した件数まで返す。履歴を消すと、日時だけが消え、閲覧位置は残る
- 画面の一覧: 読み込み、項目を選ぶと一覧が閉じてビューアで開き、開き直したものが先頭になる。履歴を消すと空になる
- ウィンドウの位置: 画面の中・左のモニター・外したモニター・上に出た・小さすぎる・値が壊れた、の判定。右端にかかる量の境目
- 設定のファイル: 新しい項目を保存して読み直せる。古いファイルでは既定値になる
- 一覧の並べ替えと「新着だけ」: 前回の値で始まり、変えると保存され、次の起動（新しい画面）で戻る
- 終了時の記録: ライブラリ画面ならアーカイブは記録しない。ビューアなら記録する。ウィンドウの位置が取れなければ、前回の値を残す
- 続きから開く: オンなら開いて記録を消す。オフなら開かない。見つからなければ、ライブラリ画面のままで記録を消す
- マイグレーション 0005（DB設計書 13.4）
- 実際のアプリで、「最近開いた」の一覧の見た目と動作、ウィンドウの位置・大きさ・最大化の復元、並べ替えの復元、続きから開く（設定をオンにして）を、手で確かめた

### 46.2 判断
- **記録を `archives` に持つ**: `thumbnail_cache` はキャッシュの削除で行ごと消えるため。画像そのものは持たない（名前と、割合の範囲だけ）
- **範囲を割合で持つ**: 切り抜きの画面は、画像を縮めて出す（長辺 1600px まで）。サムネイルを作るときは、別の大きさでデコードする。割合なら、どちらの大きさでも同じ範囲になる
- **縦横比を自由にした**: はじめはカードの比（164:220）に固定していたが、見開きの片側だけを選ぶときに、縦が足りないと、反対側が入ってしまう。そのため、自由にし、固定は「カードの縦横比に合わせる」で選べるようにした（Issue #15 の相談で決めた）
- **余白を色で埋めない**: サムネイルは JPEG のため、透明にできない。色で埋めると、テーマを切り替えたときに、その部分が浮く。カードは、画像を縦横比を保って収め、余った所にカードの背景（テーマの色）を出す作りのため、範囲の形のまま作れば、背景が自然に見える
- **画像の向きの情報（EXIF）は使わない**: これまでのサムネイルの作り方と同じ。切り抜きの画面も同じく使わないため、範囲がずれない
- **なくなったときだけ記録を消す**: 削除予約の確定などでエントリがなくなったら、戻らないため消す。読めなかっただけなら、一時的なこともあるため残す
- **RAR / 7z でもできる**: アーカイブ自体を変えないため
- **ドラッグは、始めたときの枠からの動きで決める**: 端で止まったあと、マウスを戻したときに、枠がずれないように（少しずつ足すと、ずれる）
### 46.3 テスト
- 範囲: 正しいかの判定（はみ出す、幅が 0、負の値、NaN）と、画素への変換
- 枠: はじめの枠（自由なら画像の全体、固定なら真ん中のいちばん大きな枠）、辺のつまみで横だけ・縦だけが変わり、反対の辺は動かない、画像の外へ広げない、下限、動かす、固定のときは角でも辺でも比が保たれる、固定への切り替え、割合への変換と、前の範囲からの再開、ドラッグを始めた枠への復元
- 画面: はじめは画像の全体を返す、固定にすると枠がカードの比になる、キーで動かせる、見本が出る
- サムネイルの作成: 範囲から作られる（色で確かめる）、長辺 300px まで縮め拡大しない、カードと違う比の範囲は、その形のまま
- 記録と作り直し: 選んだ画像から作られ、記録が残る。範囲も記録され、キャッシュを削除して作り直しても同じ。自動に戻す。選んだ画像がなくなると記録を消す。読めなければ自動で作り、記録は残す。正しくない範囲は記録しない
- 画面の流れ: 今の画像を表紙にすると、一覧の表紙が変わり、通知される。切り抜くときは画像を渡し、キャンセルなら何も変えない。切り抜いた範囲で作り直す。一覧表示では右クリックした画像が対象。ライブラリの右クリックで自動に戻せる
