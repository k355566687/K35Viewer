# 画像アーカイブ管理ビューア 要件定義

**文書バージョン:** Ver.0.4.3（19.1 RAR / 7z を ZIP に変換できるようにした。Ver.0.4.2: 19.1・19.3 RAR / 7z（CBR / CB7）を、閲覧だけで対応した。Ver.0.4.1: 24.5 自動バックアップを残す数を、設定で変えられるようにした。Ver.0.4: 24章 v0.2.0 で追加する機能（設定画面、バックアップと復元、アプリの更新）を追加。9.2・21.3・22章を、それに合わせて更新）  
**作成日:** 2026-11-06  
**更新日:** 2026-11-16

## 1. 目的

複数フォルダに保存された大量の画像アーカイブを一元管理し、圧縮ファイルを手作業で展開することなく、**画像の閲覧・整理・削除、およびアーカイブ自体のファイル管理を行えるWindowsアプリケーション**を開発する。

特に従来の、

**閲覧 → 展開 → 不要画像削除 → 再圧縮 → 元ファイル整理**

という作業を、

**閲覧 → 不要画像を削除指定 → 閲覧継続 → 離脱時にまとめて更新**

へ短縮することを主要目的とする。

## 2. 想定環境・規模

- Windows専用
- アーカイブ数：**10,000ファイル以上**
- 複数フォルダを横断して管理
- ローカルドライブを主対象とする
- NAS・ネットワークドライブも考慮する
- 1アーカイブ内に数十～数百枚程度の画像を想定
- アーカイブ一覧表示時にはZIP本体を原則として読み込まない

大量のファイルを扱うため、単純なフォルダ型ビューアではなく**ライブラリ型管理方式**を採用する。

## 3. 基本構造

アプリケーションでは以下の3階層を扱う。

```text
Library
 ├ Folder
 │   ├ D:\Archives
 │   ├ E:\Books
 │   └ \\NAS\Images
 │
 └ Archive
     ├ book001.zip
     │   ├ 001.jpg
     │   ├ 002.jpg
     │   └ 003.jpg
     │
     └ book002.zip
```

### 3.1 Library

複数の管理対象フォルダを統合した論理的なライブラリ。

### 3.2 Archive

ZIP等の画像アーカイブ。

### 3.3 Image

アーカイブ内部の画像ファイル。

## 4. ライブラリ管理

### 4.1 管理フォルダ

複数フォルダをライブラリへ登録できる。

例：

```text
D:\Images
E:\Archive
\\NAS01\Books
```

登録フォルダ内をスキャンし、対応するアーカイブをライブラリへ登録する。

### 4.2 インデックス

10,000以上のアーカイブを想定するため、ライブラリ情報はSQLiteで管理する。

主な管理項目：

- Archive ID
- フルパス
- ファイル名
- 拡張子
- ファイルサイズ
- 更新日時
- 画像枚数
- サムネイル情報
- 最終閲覧位置
- 最終閲覧日時

## 5. アーカイブ一覧

登録された複数フォルダのアーカイブを、保存場所を意識せず横断表示する。

### 5.1 サムネイル表示

代表画像を表紙としてグリッド表示する。

### 5.2 詳細表示

- ファイル名
- 保存場所
- 画像枚数
- ファイルサイズ
- 更新日時

などを一覧表示する。

### 5.3 アーカイブ操作

一覧から以下を実行できる。

- 開く
- 削除
- 名前変更
- 別フォルダへの移動
- エクスプローラーで表示

## 6. サムネイルキャッシュ

アーカイブ一覧を高速表示するため、表紙画像のサムネイルをローカルキャッシュする。

サムネイルはファイルパスではなく**Archive ID**に関連付ける。

例：

```text
Archive ID : 12345
        ↓
Thumbnail
archive-12345.jpg
```

これにより、アプリ内でアーカイブを移動・リネームしてもキャッシュを維持する。

一覧表示時には原則としてZIP本体を開かず、**SQLite → サムネイルキャッシュ**のみで表示できる構造とする。

## 7. 画像ビューア

アーカイブを開くと内部画像を閲覧できる。

MVPでは次を実装する。

- 前ページ
- 次ページ
- 拡大・縮小
- ウィンドウフィット
- 原寸表示
- 全画面表示
- キーボード操作

将来機能：

- 見開き
- 右綴じ・左綴じ
- サムネイルページ一覧

## 8. 画像の削除予約

表示中の画像をDelete等で削除対象に指定できる。

ただし、**Deleteした時点ではZIPを書き換えない。**

例：

```text
001.jpg
002.jpg
003.jpg  ← Delete
004.jpg
005.jpg
017.jpg  ← Delete
...
```

内部では、

```text
削除予約
 ├ 003.jpg
 └ 017.jpg
```

として管理する。

削除予約された画像は閲覧対象から除外し、ユーザーからは削除済みと同様に扱う。

実ファイルへの反映前であれば、予約解除も可能な構造とする。

## 9. アーカイブ離脱時の変更確定

以下の操作を**アーカイブからの離脱**と定義する。

- 別アーカイブを開く
- ライブラリ一覧へ戻る
- アプリケーションを終了する

未確定の変更が存在する場合、確認ダイアログを表示して変更を確定する。MVPでは設定画面を持たないため、確認は常にONとする。

### 9.1 確認ON

例：

> 5枚の画像が削除対象になっています。  
> アーカイブを更新しますか？
>
> **更新する / 変更を破棄 / キャンセル**

- **更新する:** 変更をアーカイブへ反映して離脱する。
- **変更を破棄:** 削除予約等を破棄し、元ZIPを変更せず離脱する。
- **キャンセル:** 離脱そのものを中止してビューアへ戻る。

### 9.2 確認OFF（v0.2.0）

設定画面で確認をOFFにした場合は、確認ダイアログを表示せず、自動的に変更を確定（アーカイブを更新）して離脱する。既定はONとする。詳細は 24.3。

## 10. アーカイブの安全な更新

変更確定時には元ZIPを直接破壊的に変更しない。

基本処理：

```text
original.zip
     ↓
変更内容を反映した temporary.zip を作成
     ↓
temporary.zip の作成・正常性確認
     ↓
original.zip を退避
     ↓
temporary.zip → original.zip
     ↓
SQLite更新
```

途中で処理に失敗した場合、可能な限り元アーカイブを保持する。

## 11. 更新前アーカイブの保持

アーカイブを再構築する場合、**更新前の元アーカイブは可能な限りWindowsのごみ箱へ退避する。**

これをMVPにおける簡易的な復旧手段とする。

アプリ独自の以下の機能はMVPでは実装しない。

- バージョン管理
- バックアップ世代管理
- 更新後Undo

ネットワークドライブなど、Windowsのごみ箱を利用できない保存先では、次のとおり扱う。

- アーカイブ自体の削除：ユーザーへ確認のうえ、選択された場合のみ完全削除する。キャンセル時は何も変更しない。
- ZIP再構築：元ZIPを退避できないため更新を中止し、元ZIPと削除予約を保持する。

## 12. 操作結果通知

ファイルやアーカイブに対する操作完了後、**アプリ内トースト通知**を表示する。

例：

> ✓ 5枚の画像を削除しました

> ✓ ABC.zip を移動しました

> ✓ ファイル名を変更しました

> ⚠ アーカイブの更新に失敗しました

トーストは一定時間経過後に自動的に消える。

**離脱時の確認ダイアログを無効にしている場合でも、操作結果通知は表示する。**

「確認」と「結果通知」は独立した機能として扱う。

## 13. 操作履歴

### 13.1 MVP

**操作履歴の記録処理はMVPから実装する。**

ファイルを変更する主要操作について、結果をSQLiteへ記録する。

対象：

- アーカイブ内画像削除
- アーカイブ更新
- アーカイブ削除
- アーカイブ移動
- アーカイブ名変更
- 処理失敗

想定項目：

```text
operation_history

id
archive_id
operation_type
executed_at
old_path
new_path
affected_count
status
message
```

例：

```text
2026-11-06 09:52:31
Operation : IMAGE_DELETE
Archive   : ABC.zip
ArchiveId : 12345
Count     : 5
Result    : SUCCESS
Message   : 5枚の画像を削除しました
```

トースト通知と履歴記録では、可能な限り同一の操作結果データを利用する。

```text
ファイル操作
     ↓
OperationResult
     ├── トースト通知
     └── SQLite履歴記録
```

### 13.2 将来仕様

操作履歴を閲覧する専用UIを追加する。

想定機能：

- 時系列表示
- 操作内容
- 対象アーカイブ
- 実行日時
- 成功／失敗
- ファイル移動元／移動先
- 削除画像数
- 種類による絞り込み

通知一覧のようなUIで、後から「昨日このZIPに何をしたか」を確認できるようにする。

**履歴データ自体はMVPから存在するため、履歴画面実装前の操作についても将来参照可能とする。**

## 14. アーカイブ自体の管理

ライブラリから以下を実行できる。

### 14.1 削除

可能な場合はWindowsのごみ箱へ移動する。

### 14.2 名前変更

実ファイルを変更し、SQLiteも同時に更新する。

### 14.3 移動

別の管理対象フォルダなどへ移動し、SQLiteを更新する。

## 15. ファイル同一性

各アーカイブにアプリ固有のArchive IDを割り当てる。

```text
archive_id = 12345
```

アプリ内で、

```text
D:\Books\AAA.zip
      ↓ rename
D:\Books\BBB.zip
      ↓ move
E:\Archive\BBB.zip
      ↓ 内部画像削除
E:\Archive\BBB.zip
```

となっても、`archive_id = 12345`を維持する。

これにより、以下の情報を継続して関連付けられる。

- サムネイル
- 最終閲覧位置
- 操作履歴

## 16. アプリ外での変更

エクスプローラー等による外部変更の完全追跡は保証しない。

### 16.1 同名ファイルが別の管理フォルダへ移動

移動の可能性があるものとして扱う余地を持たせる。

### 16.2 名前まで変更

原則として新規アーカイブとして登録する。

高度なハッシュ照合やコンテンツフィンガープリントによる同一性判定はMVPでは実装しない。

## 17. ライブラリスキャン

### 17.1 初回

登録フォルダをフルスキャンする。

### 17.2 2回目以降

SQLite内の以下の情報を利用して差分を検出する。

- Path
- Size
- LastWriteTime

変更のないアーカイブは極力読み込まない。

### 17.3 アプリ自身による変更

再スキャンを待たずSQLiteを即時更新する。

## 18. 検索・ソート

### 18.1 検索

- ファイル名部分一致

### 18.2 ソート

- ファイル名
- 更新日時
- ファイルサイズ
- 画像枚数

将来的には保存場所等によるフィルターも検討する。

## 19. 対応形式

MVPでは範囲を限定する。

### 19.1 アーカイブ
- ZIP
- CBZ
- RAR / CBR（閲覧だけ。v0.2.0 の後に追加した。GitHub の Issue #3）
- 7z / CB7（閲覧だけ。同上）

RAR / 7z は、画像の削除（アーカイブの作り直し）を行わない。RAR は書き込みの形式が公開されていないため、7z も含めて、編集したい場合は ZIP に変換して扱う。変換は、ライブラリの右クリックメニューと、ビューアのツールバーから行える（GitHub の Issue #20）。変換では、全部のエントリ（画像以外のファイルとフォルダを含む）を同じ名前で写し、閲覧位置とサムネイルを引き継ぎ、元のファイルはごみ箱へ移す（ごみ箱を使えない保存先では残す）。アーカイブ自体の名前変更・移動・削除は、ZIP と同じく行える。形式は、拡張子ではなく、ファイルの中身（先頭の署名）で判定する（「.cbr」という名前の ZIP などがあるため）。

### 19.2 画像

- JPEG
- PNG

MVPでは標準的かつ実装負荷の低いJPEG / PNGに対応範囲を限定する。

### 19.3 将来対応形式

- WebP
- GIF等のその他画像形式
- RAR / 7z 以外の追加アーカイブ形式（TAR / CBT など。GitHub の Issue #21）

追加形式については、MVP完成後に必要性と実装負荷を評価して拡張する。

## 20. パフォーマンス要件

10,000以上のアーカイブを日常的に扱うことを前提とする。

基本方針：

- SQLiteによるライブラリインデックス
- サムネイルキャッシュ

- アーカイブ内部情報のオンデマンド取得
- 表示画像前後のみプリロード
- バックグラウンドスキャン
- ZIP再構築の非同期処理

## 23. 主要操作フロー

```text
見る
 ↓
不要な画像をDelete
 ↓
削除予約だけ行い、そのまま閲覧継続
 ↓
別アーカイブ等へ移動
 ↓
必要なら変更確認
 ↓
ZIPを1回だけ再構築
 ↓
旧ZIPをごみ箱へ退避
 ↓
新ZIPへ置換
 ↓
SQLite更新＋操作履歴保存
 ↓
「5枚の画像を削除しました」トースト
```

本アプリでは、**対応形式の多さよりも、閲覧とファイル管理が直結した操作性を優先する。**

## 24. v0.2.0 で追加する機能

MVP（v0.1.0）の公開後、次の版（v0.2.0）で追加する。上記の各章と異なる場合は、本章を優先する。

### 24.1 設定画面

- ライブラリ画面の左下（「管理対象から外す」の下）の「設定」から、別のウィンドウで開く。ビューアの表示中は開けない
- 変更は、その場で反映し、保存する（「OK / キャンセル」はない）
- 設定は、アプリのデータの保存先（`%LOCALAPPDATA%\K35Viewer\`）の設定ファイルに保存する。ファイルが壊れていて読めない場合は、既定値で起動し、そのことを通知する

### 24.2 外観

- ダーク（既定）/ ライト / Windowsの設定に合わせる、から選ぶ
- 選ぶと、再起動せずに、その場で切り替わる

### 24.3 確認

- **アーカイブから離れるときの確認**（9章。既定はON）
  - OFFの場合、削除予約があれば、確認せずにアーカイブを更新して離れる（アプリの終了時も同じ）。更新前のアーカイブは、ONのときと同じくごみ箱へ退避する
  - 更新できない場合（外部で変更された、ごみ箱を使えない保存先など）は、OFFでも確認ダイアログを表示する（「更新する」は選べず、「変更を破棄」か「キャンセル」を選ぶ）
- **アーカイブの削除の確認**（14.1。既定はON）
  - OFFの場合、アーカイブを確認せずにごみ箱へ移す
  - ごみ箱を使えない保存先での**完全削除の確認は、OFFでも必ず表示する**（元に戻せないため）

### 24.4 表示方式の記憶

- ライブラリ画面の表示方式（詳細 / サムネイル）と、ビューアの表示方式（1枚 / 一覧）を記憶し、次に起動したときも同じ表示方式で始める
- 設定画面の項目にはせず、常に記憶する（切り替えた時点で保存する）

### 24.5 データ（保存場所、サムネイルのキャッシュ、バックアップと復元）

- **保存場所**: アプリのデータの保存先と、サムネイルのキャッシュの保存先を表示し、それぞれエクスプローラーで開ける
- **サムネイルのキャッシュの削除**: キャッシュの大きさを表示し、削除できる。削除したサムネイルは、順に作り直す。スキャン中・作成中は実行できない
- **バックアップ**: アプリのデータ（ライブラリの情報、閲覧位置、操作履歴、設定）を、1つのファイルにまとめて保存する
  - サムネイルのキャッシュとログは含めない（キャッシュは作り直せるため）
  - 保存先は、アプリのデータの保存先の `backups` フォルダとし、エクスプローラーで開ける。利用者は、このファイルを別の場所へコピーして保管できる
  - アプリの更新の前には、自動でバックアップを作る（24.6）。自動で作ったバックアップは、新しいものから決まった数だけ残す（既定は5。設定画面で1〜20に変えられる）。利用者が作ったものは、自動では削除しない。データの元はアーカイブの実ファイルで、バックアップに入るのは、そこから作れない記録（閲覧位置、操作履歴、設定など）のため、多くの世代は要らない
- **復元**: バックアップのファイルを選んで、アプリのデータをその時点に戻す
  - 確認のうえ、アプリを再起動して戻す。戻す前に、その時点のデータも自動でバックアップする
  - 今のアプリより新しい版で作ったバックアップ（DBの形が新しいもの）は、復元できない
  - 復元したあとは、サムネイルを作り直す

### 24.6 アプリの更新

- 設定画面の「更新を確認」で、GitHub のリリースに新しい版があるかを確かめる。**ボタンを押したときだけ**通信する（起動時に自動では確かめない）
- 新しい版があれば、版の番号と、変更点（リリースノート）へのリンクを表示する。試用版（Pre-release）も対象にする
- 「更新する」で、次の順に行う
  1. アプリのデータを自動でバックアップする（24.5）
  2. 新しい版の配布物（ZIP）をダウンロードし、改ざん・破損がないことをハッシュ（SHA-256）で確かめる
  3. 確認のうえアプリを終了し、アプリのフォルダの中身を新しい版に入れ替えて、新しい版を起動する
- アプリのフォルダに書き込めない場合（`C:\Program Files` の中など）や、ダウンロード・確認に失敗した場合は、入れ替えず、リリースのページを開けるようにする
- 入れ替えに失敗した場合は、元の版に戻す
- 新しい版が、DBの形を新しくした場合、古い版には戻せない。そのときは、更新の前のバックアップを使う
- **プライバシー**: 更新の確認とダウンロードで、GitHub（`api.github.com`、`github.com`）と通信する。送るのは、通常のHTTPSの要求だけで、利用者のデータは送らない。README とコード署名ポリシーのプライバシーの記述にも、このことを書く

### 24.7 v0.2.0 でも対象外とするもの

- サムネイルのキャッシュの保存先の移動
- 更新前のZIPの退避方法の選択（ごみ箱以外）
- キー割り当ての変更
- 起動時の、更新の自動確認
- 画像なし・破損のアーカイブの表示の切り替え（ユースケース定義書 8.1）
