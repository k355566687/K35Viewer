# 画像アーカイブ管理ビューア 内部アーキテクチャ設計書

**文書バージョン:** Ver.0.2.14（35章 v0.2.0 Phase 13 バックアップを追加。Ver.0.2.13: 34章 v0.2.0 Phase 12 確認のオン/オフ・サムネイルのキャッシュの削除を追加。Ver.0.2.12: 33章 v0.2.0 Phase 11 設定画面・外観・表示方式の記憶を追加。Ver.0.2.11: 25.4 に、一覧の取得中に届いた作成結果の扱いを追加）

**対象:** MVP

## 1. 目的

本書は、画像アーカイブ管理ビューアのMVPを実装するための内部アーキテクチャを定義する。

主な目的は次のとおり。

- UIとファイル操作を分離する
- ZIP更新、SQLite、サムネイル生成等の責務を明確にする
- 長時間処理をバックグラウンドで安全に実行する
- ファイル操作成功後にのみDBを更新する
- 将来の追加形式対応や画面追加を妨げない構造とする
- MVPで必要以上の抽象化を行わない

## 2. 前提技術

- 言語: C#
- ランタイム: .NET 10
- UI: WPF
- DB: SQLite
- アーカイブ: ZIP / CBZ
- 画像: JPEG / PNG
- ZIP基本操作: `System.IO.Compression`
- 非同期処理: `async` / `await` とキャンセルトークンを基本とする

## 3. 全体構成

MVPでは、論理的に次の4層へ分離する。

```text
Presentation
  Library / Viewer / Dialog / Toast
          |
          v
Application
  Use Case / Service / Session
          |
          v
Domain
  Archive / Folder / OperationResult 等
          |
          v
Infrastructure
  SQLite / ZIP / FileSystem / RecycleBin / ThumbnailCache
```

依存方向は原則として上から下とする。

UIからSQLiteやZIPを直接操作しない。

## 4. Presentation層

### 4.1 役割

- ライブラリ画面の表示とユーザー操作受付
- ビューアの1枚表示・一覧表示
- 確認ダイアログ
- トースト通知
- ViewModelと画面状態の管理

### 4.2 View

MVPでは主に次を持つ。

- `MainWindow`
- `LibraryView`
- `ViewerView`
- `ArchiveChangeConfirmDialog`
- `ArchiveDeleteConfirmDialog`
- `ToastHost`

ライブラリとビューアは別ウィンドウではなく、`MainWindow` 内で切り替える。

### 4.3 ViewModel

#### MainViewModel

- 現在表示する画面の切替
- 全体的なナビゲーション
- 長時間処理状態の連携

#### LibraryViewModel

- フォルダツリー
- アーカイブ一覧
- 検索条件
- ソート条件
- 表示モード
- フォルダ追加
- 再スキャン
- アーカイブの移動、名前変更、削除

#### ViewerViewModel

- 現在のArchive ID
- 現在画像
- 画像一覧
- 現在位置
- 1枚表示 / 一覧表示切替
- 選択状態
- 削除予約
- 拡大・縮小等の表示状態

### 4.4 UIルール

- ViewModelから直接 `File.*`、`Directory.*`、SQLite等を呼ばない。
- ユーザー操作はApplication層のサービスへ依頼する。
- ViewModelは処理結果 `OperationResult` を受け取り、画面状態へ反映する。
- トースト表示は共通の通知サービス経由とする。

## 5. Application層

画面から呼ばれるユースケースを実装する。

### 5.1 LibraryService

ライブラリに関する操作の窓口。

主な責務:

- 登録フォルダ追加
- フォルダツリー取得
- アーカイブ一覧検索
- 検索・ソート条件に応じた一覧取得
- アーカイブを開くための情報取得

想定インターフェース例:

```csharp
Task AddFolderAsync(string path, CancellationToken ct);
Task<IReadOnlyList<FolderNode>> GetFolderTreeAsync(CancellationToken ct);
Task<PagedResult<ArchiveSummary>> QueryArchivesAsync(
    ArchiveQuery query,
    CancellationToken ct);
```

### 5.2 ScanService

フォルダスキャンと差分更新を担当する。

主な責務:

- 初回スキャン
- 手動再スキャン
- 起動時更新チェック
- 登録フォルダ、サブフォルダ、ZIP / CBZの列挙
- Path、Size、LastWriteTimeを用いた差分判定
- 新規・変更・不在項目の反映
- `scan_runs` の開始・終了記録
- 差分があるアーカイブの解析要求

スキャン中でもライブラリの読み取り操作を可能とする。

### 5.3 ArchiveService

アーカイブ自体のファイル管理を担当する。

主な責務:

- 名前変更
- 移動
- 削除
- ZIP再構築
- 元ファイルの再確認
- ファイル操作成功後のDB更新
- 操作履歴作成

ZIP内部の具体的な読み書きはInfrastructure層へ委譲する。

### 5.4 ViewerService

アーカイブ内部の閲覧に必要な処理を担当する。

主な責務:

- ZIP内画像エントリ一覧取得
- 自然順ソート
- JPEG / PNGの読み込み
- 最終閲覧位置の取得・保存
- 前後画像取得

### 5.5 ViewerSession

現在開いているアーカイブの未確定状態をメモリ上で保持する。

主な状態:

```text
ArchiveId
Entries
CurrentEntry
CurrentIndex
SelectedEntries
PendingDeleteEntries
ViewMode
```

`PendingDeleteEntries` はDBへ保存しない。

アーカイブ離脱時にのみ確定または破棄する。

### 5.6 ThumbnailService

サムネイル生成・取得を担当する。

主な責務:

- ライブラリ用表紙サムネイル取得
- キャッシュ有効性確認
- サムネイル生成
- `STALE` サムネイル再生成
- キャッシュファイル消失時の再生成

一覧スクロールをブロックしないよう、生成はバックグラウンドで実行する。

### 5.7 HistoryService

操作結果を `operation_history` へ記録する。

MVPでは履歴閲覧画面を持たないが、履歴記録は実装する。

開始通知は履歴へ保存せず、確定した最終結果のみ保存する。

### 5.8 NotificationService

アプリ内トースト通知の共通窓口。

```csharp
ShowInfo(message);
ShowSuccess(message);
ShowWarning(message);
ShowError(message);
```

スキャンやZIP更新など時間を要する処理は、開始時と完了時に通知する。

## 6. Domain層

純粋なデータ構造とルールを保持する。

### 6.1 主なモデル

#### LibraryFolder

- Id
- Path
- IsEnabled
- AvailabilityStatus

#### Folder

- Id
- LibraryFolderId
- ParentFolderId
- Name
- FullPath
- RelativePath
- Depth

#### Archive

- Id
- FolderId
- FileName
- Extension
- FileSize
- LastWriteTime
- ImageCount
- LastViewEntry
- LastViewIndex
- AnalysisStatus
- AvailabilityStatus

アーカイブの実パスは `Folder.FullPath + Archive.FileName` から生成する。

#### ArchiveEntry

ZIP内の1エントリを表す。

- Name
- FullName
- Size
- CompressedSize
- LastWriteTime
- IsSupportedImage

#### OperationResult

ファイル操作の結果を共通表現する。

```text
OperationType
Status
ArchiveId
Message
AffectedCount
OldPath
NewPath
ErrorCode
ExecutedAt
```

同じ結果をトースト表示と操作履歴記録に利用する。

`OperationResult` はユーザー向けの確定結果を表し、トースト通知と `operation_history` の共通データとして使用する。例外、スタックトレース、一時ファイルパス、内部処理段階等の開発・障害調査情報は `OperationResult` へ詰め込まず、アプリケーションログへ記録する。

### 6.2 時刻

Unix timeを使用する場合は64bit整数とし、C#では `long` (`Int64`) を使用する。

`int` (`Int32`) へ変換しない。

## 7. Infrastructure層

## 7.1 SQLiteRepository

SQLiteへの永続化を担当する。

Repositoryはテーブル単位に過剰分割せず、MVPでは用途別に次を基本とする。

- `LibraryRepository`
- `ArchiveRepository`
- `HistoryRepository`
- `ScanRepository`
- `ThumbnailRepository`

DB接続設定:

```text
foreign_keys = ON
journal_mode = WAL
synchronous = NORMAL
busy_timeout = 5000
```

書き込み処理はアプリ内で1本の書き込みキューへ集約する。

### 7.2 ArchiveReader

ZIP / CBZの読み取りを担当する。

MVPでは `System.IO.Compression.ZipArchive` を利用する。

主な機能:

- エントリ列挙
- JPEG / PNG判定
- エントリStream取得
- アーカイブ検証

### 7.3 ArchiveWriter

ZIP再構築を担当する。

主な責務:

1. 一時ZIP作成
2. 削除対象以外のエントリをコピー
3. 一時ZIPを閉じる
4. 再オープンして読み取り確認
5. 成否をApplication層へ返す

元ZIPの退避・置換判断は `ArchiveService` が統括する。

### 7.4 FileSystemService

Windowsファイルシステム操作を集約する。

主な機能:

- ファイル・フォルダ存在確認
- ディレクトリ列挙
- ファイル情報取得
- 名前変更
- 移動
- エクスプローラーで対象表示
- 一時ファイル名生成

ViewModelやRepositoryから直接ファイル操作しない。

### 7.5 RecycleBinService

Windowsのごみ箱への移動を担当する。

用途:

- アーカイブ削除
- ZIP再構築時の更新前ZIP退避

ごみ箱を利用できない保存先の場合は `RECYCLE_BIN_UNAVAILABLE` を返し、自動的な完全削除へは切り替えない。

- アーカイブ削除：UIが確認ダイアログを表示し、ユーザーが承認した場合のみ、`ArchiveService` が完全削除を明示的に要求する。
- ZIP再構築：更新を中止し、元ZIPと削除予約を保持する。

### 7.6 ThumbnailCacheStore

サムネイルファイルの保存・取得・削除を担当する。

DBの `thumbnail_cache` はメタデータを保持し、画像実体はキャッシュディレクトリへ保存する。

## 8. 依存関係

代表的な処理の依存関係は次のとおり。

```text
LibraryViewModel
    -> LibraryService
        -> LibraryRepository
        -> ScanService

ViewerViewModel
    -> ViewerService
        -> ArchiveReader
        -> ArchiveRepository

ViewerViewModel
    -> ArchiveService
        -> ArchiveWriter
        -> FileSystemService
        -> RecycleBinService
        -> ArchiveRepository
        -> HistoryService
        -> NotificationService
```

`ArchiveWriter` からSQLiteを操作しない。

`ArchiveRepository` からファイルを操作しない。

## 9. ZIP閲覧フロー

```text
ユーザーがアーカイブを開く
        |
        v
LibraryViewModel
        |
        v
ViewerService
        |
        +--> ArchiveRepository からArchive取得
        |
        +--> Folder情報から実パス生成
        |
        +--> ArchiveReaderで画像一覧取得
        |
        v
ViewerSession生成
        |
        v
ViewerViewModelへ表示
```

画像データは全件を同時展開せず、現在画像と前後の必要数のみ読み込む。

## 10. 削除予約フロー

```text
Delete
  |
  v
ViewerViewModel
  |
  v
ViewerSession.PendingDeleteEntriesへ追加
  |
  +--> 画面から通常画像として除外
  |
  +--> 削除予定件数を更新
```

この時点ではZIP、SQLite、操作履歴を変更しない。

一覧表示で複数選択された場合も同じ `PendingDeleteEntries` を利用する。

## 11. アーカイブ更新フロー

アーカイブ離脱時に削除予約が存在し、「更新する」が選択された場合の処理。

```text
ViewerViewModel
    |
    v
ArchiveService
    |
    +--> 更新開始トースト
    |
    +--> 元ファイルの存在・Size・LastWriteTime確認
    |
    +--> ArchiveWriterで一時ZIP作成
    |
    +--> 一時ZIP検証
    |
    +--> RecycleBinServiceで元ZIP退避
    |
    +--> FileSystemServiceで一時ZIPを正規名へ変更
    |
    +--> DB書き込みトランザクション
    |      + archives更新
    |      + thumbnail_cacheをSTALE化
    |      + operation_history追加
    |
    +--> 完了トースト
    |
    +--> ThumbnailServiceへ再生成要求
    v
離脱を継続
```

### 11.1 失敗時

- 元ZIPをごみ箱へ移す前の失敗では元ZIPを保持する。
- 一時ZIPは可能なら削除する。
- 元ZIP退避後の失敗は復旧に必要なパスをエラー結果へ含める。
- DB更新前に実ファイル操作が失敗した場合、DBは更新しない。
- DB更新のみ失敗した場合、次回スキャンにより実ファイルから再同期可能とする。

## 12. スキャンフロー

```text
起動 / フォルダ追加 / 再スキャン
        |
        v
ScanService
        |
        +--> 開始トースト
        +--> scan_runs作成
        +--> FileSystemServiceで再帰列挙
        +--> LibraryRepositoryと差分比較
        +--> 新規Archive登録
        +--> 変更Archive解析
        +--> 不在判定
        +--> Folderツリー更新
        +--> scan_runs完了
        +--> operation_history記録
        +--> 完了トースト
```

起動時チェックはライブラリ画面表示後に開始し、通常の閲覧・検索をブロックしない。

## 13. 並行処理

MVPでは複雑な並列実行を避け、次のルールとする。

### 13.1 DB

- 読み取りは必要に応じて並行可能
- 書き込みは単一キューへ直列化

### 13.2 同一アーカイブ

同じArchive IDに対する破壊的操作は同時実行しない。

例:

- 再構築中の名前変更は禁止
- 移動中の削除は禁止
- 更新中の再更新は禁止

### 13.3 スキャンとの競合

MVPでは高度なロック、世代管理、競合解決機構は実装しない。

スキャン結果をSQLiteへ反映する直前に、対象ファイルの存在、Size、LastWriteTimeを再取得する。スキャン開始時または解析時に取得した値と異なる場合、そのファイルのスキャン結果は破棄し、次回の起動時更新チェックまたは再スキャンの対象とする。

アプリ内のファイル操作が成功した場合は、その操作結果によるDB更新を優先する。スキャン側は確認済みの古い情報で上書きしない。

## 14. キャンセル方針

### キャンセル可能

- フォルダスキャン
- 起動時差分チェック
- サムネイル生成待ち

### ZIP更新のキャンセル境界

次の処理まではキャンセル可能とする。

- 一時ZIP生成
- 一時ZIPの検証

元ZIPをごみ箱へ退避する処理を開始した時点を安全境界とし、それ以降はキャンセル不可とする。

安全境界を越えた後は、新ZIPへの置換、DB更新、履歴記録まで処理を最後まで完了させる。これにより、元ZIPのみがごみ箱にあり、一時ZIPだけが残る中途半端な状態を避ける。

## 15. エラー処理

Application層のサービスは、ユーザー操作で想定される失敗を例外のままUIへ投げず、原則 `OperationResult` 等へ変換する。

例:

- `FILE_NOT_FOUND`
- `ACCESS_DENIED`
- `DISK_FULL`
- `ARCHIVE_BROKEN`
- `ARCHIVE_CHANGED_EXTERNALLY`
- `RECYCLE_BIN_UNAVAILABLE`
- `TARGET_ALREADY_EXISTS`
- `DATABASE_ERROR`

予期しない例外は共通例外ハンドラで捕捉し、ログへ記録する。

## 16. ログ

操作履歴と開発・障害調査ログは分離する。

### 操作履歴

ユーザーが後日確認する対象。

- ZIP更新
- 名前変更
- 移動
- 削除
- スキャン最終結果

SQLiteの `operation_history` へ保存する。

### アプリケーションログ

障害調査用。

- 例外
- スタックトレース
- SQLiteエラー
- ZIP処理エラー
- スキャン詳細

アプリケーションログの記録はMVPから実装し、ローカルログファイルへ保存する。ログ閲覧画面はMVP対象外とし、将来仕様とする。

最低限、日時、ログレベル、処理名、Archive ID、対象パス、エラーコード、例外メッセージ、スタックトレースを記録できる構造とする。保存形式、保存期間、最大ファイルサイズおよびローテーション方式は実装設計で確定する。

## 17. DIと生成管理

各Service、Repository、Infrastructure依存はコンストラクタ注入を基本とする。

例:

```csharp
ArchiveService(
    IArchiveWriter archiveWriter,
    IFileSystemService fileSystem,
    IRecycleBinService recycleBin,
    IArchiveRepository archiveRepository,
    IHistoryService historyService)
```

ただしMVPではインターフェースを無制限に作らず、次の条件に該当する境界を優先して抽象化する。

- OSや外部資源に依存する
- 単体テストで置き換えたい
- 将来実装を差し替える可能性が高い

例:

- FileSystem
- RecycleBin
- ZIP Reader / Writer
- SQLite Repository
- Notification

## 18. ソリューション構成案

MVPではプロジェクトを細分化しすぎず、まず2プロジェクト構成を推奨する。

```text
K35Viewer.sln

K35Viewer.App
  Views/
  ViewModels/
  Services/
  Domain/
  Infrastructure/

K35Viewer.Tests
  Services/
  Infrastructure/
```

規模が大きくなった時点で、必要に応じてCore / Infrastructure等へ分割する。

フォルダ分離だけでも層の依存関係は維持する。

## 19. MVPのテスト重点箇所

特に次を自動テストまたは結合テスト対象とする。

1. ZIP内画像の自然順ソート
2. JPEG / PNGエントリ抽出
3. 削除予約状態の追加・解除
4. 複数削除を1回のZIP再構築で反映
5. 再構築失敗時に元ZIPが残ること
6. 外部変更されたZIPを上書きしないこと
7. 名前変更後もArchive IDが維持されること
8. フォルダ移動後も配下Archiveのパスを正しく組み立てられること
9. 起動時差分チェックでNASアクセス不能を削除扱いしないこと
10. SQLiteの64bit時刻が2038年以降でも扱えること

- RAR / 7z
- WebP / GIF
- PDF
- 動画
- Susie Plug-in
- 操作履歴閲覧画面
- 設定画面
- 更新確定後のアプリ独自Undo
- 高度な重複検出
- ファイル内容による高度な同一性追跡
- 複数端末間のDB共有

## 21. レビュー結果

1. `ViewerService` と `ArchiveService` の責務境界は現案を採用する。
2. `ViewerSession` はViewModel内部ではなくApplication層の状態として保持する。
3. ZIP再構築時の元ZIP退避と新ZIP置換は `ArchiveService` が統括する。
4. DB書き込みは単一キューへ集約し、直列化する。
5. スキャンとアプリ内操作の競合は、MVPではSizeとLastWriteTimeの書き込み直前再確認による簡易対応とする。高度なロックや世代管理は実装しない。
6. サムネイル再生成はZIP更新完了後に非同期実行する。
7. アプリケーションログの記録はMVPから実装する。ログ閲覧画面は将来仕様とする。
8. 2プロジェクト構成で開始し、必要になるまでCore / Infrastructureを別プロジェクト化しない。
9. `OperationResult` はトースト通知と操作履歴の共通データとして使用する。開発・障害調査情報はアプリケーションログへ分離する。
10. ZIP更新は、一時ZIP生成および検証まではキャンセル可能とし、元ZIPのごみ箱退避開始後はキャンセル不可とする。

## 22. Ver.0.2で確定したMVP方針

- 層およびサービスの責務境界はVer.0.1の案を採用する。
- スキャン競合は簡易再確認方式とし、過剰な競合制御を実装しない。
- 操作履歴とアプリケーションログを分離し、両方の記録をMVPから実装する。
- ログ閲覧UIは将来実装とする。
- ZIP更新処理には明確なキャンセル安全境界を設ける。

## 23. Ver.0.2.1で確定した実装方針（Phase 2 フォルダ追加・スキャン）

実装を通じて、次の方針を確定した。上記の各章と異なる場合は、本章を優先する。

### 23.1 DB書き込みキュー

- 書き込みは `DatabaseWriter` を必ず経由し、アプリ内で1つずつ（直列に）実行する。1回の呼び出しが1トランザクションになり、例外時はロールバックする
- 読み取りは `SqliteConnectionFactory` から各自で接続を開いて並行に行う（WALのため書き込みと衝突しない）
- Repositoryの書き込みメソッドは、呼び出し元のトランザクション内で実行する。複数テーブルにまたがる更新（管理フォルダ追加時のフォルダ統合等）を1トランザクションにまとめるため

### 23.2 LibraryServiceとScanServiceの関係

8章の依存関係図では `LibraryService` が `ScanService` を呼ぶ構成だったが、次のとおり変更する。

- `LibraryService.AddFolderAsync` は登録（と親フォルダ追加時の統合）だけを行い、スキャンは実行しない
- 登録に成功（`Added`）した場合、呼び出し側（`LibraryViewModel`）が `ScanService` を起動する。スキャンを待たずにUIを操作できる状態にするため、また登録とスキャンを個別にテストできるようにするため

### 23.3 スキャンの2段階処理

`ScanService` は次の2段階で処理する。詳細な反映規則はDB設計書 11.7を参照。

1. ファイル列挙: `FileSystemService` が書き込みなしで実行する。キャンセル可能
2. 差分反映: 書き込みキュー経由の1トランザクション。`scan_runs` の完了も同じトランザクションで行う

### 23.4 アクセスできない範囲の扱い

13.3の「書き込み直前の簡易再確認」に加え、次を原則とする（テスト重点箇所9の具体化）。

- 読み取れなかったフォルダと、その配下の既存登録は、不在判定の対象外とする
- 登録フォルダ自体にアクセスできない場合は、配下を変更せずスキャンを失敗として終了する
- 再確認（サイズ・更新日時）は、新規・変更として書き込むファイルだけを対象とする（変更のないファイルは再取得しない）

### 23.5 スキャンに含めない処理

スキャンは、ZIPの内容を読む処理（画像枚数、表紙画像の特定、サムネイル生成）を含まない。新規・変更のアーカイブは `analysis_status = PENDING` で登録し、解析とサムネイル生成はPhase 4以降で行う。

### 23.6 通知・履歴

- `NotificationService` はイベントで通知を発行する。バックグラウンドスレッドから呼ばれるため、購読側（トースト表示）でUIスレッドへ切り替える
- スキャンの最終結果は、キャンセル・失敗の場合も `operation_history` へ記録する。このときの書き込みは、呼び出し元のキャンセルトークンに従わない（キャンセル済みでも履歴を残すため）
- 履歴の `operation_type` は、スキャンの種別（`INITIAL` / `MANUAL` / `STARTUP`）に応じて `SCAN_INITIAL` / `SCAN_MANUAL` / `SCAN_STARTUP` とする

## 24. Ver.0.2.2で確定した実装方針（Phase 3 ライブラリ画面）

上記の各章と異なる場合は、本章を優先する。

### 24.1 ScanServiceの全体スキャン

- `ScanAsync(libraryFolderId, scanType)`: 管理フォルダ1件を対象とする（フォルダ追加直後の初回スキャン）
- `ScanAllAsync(scanType)`: 有効なすべての管理フォルダを、1回のスキャンとして実行する（再スキャン・起動時チェック）。対象がなければ何もせず `null` を返し、通知も履歴も出さない
- 全体スキャンでも、開始・完了のトーストと `scan_runs`・`operation_history` は1回分だけ作る。件数は全管理フォルダの合計とする（DB設計書 11.7）
- スキャンは同時に1つだけ実行する。実行中に別のスキャンが要求された場合は、先のスキャンの完了を待ってから開始する（起動時チェック中にフォルダを追加した場合等）

### 24.2 LibraryServiceの検索API

5.1の想定インターフェースに合わせ、次を提供する。

```csharp
Task<PagedResult<ArchiveSummary>> QueryArchivesAsync(ArchiveQuery query, CancellationToken ct);
Task<IReadOnlyList<FolderNode>> GetFolderTreeAsync(CancellationToken ct);
```

- `ArchiveQuery` は、フォルダ（任意）、検索語、並べ替え項目、昇順/降順、Offset / Limit（任意）を持つ。クエリの規則はDB設計書 11.8
- `GetFolderTreeAsync` は、登録フォルダを起点とするツリーを返す。起点はフルパス、配下はフォルダ名を持つ（画面の表示は、起点もフォルダ名だけ。32.1）。同階層は名前順（大文字小文字を区別しない）に並べる。見つからなくなったフォルダは配下ごと含めない。登録フォルダに接続できない場合は起点を残し、接続なしとして示す

### 24.3 ライブラリ画面（LibraryViewModel）

- **一覧**: 現時点では詳細表示（列表示）のみ。サムネイル表示はPhase 4で追加する
- **一覧の取得**: 現時点では取得範囲を指定せず、条件に一致する全件を取得する（1万件でも約70ms以下）。`ListView` の仮想化により、画面に見える行だけが生成される（1万件を渡しても生成される行は約30件）。ページングが必要になった場合は、`ArchiveQuery` の Offset / Limit を使う
- **一覧の差し替え**: 項目ごとの変更通知を避けるため、検索のたびに一覧を丸ごと差し替える。表示用の文字列（サイズ、日時の書式）は、画面に表示される行だけがバインド時に組み立てる
- **検索入力**: 入力後250ミリ秒待ってから取得する（デバウンス）。取得が重なった場合は前の取得をキャンセルし、最後の結果だけを反映する
- **フォルダツリー**: スキャン等でツリーを再構築しても、展開状態と選択中のフォルダを維持する。選択中のフォルダがなくなった場合は「すべて」に戻す。新しく登録されたフォルダは展開して表示する
- **起動時チェック（UC-17）**: ライブラリ画面の表示後に、管理フォルダがあれば `ScanAllAsync(Startup)` をバックグラウンドで開始する。完了を待たずに一覧を表示し、チェック中も閲覧・検索できる。完了後に一覧とツリーを読み込み直す
- **再スキャン（UC-16）**: 管理フォルダがない場合、またはスキャン中は実行できない
- **管理フォルダ追加**: 登録に成功したら、ツリーを更新したうえで、初回スキャンを待たずに開始する

### 24.4 UIのテスト

- ViewModelは、ダイアログ（`IDialogService`）を差し替えて、実DBと一時フォルダで検証する
- 一覧の仮想化は、実際のWPFウィンドウに1万件を渡し、生成された行数を数えて確認する（STAスレッドで実行）
- 実際のフォルダ選択ダイアログと、画面の見た目（配色、余白、操作感）は自動テストの対象外であり、手動で確認する

## 25. Ver.0.2.3で確定した実装方針（Phase 4 サムネイル）

上記の各章と異なる場合は、本章を優先する。

### 25.1 構成

| 部品 | 層 | 責務 |
|---|---|---|
| `IArchiveReader` / `ArchiveReader` | Infrastructure | ZIP / CBZ を開き、対応画像の数と表紙候補を返す（`Analyze`）。1エントリをメモリへ読み込む（`ReadEntry`）。破損・暗号化・存在しない等は、例外ではなく解析結果の状態で返す |
| `ThumbnailGenerator` | Infrastructure | 画像データからサムネイル（JPEG）を作る。WPF標準の画像APIだけを使い、どのスレッドからでも呼べる |
| `ThumbnailCacheStore` | Infrastructure | サムネイル画像ファイルの保存・取得・削除。保存は一時ファイル経由で置き換える |
| `ThumbnailRepository` | Infrastructure | `thumbnail_cache` の永続化 |
| `ThumbnailService` | Application | 解析とサムネイル生成の対象選定・実行・DB反映・キャッシュの修復。完了を `ArchiveProcessed` イベントで通知する |
| `ThumbnailImageLoader` | Infrastructure（画面側） | 一覧に表示する画像の遅延読み込みとメモリ上のLRUキャッシュ |
| `NaturalStringComparer` | Domain | 自然順の文字列比較（ビューアの画像順でも使う） |

`ThumbnailService` は5.6のとおりライブラリ用サムネイルを担当する。解析（画像枚数・表紙の特定）も、ZIPを1回開く処理に含めるため、同じサービスで行う。

### 25.2 ZIPを開く場面

- ZIPを開くのは、`ThumbnailService` による解析・生成と、ビューアでの閲覧だけである
- 一覧の表示・検索・並べ替え・スクロール、およびサムネイル画像の表示は、SQLiteの検索結果（サムネイルのファイルの場所と状態を含む）と、キャッシュのファイルだけで行う
- 生成済みのライブラリでは、起動時の確認でもZIPを開かない（サムネイル画像ファイルの存在を確認するだけ）。これはテストで、ZIPを開いた回数を数えて確認している

### 25.3 バックグラウンド処理

- 生成は同時に2件まで行う（CPUとディスク・NASへの負荷を抑える）。実行中に再度要求された場合は、重複して実行せず、終わったあとにもう一度確認する
- 1件の失敗（例外）で全体を止めない。アーカイブが壊れている等は異常ではなく、`BROKEN` 等の状態として記録して先へ進む
- キャンセルすると処理を中断し、処理済みの結果は残る。再開すると、残りから続ける
- 生成の開始契機は、ライブラリ画面の表示後（前回の未処理分）と、スキャンの完了後（新規・変更分）

### 25.4 画面への反映

- 1件の生成が終わるたびに `ArchiveProcessed`（Archive ID、解析状態、画像枚数、サムネイルの場所と状態）を通知する。画面は、表示中の一覧のうち該当する行だけを更新する。一覧を取得し直さないため、スクロール位置が変わらない
- **一覧の取得中に届いた通知**（Ver.0.2.11）: 一覧の取得（DBの検索）と、差し替えの間に作成が終わると、その通知は古い一覧に当たり、新しい一覧は取得した時点の状態（作成待ち）のまま残る。起動時は、更新チェックのスキャンが終わると一覧を取得し直し、同時にサムネイルの作成も動いているため、起こりうる。そこで、取得中に届いた通知を記録しておき、差し替える一覧にも当ててから差し替える。記録と差し替えは、作成スレッドからの通知と競合しないよう、ロックの中で行う（`LibraryViewModel.RefreshArchivesAsync`）。自動テストでは、取得の直後に作成を最後まで行うことで、確実に再現して確かめる
- 画像のメモリ上の保持枚数には上限を設ける（既定400枚）。1万件分を保持するとメモリを使い切るため。画面から外れた画像は破棄し、戻ってきたらキャッシュのファイルから読み直す。読み込みは新しい要求（画面に出た行）を優先する
- 再生成では同じパスの画像ファイルの中身が変わるため、通知を受けた行は、メモリ上の古い画像を破棄して読み直す
- 画像を読み込めなかったファイルは、再生成の通知があるまで再試行しない

### 25.5 サムネイル表示（一覧の表示方式）

- 画面の表示方式は「詳細」と「サムネイル」を切り替える。表示方式は記憶せず、起動のたびに詳細表示から始まる（設定画面はMVP対象外のため）。一覧の項目の選択や、アーカイブを開く操作はPhase 5以降で追加する
- サムネイル表示は、一覧を1行ぶん（横に並ぶ数枚）ずつにまとめ、その行を仮想化する。WPFの標準パネルには、折り返しながら仮想化するものがないため。1行に並べる枚数は、表示領域の幅から決める
- 詳細表示に戻したときは、行のまとまりを破棄する
- 解析できなかったアーカイブは、画像枚数の欄と、サムネイルの枠に状態を表示する（破損、暗号化（非対応）、画像なし、読み込み失敗、表紙を読めません、作成待ち）。色だけに頼らない

### 25.6 スコープ外とした項目

- 画像のEXIFの回転情報は考慮しない（コミック等の用途では影響が小さいため。必要になった場合に評価する）
- 現在表示している行を先に生成する優先制御は行わない（アーカイブID順に処理する）
- 生成の進捗は、ライブラリ画面の右下に件数で表示する（トーストは出さない）

| `MainViewModel` | Presentation | ライブラリ画面とビューア画面の切り替え |

5.4の `ViewerService` の責務のうち、「JPEG / PNGの読み込み」は `PageImageLoader` と `ViewerImageDecoder` が担う。

### 26.2 アーカイブを開いたままにする

- 連続して頁をめくる間、ZIPを開き直さない。開き直すと、毎回エントリ一覧（セントラルディレクトリ）を読むため、NASでは遅延が頁ごとに加わる
- 開くときは、他のプログラムによる読み取り・書き込み・削除・名前変更を妨げない共有モードにする。閲覧中でも、エクスプローラーでの名前変更や移動ができる（開いているファイルへの読み取りは、移動後も続けられる）
- `ZipArchive` は同じストリームからの同時読み取りで壊れるため、読み取りを直列化する。先読みと現在頁の読み込みが同時に走っても安全
- ビューアを閉じる（`ViewerSession.Dispose`）とファイルを手放す。ZIP再構築（Phase 8）では、閲覧のために開いたままのファイルを、更新の前に閉じない。削除（名前変更）を許可する共有モードで開いているため、ごみ箱への移動もできる（実際のごみ箱で確認済み。29.5）
- 閲覧中にファイルが外部で書き換えられた場合の扱いは、29.4

### 26.3 前後の頁の先読みとメモリ

- 現在の頁の前1枚・後2枚だけを保持する（UC-06: 全画像を同時に展開しない）。それより遠い頁は破棄する。戻ったら読み直す
- 破棄した頁の読み込みが途中であれば中止する。先頭から末尾へ飛ぶ操作で、使わない画像の展開を続けない
- 1枚の画像の読み込みは、展開後128MBまで。デコード後の画素数が3,600万画素を超える画像は、デコード時に縮小する（この場合、ズーム倍率は縮小後の画像に対する倍率になる）
- 壊れた画像は、エラーとして保持する（何度も読み直さない）。画面にはエラーを表示し、前後への移動は続けられる
- 測定（2400×3400のJPEG、300頁、約104MB）: ZIPを開いて画像の一覧を作るのに約15ms、最初の頁の表示約110ms、先読み済みの頁送りは中央値0ms。100頁めくっても、メモリ（プライベートバイト）の増加は約28MBで、積み上がらない

### 26.4 位置の移動

- 端では止まる（最後から次へ進んでも、先頭へは戻らない）
- 操作が連続した場合は、最後に要求した頁だけを画面に反映する。途中の頁の読み込みが遅れて届いても、上書きしない
- 削除予約された画像を移動対象から除く処理は、Phase 7で追加した（28.2）

### 26.5 拡大率

- 拡大率は「画像の1画素を画面の何画素で表示するか」で表す。画面の拡大率（DPI）を考慮し、原寸（100%）は画像の1画素＝画面の1画素になる
- **フィット**: ウィンドウに収まる倍率。ただし縮小のみで、小さい画像は拡大しない（拡大してぼかさないため）
- **原寸**: 100%
- **拡大・縮小**: 10%〜800%の段階式（10, 15, 20, 25, 33, 50, 67, 75, 100, 125, 150, 200, 300, 400, 600, 800）。現在の倍率の次の段階へ移る。フィットから操作した場合は、フィット時の倍率の次の段階になる
- 拡大率の設定（フィット / 原寸 / 倍率）は、頁をめくっても保たれる。頁が変わると、左上から表示する
- 表示領域に収まらないときは、ドラッグまたはスクロールバーで移動する。マウスホイールは頁送りに使う（Ctrlを押しながらで拡大・縮小）

### 26.6 閲覧位置の保存

- 頁の移動から約0.8秒後に保存する。連続して移動している間は、最後の位置だけを保存する
- ビューアを閉じるときは、待たずに保存する。アプリの終了時にビューアを開いたままの場合も、保存する（待ち時間は最大2秒）
- 保存に失敗しても閲覧は続け、ログに記録する
- 復元の規則はDB設計書 6.3

### 26.7 画面の切り替え

- ライブラリ画面とビューア画面は、同じウィンドウ内で表示を切り替える。どちらも作り直さないため、ライブラリへ戻ったときに、スクロール位置・検索条件・選択が残る
- 「開く」操作は、ライブラリのViewModelがイベントで通知し、`MainViewModel` がビューアを開く。開けなかった場合は、理由がトーストで通知され、ライブラリ画面に留まる（UC-05 の異常フロー）
- ビューアの表示中だけ、ウィンドウがキー操作をビューアへ渡す。ライブラリ画面の検索欄などへの入力は妨げない
- 全画面は、ウィンドウの枠をなくして最大化する。解除すると、元の状態（大きさ・位置・枠）に戻る。全画面ではツールバーを隠し、現在位置と拡大率だけを表示する
- アーカイブを「開く」操作は、詳細表示では行のダブルクリックと Enter、サムネイル表示ではカードのダブルクリック
- サムネイル表示のカードの選択とキーボード操作は、Phase 9で対応した（30.4）

### 26.8 スコープ外とした項目

- 画像のEXIFの回転情報は考慮しない
- 見開き、右綴じ・左綴じ（要件定義の将来機能）
- 削除予約（Phase 7で実装。28章）
- ビューアを開いている間のアーカイブの外部変更の検出（Phase 8）

| `ViewerViewModel` | Presentation | 1枚表示と一覧表示の切替、選択、キー操作 |

### 27.2 位置と選択

- 現在位置は `ViewerSession.CurrentIndex` 1か所で持つ。1枚表示と一覧表示で同じ値を使うため、同期のための処理は不要
- 1枚→一覧: すでに現在の画像を含む複数選択があれば維持し、含まなければ現在の画像だけの選択にする。一覧→1枚: 選択を保つ
- クリックは、通常=1枚選択、Ctrl=選択の切替、Shift=範囲選択（起点は直前に通常クリックした画像で固定）。ダブルクリックでその画像から1枚表示
- キー操作は画面一覧設計書 4.5。一覧表示では、ズーム系のキーは処理しない
- 一覧表示の間は画像本体を読み込まない。位置の保存だけを予約する（閲覧位置の保存は26.6と同じ）

### 27.3 一覧表示の性能

- カードは仮想化し、画面に見える行だけを生成する。サムネイルは画面に出た頁だけ生成する
- 測定（開発機、2400×3400のJPEG、150頁）: 最初の18枚が約125〜150ms、残り132枚が約0.9〜1.4秒、メモリの増加は約33MB

### 27.4 進捗報告の順序と、一時的なエラーの再試行

- 進捗の報告は `ContextProgress<T>` で行う。呼び出し元に同期コンテキストがなければその場で同期実行し、あれば同じコンテキストへ順序どおりに投げる。標準の `Progress<T>` は、負荷時に報告の順序が入れ替わることがあり、画面の最終表示が古い進捗になる場合があったため置き換えた
- `ThumbnailService` は、解析で一時的なI/Oエラー（`IO_ERROR`、`ACCESS_DENIED`）が起きた場合に、200ms・800ms後に最大2回再試行する。壊れている・暗号化されている・存在しない場合は再試行しない（DB設計書 11.9）

### 27.5 スコープ外・未対応

- 閲覧中の外部変更の検出（Phase 8）
- ライブラリのサムネイル表示のカードのキーボード操作（Phase 9で対応。30.4）
- 画像のEXIFの回転、画面に見える行を優先した生成順

### 28.2 削除予約の状態と移動

- 予約の状態は `ViewerSession` が1か所で持つ。1枚表示と一覧表示は同じ状態を使うため、同期のための処理は不要。DB・ZIP・操作履歴には何も書かない（5.5、10章）

### 28.3 Delete の動作

- トグル: 対象がすべて予約済みなら解除、そうでなければ全部を予約
- 1枚表示で現在の画像を予約したときは、次の（なければ前の）予約されていない画像へ移動して表示する。どちらもなければ移動せず、現在の画像を「削除予定」の表示で残す
- アーカイブを開いていないときの Delete は何もしない。画像の読み込み中であっても、Delete は予約の状態だけを更新する（画像の読み込みを待たない）

### 28.4 アーカイブを離れるときの確認

- 確認は、ビューアの表示中に削除予約が1件以上あるときだけ行う。ライブラリへ戻る操作（`CloseRequested`）と、ウィンドウを閉じる操作（`Closing`）の両方で、同じ `ConfirmLeaveViewer` を使う
- 結果が「変更を破棄」のときだけ離れる。ビューアを閉じると `ViewerSession` ごと破棄されるため、予約も消える。「キャンセル」では何も変えず、ビューアに留まる（ウィンドウを閉じる操作は中止する）
- 「更新する」は、Phase 7では常に選べなかった。Phase 8で有効にした（29章）。`IDialogService.ConfirmLeaveArchive` の第3引数は、`bool canUpdate` から、更新できない理由（`string?`。更新できるなら null）に変えた
- 確認は、画面の切り替えを始める前（`_isTransitioning` を立てる前）に、同期的に行う。確認ダイアログはモーダルで、その間は他の操作を受け付けない

### 28.5 スコープ外・未対応

- 「更新する」（ZIPの再構築、ごみ箱への退避、外部変更のチェック）はPhase 8で実装した（29章）
- 削除予約した画像を前後の先読みの対象から外す最適化。先読みは位置の前1・後2のままで、予約済みの画像を先読みすることがある（読み込みを無駄にするだけで、動作には影響しない）
- 予約済みの画像だけを一覧から非表示にするフィルター

### 29.2 更新の手順と安全境界

1. 通知: 「更新を開始しました」。同じアーカイブの更新中なら、始めずに `UPDATE_IN_PROGRESS`（通知しない）
2. **確認**（キャンセル可）: ファイルの存在、開いた時点から外部で変更されていないこと（サイズ・更新日時）、ごみ箱へ退避できること（29.3）、空き容量（ローカルドライブのみ。元のZIPの大きさ＋16MB以上）。満たさなければ、何も作らずに中止する
3. **一時ZIPの作成**（キャンセル可）: 元のZIPと同じフォルダに `〈ファイル名〉.〈GUID〉.k35tmp` を新規作成する（拡張子がzip / cbz ではないため、スキャンの対象にならない。同名があっても上書きしない）。削除対象以外を元の順序でコピーする
4. **検証**（キャンセル可）: 一時ZIPを開き直し、エントリの数・名前・サイズ・CRC32が元と一致し、すべて展開できることを確認する
5. 安全境界の直前に、元のZIPが変更されていないことをもう一度確認する
6. **安全境界**（ここからキャンセルしない）: 元のZIPをごみ箱へ移動する。失敗した場合で、元のZIPが残っていれば、一時ZIPを削除して中止する（元のZIPと削除予約を保持）
7. 一時ZIPを元の名前にする。失敗した場合は、0.2秒・0.8秒・2秒後に最大3回やり直す。それでも失敗した場合は `REPLACE_FAILED`（29.6）
8. DB更新と操作履歴を1トランザクションで行う（DB設計書 11.3）
9. 通知: 「更新しました。N枚の画像を削除しました」

安全境界より前のどの失敗・キャンセルでも、一時ZIPを削除し、元のZIPは変更されず、呼び出し側のセッションの削除予約も保持される（`ApplyDeletionsAsync` はセッションを変更しない）。安全境界を越えたあとは、`CancellationToken` を参照しない。進行状況の報告（`IProgress`）が例外を投げても、更新は止めない（画面側の不具合で、安全境界以降の処理が中断されないようにするため）。

### 29.3 ごみ箱

- ごみ箱へ退避できない保存先では、更新を中止する。完全削除への自動切替はしない（要件定義 11章、7.5）
- `SHFileOperation` は、ネットワーク上のファイルやごみ箱が無効なドライブでは、確認なしで完全削除する。そのため、呼び出す前に29.2の2.で確認する。確認する内容は開発環境設計書 14.1
- ごみ箱への移動は、ビューアが閲覧のために開いたままのファイルに対しても行える（共有モードで開いているため）。ビューアは更新の前にファイルを閉じない

### 29.4 外部変更の検出

- `ViewerService.OpenAsync` が、アーカイブを開く直前のサイズと更新日時を `ViewerSession.OpenedFileState` に記録する
- 検出するのは、変更確認ダイアログを開く前（「更新する」を選べるかの判定）、更新の確認、安全境界の直前、およびウィンドウが前面に戻ったとき（閲覧中の通知。同じセッションにつき1回）
- 変更を検出した場合は、更新しない。閲覧中の画像は、開いたままのZIPから読み出し続けるため、外部で書き換えられると、読み出しが失敗または古い内容になることがある。通知は、その可能性を伝えるもの

### 29.5 更新後の表示

- 更新に成功したら、ビューアの閲覧位置の保存を止めたまま（`SuspendPositionSaving` → `MarkArchiveUpdated`）閉じる。更新で決めた位置を、更新前の位置で上書きしないため。更新を始める時点から止めるので、更新中に遅延保存が動いても上書きしない。失敗・キャンセルでは再開する
- ライブラリ画面は `LibraryViewModel.OnArchiveChangedAsync` で一覧を読み込み直し、サムネイルの作成を始める。解析待ち（`PENDING`）になったアーカイブの解析と、サムネイルの再生成（`STALE`）が行われ、画像枚数と表紙が更新後の内容になる
- スキャンが更新後のファイルを見ても、同じArchive IDのまま、サイズ・更新日時がDBと一致しているため、変更扱いにならない

### 29.6 置き換えの失敗

元のZIPをごみ箱へ移したあとに、一時ZIPを元の名前にできなかった場合。

- 更新前のファイルはごみ箱にあり、更新後のファイルは一時ファイルに残っている。ユーザーへ、その場所を通知する（トースト）
- 操作履歴に `IMAGE_DELETE`（`FAILED`、`error_code = REPLACE_FAILED`）を記録する。`old_path` は元のパス、`new_path` は一時ファイルのパス
- ビューアは閉じる（開いているファイルの内容が、もう現在のファイルではないため）。呼び出し側は、結果の `OriginalPreserved` が false であることでこれを判断する

### 29.7 再構築の詳細

- 圧縮: `Optimal` を基本に、元のZIPでほとんど圧縮されていないエントリ（圧縮後が元の95%以上）はそのまま保存する（開発環境設計書 13.3）
- 維持するもの: エントリ名（UTF-8）、順序、フォルダのエントリ、画像以外のエントリ、更新日時、外部属性、エントリのコメント。維持しないもの: ZIP全体のコメント、特殊な追加フィールド
- エントリ名を正しく読めないアーカイブ（UTF-8 でも Shift_JIS でもない。名前に U+FFFD を含む）は、名前を壊さないよう、更新を中止する（`UNSUPPORTED_ENTRY_NAME`）。Shift_JIS の名前は、Phase 10 で読めるようにした（31.3）
- 削除対象が元のZIPにない（アーカイブが閲覧中の内容と違う）場合は、`ENTRY_NOT_FOUND` で中止する
- エラーコード: `ARCHIVE_CHANGED`、`FILE_NOT_FOUND`、`RECYCLE_BIN_UNAVAILABLE`、`RECYCLE_FAILED`、`DISK_FULL`、`ACCESS_DENIED`、`ARCHIVE_BROKEN`、`IO_ERROR`、`ENTRY_NOT_FOUND`、`UNSUPPORTED_ENTRY_NAME`、`VERIFY_FAILED`、`REPLACE_FAILED`、`UPDATE_IN_PROGRESS`、`NOTHING_TO_DELETE`、`UPDATE_FAILED`（想定外）、`CANCELLED`

### 29.8 スコープ外・未対応

- CP932のエントリ名のアーカイブ（Phase 10 で対応。31.3）
- 更新中に異常終了した場合に残る一時ファイル（`〜.k35tmp`）の後始末（Phase 10 で対応。31.2）
- 進行状況の割合表示（段階の表示のみ）
- ネットワークドライブ・NAS上のアーカイブの更新（ごみ箱へ退避できないため、行わない）

### 30.2 操作の共通規則

- 実ファイルの操作が成功してから、DBの更新と操作履歴の記録を1トランザクションで行う（6.2、DB設計書 11章）
- 結果は `OperationResult` で返し、トーストで通知する。**操作の前の検証で断った場合**（同名がある、使えない名前、移動先が管理フォルダの外など）は、ファイルに何もしていないため、通知だけを行い、履歴には記録しない。**ファイルの操作に失敗した場合**は、通知と履歴（`FAILED`）の両方に反映する（ユースケース定義書 6.2）
- 対象のアーカイブが登録されていない、または不在（`MISSING`）の場合は、何もせず再スキャンを促す
- 操作の実行中は `LibraryViewModel.IsOperating` が true になり、重ねて操作できない。成功した場合は一覧とツリーを読み込み直し、サムネイルの作成を始める（移動先で再解析が必要になった場合のため）
- ビューアの表示中はライブラリ画面を操作できないため、ビューアで開いているアーカイブを名前変更・移動・削除することはない（UC-18 の「ビューアで開いているアーカイブが対象の場合」も、この構造で満たす）

### 30.3 各操作

- **名前変更**: 検証（30.5）→ 同名の確認（大文字小文字だけの変更は除く）→ ファイルの名前変更 → DB更新・履歴。DB更新に失敗した場合は、ファイル名を元に戻す
- **移動**: 移動先の確認（アクセスできる、管理フォルダの中、元と同じフォルダではない、同名のファイルがない）→ 移動 → 移動先のフォルダの登録（未登録なら途中のフォルダも）→ DB更新・履歴。異なるボリューム間はコピー → 大きさの確認 → 元の削除の順で、元を削除できなければ一部成功（`PARTIAL`）とする。移動先を管理フォルダの中に限るのは、外へ移すとライブラリから見えなくなり、Archive IDを維持する意味がなくなるため
- **削除**: 通常はごみ箱へ移動する。ごみ箱を使えない保存先では、画面が元に戻せないことを示して確認し、承認された場合だけ `permanent: true` で完全に削除する（自動の切替はしない）。ファイルを削除できてから、DBの登録とサムネイルの管理行を削除し、サムネイル画像のファイルを削除する
- **エクスプローラーで表示**: ファイルの存在を確認してから起動する。パスは常に引用符で囲む（Windowsのファイル名には引用符を含められない）
- **管理フォルダの解除**: 確認（件数つき）→ 1トランザクションで、サムネイルのパスの取得・登録の削除（CASCADE）・履歴の記録 → サムネイル画像のファイルの削除。スキャン中は実行できない（コマンドを無効にする）

### 30.4 選択とキー操作

- 選択は1件。詳細表示は一覧（`ListView`）の選択と双方向にバインドし、サムネイル表示はカードのクリックで選ぶ
- 一覧を取得し直したときは、選択していたアーカイブが一覧にあれば選択を保つ。操作の後は、操作したアーカイブ、それが一覧にない場合は操作前の次の（なければ前の）項目を選ぶ
- キー操作は `LibraryViewModel.HandleKey` に集約する。Enter・F2・Delete は両方の表示で使える。サムネイル表示では矢印・PageUp/PageDown・Home/End で選択を動かし、その行へスクロールさせる（`ScrollToRowRequested`）。詳細表示の矢印キーは、一覧の標準の動作に任せる
- 右クリックしたアーカイブ・ツリーの項目は、メニューを開く前に選択する。詳細表示の行（`ListViewItem`）とツリーの項目は右クリックを処理済みにするため、処理済みのイベントも受け取るハンドラーで選択する。ツリーは、入れ子の項目でも、右クリックした位置に最も近い項目を選ぶ

### 30.5 ファイル名の検証

- 前後の空白を除く。拡張子が .zip / .cbz でなければ、元の拡張子を付ける（「v1.2」のように「.」を含む名前でも、拡張子として扱わない）
- 断る名前: 空、`Path.GetInvalidFileNameChars()` の文字を含む、末尾が「.」、拡張子を除いた部分が空、予約名（CON、PRN、AUX、NUL、COM1〜9、LPT1〜9。「NUL.zip」も含む）、256文字以上
- 同名の確認は、検証に通った名前で、同じフォルダの既存のファイルと比べる（大文字小文字を区別しない）。名前変更のダイアログは、入力のたびにこの検証を行い、理由を表示する

### 30.6 スキャンとの競合

- スキャンは列挙（DBへ書き込まない）とDBへの反映を分けて行うため、その間にアプリ内で名前変更・移動すると、列挙結果は古い場所を指す。反映の際に、不在にする前に、DBの記録どおりの場所にファイルがあるかを確認し、あれば不在にしない（13.3、DB設計書 11.7）
- 古い場所のファイルは既にないため、新規の登録にもならない（反映の直前の再確認で除かれ、失敗として数える）

### 30.7 スコープ外・未対応

- 複数のアーカイブの同時選択と一括操作
- 操作履歴の画面（SCR-04。MVP対象外）
- ドラッグ＆ドロップでの移動
- 管理フォルダの外への移動
- 名前変更・移動の取り消し（Undo）

## 31. Ver.0.2.9で確定した実装方針（Phase 10 安定化）

上記の各章と異なる場合は、本章を優先する。

### 31.1 想定外の例外

`UnhandledExceptionReporter`（Infrastructure）が、どこでも処理されなかった例外をログへ記録する。起動時に `App` が登録する。

| 発生場所 | 扱い |
|---|---|
| 画面のスレッド（`Dispatcher.UnhandledException`） | Error で記録し、処理済みにしてアプリは続ける。利用者には「予期しないエラーが発生しました。操作は続けられますが、直前の操作が完了していない可能性があります」とログの場所を知らせる。続けて起きた場合、知らせるのは5秒に1回まで |
| 待たれなかったタスク（`TaskScheduler.UnobservedTaskException`） | Error で記録し、観測済みにする（アプリは続ける。利用者には知らせない） |
| それ以外のスレッド（`AppDomain.UnhandledException`） | Critical で記録する。.NETの既定どおり、アプリは終了する |

- 利用者に見せる文には、例外の内容やスタックトレースを含めない（ログだけに残す。15章）
- ログの出力は、1件ごとにファイルへ書き込まれる（Serilog のファイル出力の既定。バッファしない）ため、異常終了の直前の記録も残る

### 31.2 異常終了で残った一時ファイル（ユースケース定義書 6.2）

| 一時ファイル | 片付ける処理 | 規則 |
|---|---|---|
| 管理フォルダの中の `〈元の名前〉.〈GUID〉.k35tmp`（ZIP再構築、ボリュームをまたぐ移動） | スキャン（起動時の更新チェック、再スキャン、初回スキャン） | 同じフォルダに元のファイルがあれば、途中で止まった処理の作りかけなので削除する。元のファイルがなければ、置き換えの途中で止まった更新後のファイルや、移動の途中のファイルの可能性があるため、削除せずに残し、場所を通知する（「内容を確認し、不要なら削除してください」） |
| サムネイルのキャッシュの `〜.tmp` | 起動時の後始末（`StartupMaintenance`） | 削除する |
| アプリの一時フォルダ（`%LOCALAPPDATA%\K35Viewer\temp`）のファイル | 起動時の後始末 | 削除する |

- どれも、最後の書き込みから10分以内のものには触れない（実行中の処理が使っている可能性があるため）。使用中で削除できないものは、次の機会に回す
- 形式が違うファイル（GUIDの部分がない等）は、アプリが作ったものではないため触れない
- 一時ファイルは拡張子が zip / cbz ではないため、アーカイブとして登録されることはない
- 起動時の後始末は、画面の表示を待たせないよう、表示のあとに背景で行う。失敗しても起動は妨げない

### 31.3 Shift_JIS のエントリ名

- ZIPを読み取りで開くときは、必ず `ArchiveReader.OpenRead`（または同じ `ZipEntryNameEncoding` の指定）を使う。解析・閲覧・再構築・検証で開き方が違うと、同じエントリの名前が変わり、閲覧位置の記録や削除対象と一致しなくなるため
- UTF-8 のフラグがあるエントリは、.NETが常に UTF-8 で読む。フラグがないエントリだけ、名前のバイト列を厳密な UTF-8 として読み、不正なら Shift_JIS（CP932）として読む。どちらでも読めなければ、読めない部分を U+FFFD にする
- 再構築で作るZIPは、.NETの既定どおり、ASCII以外の名前を UTF-8 とフラグで保存する。Shift_JIS のアーカイブを更新すると、更新後は UTF-8 の名前のアーカイブになる（名前の文字列は同じ）
- 既知の限界: 半角カナだけからなる短い名前などは、まれに UTF-8 としても正しいバイト列になり、UTF-8 として読まれる（Shift_JIS の正しい名前にならない）。また、この変更の前に Shift_JIS のアーカイブで記録した閲覧位置（U+FFFD を含む名前）は一致しなくなり、次に開いたときは先頭から開く

### 31.4 二重起動の防止

- 起動時に名前つきのミューテックス（`Local\K35Viewer.SingleInstance`。ユーザーのセッションごと）を取得する。取得できなければ、すでに動いている方のウィンドウを（最小化されていれば元に戻して）前面に出し、終了する（終了コード 0）
- 二重に起動すると、同じDBに対してスキャン・サムネイルの作成が同時に動き、ログファイル（排他で開いている）も2つ目からは書けなくなるため

### 31.5 異常系の確認

| 異常 | 動作 | 確認 |
|---|---|---|
| 壊れたZIP | 解析で `BROKEN` とし、一覧に「破損」と表示。開こうとすると理由を通知してライブラリに留まる。再構築は `ARCHIVE_BROKEN` で中止 | 自動テスト（Phase 4・5・8） |
| 管理フォルダに接続できない（NAS切断） | 配下を不在にせず、管理フォルダを `UNAVAILABLE`（ツリーに「接続なし」）にする。接続が戻ると元どおり | 自動テスト（フォルダを見えなくして再現） |
| 閲覧中の切断 | 読めない頁はエラーとして表示し、閲覧は続けられる。接続が戻れば、次の頁は読める | 自動テスト（読み出しで IOException を返すアーカイブで再現） |
| ディスク容量不足 | ZIP再構築は、一時ZIPを作る前に空き容量（元の大きさ＋16MB）を確認して中止する。作成中に不足した場合も、書きかけを削除して元のZIPを保持する | 自動テスト（空き容量の取得と、容量不足の HRESULT を差し替えて再現） |
| 想定外の例外 | 31.1 | 自動テスト（画面のスレッドで例外を起こし、記録・通知・継続を確認） |

- 実際のNASでの切断、実際のディスクの容量不足は、環境がないため確認していない（上記はいずれも再現による確認）

- 25.5の「1行ぶんずつにまとめて仮想化する」構成は変えない。1行の中の並べ方だけを変えた

- 列の数は、一覧の使える幅（一覧の枠・内側の余白・縦スクロールバーの幅を除いた幅）に入るカードの数とする。ビューアの一覧表示（27章）も同じ規則で、使える幅の計算は `LibraryView.UsableWidth` を共用する
- 列の数は、一覧の大きさが変わったときに加えて、**一覧が表示されたとき**と**ViewModelがつながったとき**にも計算し直す。起動直後は、ViewModelがつながる前に一覧の大きさが決まり、その後は表示方式を切り替えても大きさが変わらないため、大きさの変化だけを見ていると、列の数が既定値のまま残る（画面の確認で見つかった不具合）

### 33.2 設定のファイル

- JSON。選択肢（外観、表示方式）は名前で保存する（例: `"Theme": "Light"`）。読んで意味がわかり、選択肢の並びを変えても壊れない
- ファイルにない項目は既定値になる（古い版で作ったファイルを読んでも、新しく増えた項目は既定値で動く）
- 読めない場合（JSON として不正、知らない選択肢の名前、`null`）は壊れたとみなし、既定値で起動する。壊れたファイルは `settings.json.broken` として残し（原因を調べられるように）、起動後に「設定のファイルを読めなかったため、初期の設定で起動しました」と通知する
- 保存に失敗しても（書き込めないなど）、変更はアプリの実行中は有効にする。ログに記録し、次の変更でもう一度保存する
- 読み込みに失敗しても、DB（ライブラリの情報）は使えるため、起動は止めない

### 33.3 外観

- 起動時は、画面を表示する前に、設定の外観を当てる（`App.xaml` の `ThemeMode="Dark"` は、設定を読む前の既定）。設定画面で変えると、`SettingsService.Changed` を受けて、その場で当て直す

- 独自のスタイルは、テーマのスタイルを引き継ぐ（`BasedOn`）。引き継がないと、古い見た目（白い入力欄など）に戻る（設定画面の、保存場所の欄で起きた）

### 33.4 表示方式の記憶

- ライブラリ: `LibraryViewModel.InitializeAsync` で、記憶した表示方式にする（このときは保存しない）。以降、切り替えるたびに保存する
- ビューア: アーカイブを開いたときに、記憶した表示方式で始める。一覧表示で始める場合は、画像本体を読み込まない（一覧表示の規則どおり。27章）。保存するのは、切り替えの操作（G、ツールバーのボタン）のときだけ。一覧でダブルクリックして1枚表示にするのは「その画像を見る」操作のため、記憶しない
- `SettingsService` は、両方の ViewModel の省略可能な引数（既定は null）にした。null なら記憶しない（それまでのテストは、そのまま動く）

### 33.5 設定画面からの、フォルダ・ページを開く

- `IExplorerLauncher` に、フォルダを開く（`OpenFolder`。なければ作ってから開く）と、Web のページを開く（`OpenWebPage`）を加えた
- ブラウザに渡すのは、アプリが組み立てた `https://github.com/` のページだけにする（ほかの URL は例外。任意の文字列を既定のプログラムで実行させないため）
- 開けなかった場合は、ログに記録して「開けませんでした」と通知する

### 33.6 テスト

- 設定のファイル: ファイルがない、保存と読み込み、項目が足りない、壊れている（3種類）、変更の通知と保存、起動時の壊れたファイル

## 34. v0.2.0 Phase 12 で確定した実装方針（確認のオン/オフ・サムネイルのキャッシュの削除）

要件定義 24.3・24.5、画面一覧 8.3。上記の各章と異なる場合は、本章を優先する。

### 34.1 確認のオン/オフ

- 設定は `AppSettings.ConfirmBeforeLeave`（離れるとき）と `ConfirmBeforeDelete`（削除するとき）。どちらも既定は true。設定画面のチェックボックスから、`SettingsService.Update` で、その場で保存する
- **離れるとき**（`MainViewModel.DecideLeave`）: オフで、削除予約があり、更新できる（`GetUpdateBlockReason` が null）場合は、ダイアログを出さずに `Update` を返す。ビューアを閉じる場合と、アプリを終了する場合の、どちらも同じ経路を通る。更新できない場合（外部変更、ごみ箱を使えない保存先など）は、オフでも DLG-01 を表示する（「更新する」は選べない）
- **失敗した更新を、確認なしで繰り返さない**: アプリの終了では、更新が失敗すると、ウィンドウを閉じる要求が再び `DecideLeave` を呼ぶ。オフのままだと、失敗する更新を確認なしで繰り返してしまう。そのため、更新が失敗・キャンセルされたあとの1回は、オフでも DLG-01 を表示する（`MainViewModel` の `_confirmNextLeave`。更新を終えるたびに、成功なら false、失敗なら true にする。ダイアログを出したら false に戻す）
- **削除するとき**（`LibraryViewModel.DeleteSelectedAsync`）: ごみ箱へ移せる場合だけ、設定がオフなら DLG-02 を省く。ごみ箱を使えない保存先の完全削除の確認は、設定によらず必ず出す（元に戻せないため）
- `SettingsService` は、`MainViewModel` の省略可能な引数（既定は null）にした。null なら、常に確認する（それまでのテストは、そのまま動く）

### 34.2 サムネイルのキャッシュの削除

| 部品 | 層 | 責務 |
|---|---|---|
| `ThumbnailCacheStore.GetTotalBytes` / `Clear` | Infrastructure | キャッシュの大きさを数える。サムネイルのファイルを削除する |
| `ThumbnailRepository.DeleteAllAsync` | Infrastructure | `thumbnail_cache` の記録をすべて削除する |
| `ThumbnailService.GetCacheSizeAsync` / `ClearCacheAsync` | Application | 大きさを返す。記録とファイルを削除する。作成中は実行せず false を返す |
| `IThumbnailCacheMaintenance` | Application | 設定画面から見た、キャッシュの管理の窓口（削除できない理由、大きさ、削除）。状態の変化は `INotifyPropertyChanged` で知らせる |
| `LibraryViewModel` | Presentation | `IThumbnailCacheMaintenance` を実装する。削除したあと、一覧を読み込み直し、作り直しを始める |

- **削除するもの**: キャッシュのフォルダの直下のサブフォルダにある `archive-*` のファイル（サムネイル本体と、書き込み途中の一時ファイル）だけ。同じフォルダにあるほかのファイルには触れない。削除できないファイルがあっても、残りの削除を続ける。空になったサブフォルダは消す
- **順序**: 記録（DB）を先に消し、そのあとにファイルを消す。途中で失敗しても、記録のないファイルが残るだけで、画面には出ない（作り直すときに上書きされる）
- **作り直し**: 記録を消すと、`GetPendingProcessingIdsAsync` の対象（記録のない、解析済みのアーカイブ）になる。削除のあと `LibraryViewModel` が一覧を読み込み直し（作成待ちの表示に戻る）、`StartThumbnailProcessing` で順に作り直す。失敗（FAILED）の記録も消えるため、作り直しの1回で再試行される
- **同時に実行しない**: `ThumbnailService.ClearCacheAsync` は、作成と同じ実行中の印（`_running`）を使う。削除の途中で作成が始まらず、作成中は削除できない。さらに `LibraryViewModel.ClearBlockedReason` が、スキャン中・作成中・他の操作の実行中は理由を返し、削除させない（要件定義 24.5）
- **設定画面**: 開いたとき（`InitializeAsync`）に大きさを調べ、`ClearBlockedReason` の変化を購読する。削除できない間は、ボタンを無効にし、ツールチップで理由を示す（`ShowOnDisabled`）。スキャンや作成が終わったら、ボタンを有効にし、大きさを調べ直す。閉じたとき（`Closed`）に、購読をやめる（ライブラリの ViewModel は、アプリの間ずっと生きているため）
- 確認のダイアログは出さない。削除したあと、「サムネイルのキャッシュを削除しました。サムネイルを順に作り直します」と通知する（画面一覧 8.3）

### 34.3 テスト

- キャッシュの保存場所: 大きさ、削除（サムネイルだけを消し、ほかのファイルとフォルダは残す）、フォルダがない場合
- `ThumbnailService`: 作成 → 削除（記録もファイルも消え、アーカイブの登録は残る）→ 作り直し
- `LibraryViewModel`: 削除すると作成待ちに戻り、作り直されて、READY に戻る
- 設定画面: 大きさの表示、削除と通知、削除できない間の無効とツールチップ、終わったあとの再計算、削除できない状態になっていた場合の警告
- 確認: 設定の保存、削除の確認がオフ（確認なしでごみ箱へ。完全削除は確認する）、離れるときの確認がオフ（確認なしで更新して離れる、削除予約がなければ何もしない、更新できない場合は確認する、更新をキャンセルしたあとは確認する）

## 35. v0.2.0 Phase 13 で確定した実装方針（バックアップと復元）

要件定義 24.5、画面一覧 8.3。上記の各章と異なる場合は、本章を優先する。Phase 13 は、バックアップの作成（35.1〜35.2。実装済み）と、復元（35.3。次のコミットで実装し、結果をここに追記する）に分けて進める。

### 35.1 バックアップの作成

| 部品 | 層 | 責務 |
|---|---|---|
| `BackupService` | Application | バックアップの作成、一覧、古い自動バックアップの整理 |
| `AppPaths.BackupsDirectory` | Infrastructure | 保存先（`<データの保存先>\backups`）。最初のバックアップを作るときに作る |
| `AppSettings.AutoBackupKeepCount` | Infrastructure（Settings） | 自動バックアップを残す数（既定5、範囲1〜20） |

- **ファイルの形**: ZIP 1つ。`K35Viewer-backup-〈yyyyMMdd-HHmmss〉.zip`（手動）、`K35Viewer-auto-〈yyyyMMdd-HHmmss〉.zip`（自動）。同じ秒に続けて作った場合は、`-2`、`-3` と番号を足す（上書きしない）。時刻は、ローカル時刻
- **中身**: `library.db`（DB の整合のとれたコピー）、`settings.json`（あれば）、`manifest.json`（`FormatVersion`、`AppVersion`、`SchemaVersion`、`CreatedAt`、`Kind`）。サムネイルのキャッシュとログは含めない
- **DB の写し方**: SQLite のバックアップ機能（`SqliteConnection.BackupDatabase`）で、別のファイルへ写す。スキャンなどでDBを使っている最中でも、整合のとれたコピーになる（ファイルのコピーでは、WAL の途中を写してしまう）。写したあとは `journal_mode = DELETE` にして、`-wal` / `-shm` のファイルを残さない。写し先の接続は、プールを使わない（閉じたときにファイルを手放し、作業フォルダを消せるようにする）
- **作り方**: 作業フォルダ（`temp\backup-〈GUID〉`）に3つのファイルを置き、ZIP を `.tmp` として作ってから、名前を変える。途中で失敗しても、不完全なバックアップのファイルは残らない。作業フォルダは、成功・失敗に関わらず消す
- **整理**（`PruneAutoBackups`）: 自動バックアップ（名前の `auto`）を、新しいものから残す数だけ残して、ほかを削除する。手動のバックアップは、数に関わらず削除しない。呼び出し側が指定したファイル（復元元）も削除しない。残す数が範囲の外なら、範囲に収める。自動バックアップを作ったあと、設定の数を変えたときに、整理する
- **一覧**（`List`）: 名前が上の形式に合うファイルだけを、新しいものが先で返す。ほかの名前のファイル（利用者が置いたメモなど）は、無視する

### 35.2 設定画面

- 「バックアップ」の行: 最後のバックアップ（日時と、手動 / 自動）、「バックアップを作成」、「フォルダを開く」。作っている間は、作成のボタンを押せない。失敗は、ログに記録して通知する
- 「自動バックアップ」の行: 残す数を、1〜20から選ぶ（`ComboBox`）。選ぶと、その場で保存し、整理する

### 35.3 復元（方針。実装は次のコミット）

1. 選んだ ZIP を検証する（ZIP として開ける、3つのファイルの形が合う、`manifest.json` の `SchemaVersion` が、今のアプリが対応する版以下）。今のアプリより新しい版のものは、理由を表示して復元しない
2. 確認のダイアログ（画面一覧 8.3）。復元元を、一時フォルダに展開する
3. 今のデータを、自動でバックアップする（復元元は、整理の対象から外す。残す数が1でも、復元元は消えない）
4. 入れ替える予定の目印を残し、アプリを終了して、新しいプロセスを起動する。単一起動の仕組み（mutex）があるため、新しい方は、古い方が終わるまで待つ
5. 新しい方は、起動の最初（DB を開く前）に、`library.db`（と `-wal` / `-shm`）、`settings.json` を入れ替える。サムネイルのキャッシュのファイルと、DB の `thumbnail_cache` の記録は消し、作り直す
6. 入れ替えの途中で失敗した場合は、元のファイルに戻して、通常どおり起動する
